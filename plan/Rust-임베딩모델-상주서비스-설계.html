Rust 임베딩 모델 상주 서비스
— 파일마다 exe 를 불러도 모델은 한 번만 올린다

엠파워 v11 은 파일 하나마다 MpowerClassify-rs.exe 를 한 번씩 부른다. 지금 Rust 판은 그때마다 임베딩 모델을 새로 읽는다. 파이썬 판처럼 모델을 물고 있는 상주 프로세스를 두고, exe 는 거기에 텍스트만 보내 벡터를 받아 오게 한다.

대상 Rust 엔진 (MpowerClassify-rs) 범위 새 daemon 모듈 · main.rs 인자/2차 임베딩 단계 분류 결과 변화 없음(목표) 상태 설계 · 구현 완료 2026-10-12 (§16) 작성일 2026-10-12
한 줄 요약

--serve 로 임베딩만 맡는 상주 프로세스를 띄우고, 분류 호출에 --daemon 을 붙이면 모델을 직접 읽는 대신 그 프로세스에 묻는다. 추출·규칙·전파는 지금처럼 호출한 exe 안에서 돈다. 상주 프로세스를 못 쓰면 지금 방식(직접 로드)으로 조용히 되돌아가므로 결과가 안 나오는 경우는 생기지 않는다. 옵션 이름·통신 규약은 파이썬 판과 같게 맞춘다.

01

왜 필요한가

Rust 판에는 상주 데몬이 없어 모든 실행이 콜드 스타트다. 임베딩이 필요한 호출은 매번 아래를 새로 치른다 embed.rs:224 Embedder::load().

  • model.onnx 118MB 읽기 + ORT 세션 구성 + Level3 그래프 최적화(CPU 작업 — 페이지 캐시로도 안 없어진다)
  • tokenizer.json 17MB 파싱
  • onnxruntime.dll 동적 로딩

기존 실측(Rust/README.md 성능표, 200건 --with-vector)으로 보면 이 고정비가 건당 약 1.4초다.

호출 방식RustPython(데몬 on)
--files-from 1회 (한 프로세스)44.0s (0.22s/건)84.0s
--file 200회 (파일마다 프로세스) — v11 이 쓰는 방식320.6s (1.60s/건)265.5s (1.33s/건)

그동안의 권고는 "--files-from 으로 한 프로세스에 몰아 달라"였다. v11 연동은 로직상 그럴 수 없으므로 (파일 1건 = exe 1회), 남는 방법은 모델을 프로세스 밖에 상주시키는 것뿐이다.

기대치

임베딩이 필요한 호출에서 건당 약 1.4초가 "소켓 왕복 1번"으로 바뀌는 것이 목표다. 이 숫자는 기존 실측에서 뺀 추정이고, 실제 값은 구현 뒤 같은 200건으로 다시 잰다(§13). 규칙만으로 끝나는 호출은 2026-09-02 지연 로딩 덕에 이미 모델을 안 읽으므로 이번 변경으로 달라지는 것이 없다.

02

결정 요약

항목결정이유
상주 프로세스가 맡는 일임베딩만(텍스트 → 벡터) 분류 로직이 한 곳(호출한 exe)에만 있어야 결과가 안 갈린다. 파이썬 분류 경로도 embed_text 만 쓴다.
켜는 방법분류 호출에 --daemon (기본은 꺼짐) 기존 호출부·UI·배치 동작을 그대로 둔다. 지금도 받는 인자라 호출부 수정이 한 단어다.
미리 띄우기--serve 로 직접 기동 + 없으면 첫 --daemon 호출이 자동 기동 "처음부터 떠 있게" 와 "죽어도 다시 뜨게" 를 둘 다 만족.
통신127.0.0.1 TCP · 4바이트 길이 + JSON · 토큰 파이썬 판 daemon/ipc.py 와 같은 규약. 윈도우·리눅스 공통, 새 크레이트 불필요.
유휴 종료기본 0 = 무한(자동 종료 없음), --idle-timeout N 으로 유한 파이썬 판 기본값과 같다. v11 은 "항상 떠 있어야" 한다.
못 쓸 때지금 방식(프로세스 안 직접 로드)으로 폴백 상주 프로세스는 속도 장치일 뿐, 없다고 분류가 실패하면 안 된다.
파이썬 데몬과의 관계서로 안 섞는다(레지스트리 파일명 분리) 파이썬 클라이언트는 버전이 다른 데몬을 정지시킨다 — 같은 파일을 쓰면 서로 죽인다(§7).
03

검토한 대안

안내용판단
A. 임베딩 상주 채택 상주 프로세스는 모델만 물고, 추출·규칙·seed 비교는 호출한 exe 가 한다. 고정비의 대부분(모델 로드)을 없애면서 바뀌는 코드가 가장 적다. 결과 동일성을 지키기 쉽다.
B. 분류 전체 상주 파일 경로를 보내면 상주 프로세스가 분류까지 해서 레코드를 돌려준다. 정책 파일 로드·pdfium 초기화까지 아끼지만, 정책이 바뀌면 다시 읽어야 하고 출력·옵션·오류 계약을 통째로 원격화해야 한다. 이번 범위를 크게 넘는다. A 를 재고 나서 남는 고정비가 크면 그때 검토.
C. Rust exe 가 파이썬 데몬에 붙기 이미 있는 파이썬 --serve 를 재사용. 파이썬 판 배포가 같이 깔려야 한다. Rust 판을 쓰는 이유(단일 바이너리)와 어긋난다.
D. --files-from 로 묶기 호출 구조를 바꾼다. v11 로직상 불가(전제).
04

구조와 호출 흐름

  1. 3번에서 "필요 없음"이면 상주 프로세스에 접속조차 하지 않는다. 기존 need_any 게이트를 그대로 쓴다 main.rs:2982.
  2. 필요하면 지금 Embedder::load() 를 부르는 한 자리 main.rs:2997 만 "상주 프로세스 우선, 실패 시 직접 로드"로 바꾼다.
  3. 그 뒤의 seed 비교·전파·출력은 벡터가 어디서 왔는지 모른다(변경 없음).

CLI 옵션

이름은 전부 파이썬 판에 이미 있는 것이다. Rust 판도 지금 인자로는 받고 있어 main.rs:602-608, 657, 새 이름은 하나도 없다 — 뜻만 채운다.

옵션지금(Rust)바뀐 뒤
--serve미지원 오류(1012, 종료코드 3) 이 프로세스가 상주 서버가 된다. 포그라운드로 돌며 정지/유휴 종료 때 0 으로 끝난다. 같은 모델 서버가 이미 있으면 한 줄 알리고 0.

06

통신 규약

파이썬 판 daemon/ipc.py 와 같다: 연결 하나에 요청 하나, 응답 하나. 메시지는 [길이 4바이트 big-endian][UTF-8 JSON], 한 메시지 상한 16MB.

op요청응답토큰
ping{op} {ok, model_ready, model, dim, version, proto, pid}불필요
embed_text{op, token, text} {ok:true, vector, dim, model, version}
{ok:false, error, kind}		필요
stop{op, token}{ok:true}필요
그 밖(embed 등)—{ok:false, kind:"bad_op"}—
  • 파이썬의 embed(파일 경로를 보내 서버가 추출까지)는 만들지 않는다. Rust 판의 추출은 언제나 호출한 exe 가 한다.
  • 텍스트는 다듬지 않은 채 보낸다. 서버가 부르는 embed_document() 가 지금처럼 clean_for_embed 를 스스로 하므로, 직접 로드할 때와 같은 입력이 같은 함수를 지난다.
  • 청크 크기·겹침 옵션은 받지 않는다. Rust 판은 512/32 고정이고 다른 값은 이미 인자 단계에서 1012 로 멈춘다 embed.rs:107.
  • kind 는 auth(토큰 불일치) · embed(빈 텍스트/추론 실패 — 직접 로드에서 None 이 나오는 경우) · not_ready(모델 올리는 중 — 부른 쪽이 잠깐 뒤 다시 묻는다) · bad_op.
  • 텍스트 상한(기본 200만 자)은 한글 기준 약 6MB 라 16MB 안에 든다. 상한을 올려 넘치는 문서는 그 문서만 직접 로드로 처리한다.
07

레지스트리와 "하나만 뜨기"

"지금 이 모델 서버가 어느 포트에 있나"를 파일로 남긴다. 자리는 파이썬 판과 같은 상태 폴더, 파일 이름만 다르다.

PythonRust(이번 설계)
폴더%LOCALAPPDATA%\MpowerClassify (없으면 ~/.csoclassify)
접속 정보daemon-<model>.jsondaemon-rs-<model>.json
잠금daemon-<model>.json.lockdaemon-rs-<model>.json.lock
내용pid, host, port, token, version, model, idle_timeout, started같은 칸 + proto, dim, exe
왜 분리

파이썬 클라이언트는 기록의 version 이 자기와 다르면 그 데몬에 stop 을 보내고 기록을 지운다 client.py:97. 같은 파일을 쓰면 두 판이 한 PC 에 같이 깔렸을 때 서로의 서버를 계속 죽인다. 또 Rust 판은 NFC 정규화가 빠져 있어 embed.rs:344 두 판의 벡터가 완전히 같다는 보장도 없다. 섞지 않는다.

서버 기동 순서

  1. 잠금 파일을 "없을 때만 만들기"로 만든다. 성공하면 내가 서버다(pid·시각 기록).
  2. 소켓을 먼저 연다(127.0.0.1, 포트 0 = OS 가 빈 포트 지정) → 토큰 생성 → 접속 정보 파일을 임시 파일에 쓰고 이름 바꾸기로 교체.
  3. 그다음에 모델을 올린다. 실패하면 기록·잠금을 지우고 model_load_failed(3002, 종료코드 2).
  4. 요청 루프. 끝날 때(정지·유휴·Ctrl+C) 기록·잠금을 지운다.

이미 잠금이 있을 때 — 살아 있는 서버인가

파이썬 판은 "기록된 pid 가 살아 있는가"로 판단한다. Rust 판은 "기록된 포트에 실제로 접속되는가"로 판단한다.

관찰판정
접속되고 ping 응답의 pid 가 기록과 같다살아 있음 — 나는 물러난다(0)
위와 같되 응답의 model_ready 가 false모델 올리는 중 — 물러난다(0)
ping 이 안 돌아오지만 잠금이 생긴 지 3초 안기록을 쓰기 직전의 기동 중 — 물러난다(0)
그 밖(접속 안 됨 / 응답이 엉뚱함 / pid 가 다름)죽은 기록 — 지우고 한 번 더 시도
파이썬과 다른 점

pid 방식은 서버가 강제 종료되거나 PC 가 재부팅된 뒤 그 pid 를 다른 프로그램이 받으면 "아직 살아 있다"고 오판한다. 그러면 새 서버는 뜨자마자 물러나고, 클라이언트는 호출마다 기동 대기(20초)를 다 채운 뒤에야 폴백한다. "항상 떠 있어야 하는" 용도에서는 치명적이라 접속 여부로 바꾼다. 소켓을 모델보다 먼저 여는 것(순서 2→3)도 이 판정을 위해서다 — 구현에서는 한 걸음 더 가서, 요청을 받는 스레드를 모델보다 먼저 띄워 모델을 올리는 중에도 ping 에 "살아 있음, 준비 중"이라고 답한다. 그래서 "느려서 답이 없다"와 "죽었다"를 시간으로 추측할 필요가 없다. 덤으로 pid 확인용 OS API 를 부를 필요가 없어진다.

토큰은 OS 난수 16바이트(hex)다. getrandom 은 이미 의존 트리에 있어(Cargo.lock) 직접 의존으로 올려도 새로 받는 것이 없다. 리눅스에서는 접속 정보 파일을 0600 으로 만든다.

08

클라이언트 동작과 폴백

// main.rs:2997 자리 — 의사 코드
let mut backend = if opts.daemon { EmbedBackend::Daemon(client) } else { EmbedBackend::Local(None) };
for it in items.iter_mut() {
    if need_vec(it) { it.vector = backend.embed_document(&it.text); }
}

// EmbedBackend::embed_document
Daemon  → 빠른 길: 기록 읽기 → 접속 → embed_text → 벡터
            ├ 응답 ok:false, kind=embed      → None (직접 로드의 None 과 같은 뜻. 폴백 아님)
            └ 접속·통신 실패 / 버전·모델·차원 불일치
                 → 느린 길: (불일치면 stop) → 자동 기동 → ping 폴링(최대 20초) → 재요청
                      └ 그래도 실패 → note 한 줄 + Local 로 전환(이 실행의 남은 문서 전부)
Local   → 처음 필요할 때 Embedder::load() 한 번 → embed_document
  • 빠른 길에는 ping 이 없다. 파이썬은 요청마다 ping 연결 + 본 요청 연결로 두 번 왕복한다. 응답에 model·dim·version 을 실어 한 번으로 줄인다.
  • 응답 검증: dim 이 이번 모델 스펙과 다르거나 벡터 길이가 다르면 그 서버를 쓰지 않는다 — 다른 차원 벡터가 seed 와 섞이면 조용히 틀어진다(직접 로드의 기존 방어와 같은 이유).
  • 버전 불일치(exe 를 교체했는데 옛 서버가 남음): 기록의 version·proto 가 다르면 stop 을 보내고 새로 띄운다. 배포 교체 때 서버를 따로 내리지 않아도 된다.
  • 배포 점검은 그대로 한다 main.rs:2481. 파일 존재 확인(stat 몇 번)이라 싸고, 폴백이 실제로 가능한지 미리 알려 준다. 점검이 실패했더라도 살아 있는 서버가 있으면 그 서버는 쓴다.
  • 폴백까지 실패하면 지금과 같다: 결과는 내고 종료코드 2(3002), --vector-only 는 결과 없이 멈춘다. 새 오류코드는 만들지 않는다.

자동 기동

자기 자신을 --serve --model <m> --idle-timeout <n> (+ --log, -v 물려주기)로 띄운다. 표준 입출력은 전부 버리고 부모와 분리한다 — 윈도우는 DETACHED_PROCESS | CREATE_NO_WINDOW | CREATE_NEW_PROCESS_GROUP, 리눅스는 새 프로세스 그룹. 동시에 여러 호출이 띄워도 잠금이 하나만 남긴다.

확인 필요

v11 이 exe 의 stdout 을 파이프로 받아 읽는다면, 자동 기동된 서버가 그 파이프 핸들을 물려받는 순간 v11 은 "출력이 안 끝났다"고 보고 영영 기다린다. 표준 입출력을 버리도록 띄우면 물려받지 않을 것으로 보지만 구현 때 직접 시험해서 확인한다(§13 시험 6). v11 이 시작할 때 --serve 로 미리 띄워 두면 자동 기동 자체가 거의 일어나지 않는다.

09

서버 동작

  • 임베딩은 한 번에 하나씩 처리한다. ORT 세션은 추론할 때 독점이 필요하고(embed_one(&mut self)), 추론 자체가 이미 코어를 다 쓴다. 연결마다 스레드를 하나 쓰되 모델은 잠금으로 차례를 지킨다 — 그래서 긴 임베딩이 도는 중에도 ping 은 곧바로 답한다(구현 때 바꾼 점. 파이썬 판은 연결 자체를 하나씩 받는다).
  • 연결마다 읽기 한도 10초. 요청을 보내다 만 클라이언트가 서버 전체를 붙잡지 못하게 한다(파이썬 판에는 없는 방어).
  • 유휴 종료: --idle-timeout N 이면 N초 동안 접속이 없을 때 스스로 끝난다. 0 이면 무한.
  • 종료 정리: 정지 요청·유휴·Ctrl+C 어느 쪽이든 접속 정보·잠금 파일을 지운다. 지금 Ctrl+C 처리기는 임시폴더만 지우고 130 으로 끝내므로 main.rs:2123, 서버 모드에서는 레지스트리 정리를 더한다. 강제 종료로 못 지운 기록은 §7 판정이 걸러 낸다.
  • 로그: --log 로 받은 파일에 시작·준비 완료(포트)·요청별 소요(글자 수, ms)·종료 사유를 남긴다. 문서 본문은 남기지 않는다.
  • 보안: 127.0.0.1 에만 묶는다(외부 주소 금지). 임베딩·정지는 토큰이 맞아야 한다. 토큰은 사용자 프로필 폴더의 파일에만 있다.
  • 메모리: 모델 하나를 계속 물고 있다(수백 MB 수준 예상 — 실측해서 가이드에 적는다). 모델을 여러 개 쓰면 서버도 그만큼 뜬다.
10

결과가 같아야 한다

이 변경의 조건은 하나다 — --daemon 을 붙여도 레코드가 한 글자도 달라지지 않는다.

  • 같은 코드: 서버도 embed::Embedder::embed_document() 를 그대로 부른다. 임베딩 로직을 복사하지 않는다.
  • 같은 모델: 서버·클라이언트가 같은 exe, 같은 모델 폴더 규칙을 쓴다. 기록의 version 과 응답의 dim 으로 어긋남을 잡는다.
  • 숫자 왕복: 벡터는 f32 → JSON 글자 → f32 로 오간다. serde_json 은 f32 를 "되읽으면 같은 값이 되는 가장 짧은 표기"로 쓰므로 값이 보존될 것으로 본다. 다만 읽는 쪽이 f64 를 거쳐 f32 로 내려오는 경로라 이론상 예외를 배제하지 못했다. 그래서 시험 2 에서 비트 단위 일치를 직접 확인하고, 하나라도 어긋나면 벡터만 리틀엔디언 바이트(base64)로 싣는 것으로 바꾼다(규약의 proto 번호를 올림).
  • 모델 폴더가 다른 경우: 서버를 CSO_MODEL 등 환경변수가 다른 상태로 띄우면 클라이언트가 직접 로드할 때와 다른 모델을 쓸 수 있다. 기록에 서버가 실제로 연 모델 폴더 경로를 넣고, 클라이언트가 자기 쪽 해석과 다르면 그 서버를 쓰지 않고 경고한다.
11

v11 에서 쓰는 방법

  1. v11 서비스가 시작할 때 MpowerClassify-rs.exe --serve --model <모델> 을 자식 프로세스로 띄워 둔다(창 없음). 첫 파일부터 웜이다.
  2. 파일마다 기존 명령에 --daemon 을 붙인다.
  3. 서버가 죽었으면 다음 호출이 자동으로 다시 띄운다. 그 호출 한 번만 모델 로드 시간만큼 느리다.
  4. exe 를 새 버전으로 바꾸면 다음 호출이 옛 서버를 정지시키고 새로 띄운다.
계정 주의

접속 정보 파일은 사용자별 폴더(%LOCALAPPDATA%)에 있다. 서버를 띄운 계정과 exe 를 부르는 계정이 다르면 (예: 서버는 관리자가 손으로, 호출은 SYSTEM 서비스가) 서로를 못 찾고, 호출하는 계정으로 서버가 하나 더 뜬다. 서버 기동과 파일별 호출을 같은 계정(같은 v11 프로세스)이 하도록 한다. 계정을 맞출 수 없는 구성이라면 양쪽에 환경변수 CSOCLASSIFY_STATE_DIR 로 같은 폴더를 준다(구현에 넣었다 — 시험 격리에도 필요했다).

윈도우 서비스(SCM) 등록·systemd 유닛은 이번 범위에 넣지 않는다. --serve 는 포그라운드 프로세스라 필요하면 작업 스케줄러·NSSM·systemd 가 그대로 감쌀 수 있다.

#질문설계의 가정(권고)
1상주 서버 사용을 기본으로 켤까, --daemon 을 줄 때만 쓸까? 줄 때만. 기존 호출부·UI 배치는 그대로 두고 v11 만 한 단어를 더한다. 파이썬 판은 기본 on 이라 두 판의 기본값은 달라진다.
2v11 은 exe 를 동시에 몇 개까지 부르나? 한 번에 하나씩 처리로 충분하다고 가정. 동시 호출이 많고 문서가 길면 대기가 생기므로, 그 경우 서버 내 병렬을 2차로 검토.
3v11 은 어떤 계정으로 exe 를 부르나(서비스 계정/로그인 사용자)? 서버 기동과 호출이 같은 계정. 다르다면 CSOCLASSIFY_STATE_DIR 를 추가한다.
4윈도우 서비스로 등록하는 기능까지 필요한가? 이번에는 넣지 않는다. v11 이 자식 프로세스로 띄우는 것으로 충분하다고 가정.
5v11 은 exe 의 stdout 을 파이프로 읽나, 결과 파일(--out)을 읽나? 어느 쪽이든 되게 만든다(시험 6). 파이프라면 --serve 미리 띄우기를 강하게 권한다.

구현 결과 (2026-10-12)

§15 의 1~4단계를 모두 구현했다. §14 의 질문은 답을 받기 전이라 표의 "가정(권고)" 대로 만들었다 (기본 꺼짐 · 임베딩은 차례로 · 윈도우 서비스 등록 없음).

설계와 달라진 점

  • ping 은 임베딩과 따로 곧바로 답한다(§7·§9). 모델을 올리는 중에도, 긴 임베딩 중에도 생존 확인이 막히지 않는다.
  • CSOCLASSIFY_STATE_DIR 를 넣었다(§14-3 은 "필요하면"이었다). 시험이 개발자 PC 의 실제 서버를 건드리지 않으려면 어차피 필요했다.
  • 응답의 chunks 칸은 뺐다. 이 판의 embed_document() 는 청크 수를 돌려주지 않고, 쓰는 곳도 없다.
  • 큰 문서: 본문이 8MB(메시지 상한의 절반)를 넘으면 그 실행은 직접 로드로 넘어간다. 기본 상한(200만 자 ≈ 6MB)에서는 걸리지 않는다.
  • 윈도우 자동 기동: 띄우기 직전에 이 프로세스의 표준 입출력 핸들의 "상속 가능" 표시를 끈다. 자식에게 NUL 을 주는 것만으로는 부른 쪽이 준 파이프 핸들이 서버로 따라가는 것을 막지 못하기 때문이다(§8 "확인 필요"의 답).
  • 자동 기동 횟수 상한 2회. 뜨자마자 죽는 서버(모델 없음 등)를 호출 한 번이 끝없이 띄우지 않는다.
