개선 설계 · Pre-decrypt Size Gate

복호화 전 크기 상한 정합
— 풀기 전에 거르는 기준을 풀린 뒤의 기준과 같게

암호화 문서는 풀기 전에 크기를 보고 너무 크면 풀지 않는다. 그런데 지금은 파일 종류와 상관없이 일반 문서 상한(100MB) 하나로만 거른다. 풀린 뒤에는 압축파일·텍스트에 다른 상한이 적용되므로, 같은 파일이 평문이면 분류되고 엠파워에 올라가 있으면 분류되지 않는 일이 생긴다. 이 설계는 앞 상한을 없애지 않고, 풀린 뒤 실제로 적용될 상한을 미리 골라 쓰게 바꾼다.

대상 Rust 판 · Python 판 같은 계약 범위 복호화 직전 크기 검사(+ Rust --text-only) 기존 실행 100MB 이하 문서는 변화 없음 상태 설계 · 구현 완료 2026-10-16 (§10) 작성일 2026-10-16 관련 엠파워v11-암호화문서-복호화연동-설계-20261012 §9
한 줄 요약

복호화 전 크기 검사를 (1) 원래 크기(org_size)가 있으면 그것으로, (2) 원래 이름의 확장자로 압축·텍스트·일반을 갈라 각자의 상한으로 본다. --no-size-limit 이면 지금처럼 앞 상한도 모두 끈다. 결과적으로 평문 파일과 암호화 파일이 같은 크기에서 같은 판정을 받는다.

01

지금 동작

복호화 직전에 저장 파일(.SMF) 크기를 MAX_FILE_BYTES(기본 100MB)와 견줘, 넘으면 도구를 부르지 않고 size_limit 로 남긴다.

# Python — cli.py _iter_dec_jobs
max_b = config.MAX_FILE_BYTES
if max_b and max_b > 0 and src_len > max_b:
    raise decrypt.DecError("size_limit", "저장 파일이 크기 상한을 넘어 풀지 않았습니다(…)")

# Rust — main.rs 분류 루프
let max = limits::max_file_bytes();
Ok(_) if max > 0 && src_len > max => Err(DecError { reason: "size_limit", … })
항목지금
비교하는 크기저장 파일(.SMF) 크기 stored_size
비교하는 상한언제나 MAX_FILE_BYTES (기본 100MB, --max-file-mb · CSOCLASSIFY_MAX_FILE_BYTES)
--no-size-limitMAX_FILE_BYTES = 0 → "0 이하 = 상한 없음" 규칙으로 이미 꺼진다(두 판 모두)
Rust --text-only --decrypt앞 검사가 아예 없다 — 바로 풀고, 풀린 뒤 추출기 상한만 본다(Python 판은 있음)

풀린 뒤에는 지금까지처럼 추출 단계의 상한을 한 번 더 거친다. 이 상한은 파일 종류마다 다르고, 종류는 내용으로 판별한다.

풀린 파일 종류(내용 판별)풀린 뒤 상한기본값바꾸는 법
압축(zip · 7z · rar · tar · gz · bz2 · xz)MAX_ARCHIVE_BYTES500MB--max-archive-mb
텍스트 계열(text · html)MAX_FILE_BYTES_TEXT100MB--max-file-mb-text
그 밖의 문서(hwp · docx · pdf …)MAX_FILE_BYTES100MB--max-file-mb
02

문제 — 앞 상한과 뒤 상한이 어긋난다

앞 상한은 "어차피 뒤에서 버려질 문서를 풀지 않으려는" 장치다. 그렇다면 뒤에서 받아 줄 문서는 앞에서도 통과해야 한다. 지금은 그렇지 않다.

경우평문 파일이면엠파워 암호화 파일이면 (지금)
200MB 7z 묶음펼쳐서 분류(압축 상한 500MB)풀지도 않고 size_limit
150MB csv, --max-file-mb-text 200분류풀지도 않고 size_limit(앞 상한은 여전히 100MB)
정확히 100MB 문서, enc_mode=26분류저장본에 32바이트 머리가 붙어 100MB+32 → size_limit
120MB 문서, zip_mode≠0(저장본 80MB)상한 초과앞 검사는 통과 → 120MB 를 다 푼 뒤 추출 상한에서 버림(시간·임시 공간 낭비)
현실

엠파워 기본 정책은 zip 을 암호화하지 않지만(ENC_LIST 제외), 7z · egg 는 암호화한다(2026-10-15 확인). 큰 7z 묶음은 실제로 생길 수 있는 경우다.

03

원칙

  1. 앞 상한은 뒤 상한의 "미리 보기"다. 판정의 주인은 여전히 풀린 뒤의 추출 상한이다. 앞 상한은 버려질 문서를 일찍 거르는 최적화일 뿐이다.
  2. 평문과 암호화가 같은 판정을 받는다. 같은 크기 · 같은 종류 · 같은 옵션이면 결과가 같아야 한다.
  3. 모르면 지금처럼. 종류를 알 수 없으면(이름 없음) 지금 기준(MAX_FILE_BYTES, 저장 크기)을 그대로 쓴다 — 지금보다 느슨해지는 경우를 만들지 않는다.
  4. 상한은 없애지 않는다. 엠파워 도구(mpower_decrypt)에는 크기 제한이 없지만, 큰 문서를 풀면 시간 · 임시 공간(/dev/shm 이면 메모리) · 시간 제한 위험만 늘고 결과는 같다.
04

설계

4-1. 무엇의 크기를 보나 — 판단 크기

있는 정보판단 크기이유
원래 크기가 있다(목록의 size 또는 --size)org_size 풀린 결과는 verify 가 이 값과 같은지 본다 — 곧 풀린 뒤 크기 그 자체다. zip_mode 압축 · enc_mode=26 머리(32B)에 흔들리지 않는다
원래 크기가 없다stored_size지금과 같다. 대부분(enc_mode 3 · zip_mode 0)은 풀린 크기와 같다

4-2. 어느 상한을 쓰나 — 원래 이름의 확장자로 고른다

풀기 전에는 내용이 암호문이라 내용 판별을 할 수 없다. 그래서 원래 이름(name)의 확장자로 종류를 고른다.

원래 이름의 확장자앞 상한맞추는 대상(풀린 뒤 상한)
zip 7z rar tar tgz gz bz2 tbz2 xz txzMAX_ARCHIVE_BYTES압축 펼치기의 누적 상한(500MB)
txt csv tsv json jsonl log md xml html htmMAX_FILE_BYTES_TEXT추출기의 텍스트 상한
그 밖(hwp docx xlsx pptx hwpx pdf doc …) · egg · alzMAX_FILE_BYTES추출기의 일반 상한
이름이 없다 · 확장자가 없다MAX_FILE_BYTES지금과 같다(원칙 3)
  • docx · xlsx · pptx · hwpx 는 속이 zip 이지만 문서 1개다 — 압축 목록에 넣지 않는다(풀린 뒤에도 펼치지 않고 일반 상한을 받는다).
  • egg · alz 는 펼치기를 지원하지 않아 풀린 뒤에도 압축 상한을 받지 않는다 — 일반 상한에 둔다.
  • 확장자가 내용과 다른 파일(예: 이름은 .txt 인데 실제는 바이너리)은 앞 상한이 조금 다를 수 있다. 최종 판정은 뒤 상한이 하므로 잘못 분류되는 일은 없고, 기껏해야 "풀었다가 뒤에서 버림"이 된다.
  • 확장자 목록은 두 판이 같은 표를 쓴다(Python decrypt.py · Rust decrypt.rs 의 상수). 한쪽만 고치면 같은 목록이 두 판에서 다르게 처리된다.

4-3. --no-size-limit — 지금처럼 앞 상한도 모두 끈다

--no-size-limit 은 세 상한(MAX_FILE_BYTES · MAX_FILE_BYTES_TEXT · MAX_ARCHIVE_BYTES)을 모두 0 으로 만든다(두 판 모두 이미 그렇다). 앞 상한도 고른 상한이 0 이하면 검사하지 않는다는 규칙 하나로 따라 꺼진다 — 따로 분기를 두지 않는다.

옵션압축(7z 등)텍스트(csv 등)일반(hwp 등)
(없음)500MB100MB100MB
--max-file-mb 300500MB100MB300MB
--max-file-mb-text 200500MB200MB100MB
--max-archive-mb 10001000MB100MB100MB
--no-size-limit검사 안 함검사 안 함검사 안 함
상한 값 0 (예: --max-archive-mb 0)그 종류만 검사 안 함("0 이하 = 상한 없음", 기존 규칙)

※ 일반 상한을 낮추면 텍스트 상한도 그 아래로 따라 내리는 기존 규칙(뒤집힌 설정 방지)은 그대로 둔다 — 앞 상한은 그 결과 값을 그대로 읽는다.

4-4. 판정 함수 — 두 판에 하나씩, 같은 계약

# Python — decrypt.py (Rust decrypt.rs 에 같은 이름·같은 판정)
def pre_size_limit(name, org_size, stored_size):
    # 1) 판단 크기: 원래 크기가 있으면 그것, 없으면 저장 크기
    basis, size = ("org_size", org_size) if org_size is not None else ("stored_size", stored_size)
    # 2) 원래 이름의 확장자로 상한을 고른다(모르면 일반 상한)
    ext = safe_ext(name)
    if ext in ARCHIVE_EXTS:  limit, which = config.MAX_ARCHIVE_BYTES,   "MAX_ARCHIVE_BYTES"
    elif ext in TEXT_EXTS:   limit, which = config.MAX_FILE_BYTES_TEXT, "MAX_FILE_BYTES_TEXT"
    else:                    limit, which = config.MAX_FILE_BYTES,      "MAX_FILE_BYTES"
    # 3) 0 이하는 '상한 없음'(--no-size-limit 포함)
    if not limit or limit <= 0 or size <= limit:
        return None
    return DecError("size_limit",
        f"복호화 전 크기가 상한을 넘어 풀지 않았습니다({basis} {size}바이트 > {limit}바이트, {which}) — "
        f"{_hint(which)} 로 조정할 수 있습니다")
  • 부르는 곳: Python cli._iter_dec_jobs(분류 · --text-only 공용), Rust 분류 루프, Rust run_text_only(지금 빠져 있는 자리 — 새로 넣는다).
  • 안내 문구(_hint)는 고른 상한에 맞춰 --max-archive-mb · --max-file-mb-text · --max-file-mb 를 알려 준다(지금은 늘 --max-file-mb).
  • 사유 이름은 그대로 size_limit — 결과 레코드(error.kind = "size_limit") · 요약("크기초과") · 종료코드(1)가 바뀌지 않는다.
  • 실패 로그 줄은 기존 모양 그대로(reason=size_limit … org_size= stored_size= …). 문장에 판단 크기와 고른 상한이 들어가 왜 걸렸는지 로그만 보고 안다.

판정이 느슨해지는 쪽은 "평문이었으면 받아 줬을 문서"뿐이다(압축 · 텍스트 상한을 따로 둔 경우). 판정이 엄해지는 쪽은 "어차피 뒤에서 버릴 문서"뿐이다(zip_mode). 최종 분류 결과가 평문과 달라지는 경우는 없어진다.

08

하지 않는 것 · 남는 한계

  • 앞 상한을 없애지 않는다 — 버려질 문서를 풀어 평문을 디스크 · 메모리에 두는 시간을 늘릴 이유가 없다(원칙 4).
  • 엠파워 쪽은 바꾸지 않는다 — removeenc.php · mpower_decrypt 에는 크기 제한이 없고, 둘 필요도 없다.
  • 시간 제한은 따로다 — 상한을 올리면 큰 문서가 --decrypt-timeout(기본 60초)에 걸릴 수 있다. 문서에 "상한을 올릴 때 시간 제한도 함께" 를 적는다.
  • 압축 안의 문서는 지금처럼 풀린 뒤 펼치기 단계의 상한(파일 수 · 누적 크기 · 각 문서의 추출 상한)이 맡는다 — 이 설계는 바깥 파일 하나의 앞 검사만 다룬다.
  • 확장자가 거짓인 파일은 앞 검사가 조금 어긋날 수 있지만, 최종 판정은 뒤 상한이 하므로 잘못된 등급은 나오지 않는다.
