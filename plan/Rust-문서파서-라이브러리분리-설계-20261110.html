지금 문서 → 본문 추출 코드는 MpowerClassify 저장소 안에 있다. 이것을 별도 프로젝트(별도 git 저장소) D:\Project\DocParse-rust 로 옮기고, 거기서 Windows 용 docparse.dll 과 Linux 용 libdocparse.so 를 만든다. MpowerClassify 의 Rust 판과 Python 판은 둘 다 이 라이브러리 파일을 실행 중에 불러서(load) 쓴다. 소스는 더 이상 MpowerClassify 에 두지 않는다. 추출 결과는 한 글자도 달라지면 안 된다.

한 줄 요약

추출 파일 11개(약 7,200줄, 압축 해제 포함)를 D:\Project\DocParse-rust 저장소로 옮긴다. 그 프로젝트는 C 함수 방식(C ABI)으로 함수 11개를 내보내는 공유 라이브러리를 Windows·Linux 두 벌로 만들어 배포 묶음(zip·tgz)으로 낸다. MpowerClassify 는 그 묶음을 third_party/docparse/ 에 버전을 고정해 받아 두고, Rust 판은 libloading 으로, Python 판은 ctypes 로 같은 파일 하나를 불러 쓴다. 옵션과 결과는 UTF-8 JSON 으로 주고받는다. 전역 상태 4가지(모드·상한·부분추출 메모·로그 파일)를 끊는 일은 앞 판과 같다. Rust 판은 분리 전후 본문 sha256 이 전부 같아야 끝나고, Python 판은 평가셋으로 판정 차이를 확인한 뒤 기본값을 바꾼다.

개정

앞 판은 "같은 저장소 안의 작업 공간(Rust/crates/docparse)에 두고 Rust 판은 소스째 링크, Python 판은 PyO3 모듈(2편), C 진입점은 보류(3편)" 였다. 이번 판은 ① 별도 프로젝트 폴더·저장소로 완전히 떼고 ② C 진입점 DLL/.so 를 유일한 공개 형태로 삼아 ③ Rust·Python 둘 다 그것을 불러 쓰는 방향으로 바꾼다. 그래서 3편(C 진입점)의 내용은 이 문서 §5 로 들어오고, 2편의 PyO3 모듈(docparse-py)은 만들지 않는다(§7). 2편에서 Python 쪽 엔진 표·폴백·정제 흐름을 어떻게 바꿀지는 그대로 유효하다.

01

왜 하나 · 왜 이 방식인가

  • 다른 프로젝트에서 쓰기 — 지금은 extract.rs 를 가져가도 crate::limits·crate::errlog·linfo! 같은 이 프로그램 전용 모듈이 따라와야 한다. 별도 저장소에 두면 "MpowerClassify 를 몰라도 빌드·시험되는" 상태가 강제된다.
  • 한 파서를 두 판이 같이 쓰기 — Python extract/ 3,084줄과 Rust 추출 쪽이 같은 일을 두 벌로 한다. 한 DLL 을 두 판이 불러 쓰면 고칠 곳이 하나가 된다.
  • 파서만 따로 고쳐 배포 — 파서 버그를 고치면 DLL 만 바꿔 넣으면 된다. Rust 실행파일·Python 패키지를 다시 빌드하지 않아도 된다(함수 모양이 같은 한, §5-4).

Rust 판도 "불러 쓰기" 로 하는 이유

방식좋은 점나쁜 점판단
Rust 판은 소스째 링크(docparse = { git = … }), Python 은 DLLRust 판은 실행파일 하나 그대로. JSON 변환 없음두 판이 다른 빌드를 쓰게 되어 "Rust 판에선 되는데 Python 판에선 다르다" 가 다시 생길 수 있음. 빌드서버가 DocParse-rust 저장소도 받아야 함쓰지 않음
둘 다 같은 DLL/.so 를 불러 씀바이트 단위로 같은 파서. 파서만 교체 배포 가능. MpowerClassify 빌드에 DocParse-rust 소스가 필요 없음배포본에 파일 하나가 늘어남(pdfium 처럼). 호출마다 JSON 변환(문서 파싱 대비 무시할 만함)채택

04

끊어야 할 전역 연결 4가지

DLL 로 내보내면 한 프로세스(예: Python 인터프리터)가 여러 스레드에서 서로 다른 옵션으로 부를 수 있어야 한다. 그래서 아래 4가지는 반드시 끊는다(앞 판과 같은 내용, 진행분에서 이미 대부분 끊었다).

#지금문제바꾼 뒤
Aextract::set_mode() 가 OnceLock 에 모드를 한 번 새김한 프로세스에서 두 모드를 못 씀옵션 JSON 의 engine 으로 매번 넘김
Blimits::set_overrides() 의 전역 상한. 환경변수(CSOCLASSIFY_MIN_TEXT_LEN 등)도 직접 읽음라이브러리가 이 프로그램의 환경변수 이름을 앎옵션 JSON 의 limits. 환경변수 읽기는 MpowerClassify 쪽으로
C'부분추출'·'스캔 페이지' 표식을 thread_local 메모에 적고 notes_take() 로 꺼냄DLL 경계 너머로는 꺼낼 길이 없음결과 JSON 의 partial·layout
Dlinfo!·errlog::err() 로 이 프로그램 로그 파일에 직접 씀errlog 가 axes·decrypt·errcodes 까지 끌고 옴본체는 표준 log 크레이트로 남기고, ffi 가 로그 콜백(§5-3)으로 부른 쪽에 넘김

limits.rs 나누기

  • 라이브러리로 — ParserDeadline, PDF 쪽수 상한, check_size_limit, truncate_text, human_bytes, 압축 상한(max_archive_bytes·max_archive_members → ArchiveOptions).
  • MpowerClassify 에 남김 — 상한값을 CLI 인자·환경변수에서 읽어 옵션을 채우는 부분.
  • 글자 수 상한(truncate) 은 분류 쪽 정책이다. MpowerClassify 가 결과 본문에 직접 적용한다. decrypt.rs 가 쓰는 함수(크기 표시 등)는 MpowerClassify 쪽에 작은 사본을 둔다 — DLL 의 내부 함수를 이것 때문에 내보내지 않는다.
주의 · D

로그 문장은 운영 로그를 읽는 도구·사람이 기대는 형식이다(추출 engine=… file=… chars=…, [PDF 부분추출] …). 문장을 그대로 유지하고 레벨도 맞춘다(info → info, errlog → warn + target "docparse::errlog"). MpowerClassify 의 콜백은 이 target 이 오면 errlog 파일에도 쓴다.

4-2. pdfium 찾는 위치 — DLL 이 되면 반드시 고쳐야 한다

지금 pdfium_lib_path() 는 std::env::current_exe() 옆을 찾는다. DLL 을 Python 이 불러 쓰면 current_exe 는 python.exe 라서 pdfium 을 못 찾고, PDF 가 오류 없이 전부 빈 본문으로 떨어진다(build.rs 주석에 적힌 바로 그 '조용한 고장').

  • 찾는 순서: ① 옵션 pdfium_lib → ② docparse DLL/.so 자신이 있는 폴더 → ③ 실행파일 옆 → ④ 시스템.
  • ② 는 Windows GetModuleHandleExW(FROM_ADDRESS) 와 GetModuleFileNameW, Linux dladdr 로 구한다.
  • pdfium 을 끝내 못 붙였을 때의 결과는 분리 전과 같게 둔다(그 PDF 는 추출 실패). 분리 작업에서 결과를 바꾸지 않기 위해서다 — 분명한 오류 문장으로 바꾸는 일은 DocParse-rust 에서 따로 한다.

void        docparse_set_logger(dp_log_fn fn, int max_level, void* user);  /* 11) 등록 안 하면 로그를 버림 */
구현 · 7개 → 11개

MpowerClassify 가 추출 말고도 라이브러리 안 판단을 쓰는 자리가 넷 있었다 — 크기 상한을 분할 압축 조각 판정보다 먼저 보는 자리(check_size), 분할 조각 안내(split_volume_hint), 6단계 정제(clean_text), 스캔 PDF 판정(scan_pdf_verdict). 이것들을 MpowerClassify 에 사본으로 두면 "한 파서" 가 깨지므로 함수로 더했다. 글자 수 자르기(truncate_text)만 분류 쪽 정책이라 MpowerClassify 에 둔다. 로그 콜백에는 분리 전 로그의 "모듈:줄" 자리를 채우려고 site 를 더했다.

5-3. 안전 규칙

규칙왜어떻게
패닉이 경계 밖으로 새지 않는다Rust 패닉이 C·Python 쪽으로 넘어가면 프로세스가 정의되지 않은 상태가 된다모든 함수를 catch_unwind 로 감싸 DP_ERR_PANIC + 메시지. Cargo 프로필은 panic = "unwind" 유지
NULL·잘못된 UTF-8 은 오류부른 쪽 실수로 죽지 않게모든 포인터 검사 → DP_ERR_ARG
전역 상태 없음여러 스레드에서 동시에 부를 수 있어야§4 로 성립. 로거 등록만 전역이고 원자적으로 바꾼다
할당한 쪽이 해제할당기가 다르면 죽는다docparse_free 로만 해제
로그 콜백은 아무 스레드에서나 온다추출을 부른 작업 스레드에서 그대로 부른다콜백은 짧게, 스레드 안전하게. 콜백 안에서 docparse_* 를 다시 부르지 않는다(헤더에 명시)
사이냅 자식 프로세스 정리DLL 안에서 띄운 snf_exe 가 시간 초과 때 남으면 안 된다지금 synap.rs 의 종료 처리 그대로. 부른 쪽 Ctrl+C 처리와는 무관하게 시간 상한으로 끝난다

5-4. 버전 관리

  • ABI 버전은 함수 모양이 바뀔 때만 올린다(함수를 지우거나 인자를 바꿀 때). 감싸개는 불러온 직후 docparse_abi_version() 을 자기 값과 비교해 다르면 시작을 멈춘다.
  • 새 기능은 새 JSON 키나 새 함수로 더한다. 그러면 ABI 를 올리지 않고 DLL 만 바꿔 넣을 수 있다.
  • 라이브러리 버전(docparse_version())은 MpowerClassify 가 라이브러리를 처음 불러올 때 일반 로그에 한 줄 남긴다(문서파서 docparse=0.1.0+abc1234 lib=…, Python 판은 실행 자체파서=rust docparse=… lib=…). 분류 레코드에는 넣지 않는다 — 레코드 모양을 바꾸면 두 판 교차 검증과 소비 쪽이 같이 바뀌어야 하므로, 필요해지면 따로 정한다.
  • 파서 동작이 바뀌는 수정(결과 본문이 달라지는 것)은 DocParse-rust 의 CHANGELOG.md 에 반드시 적는다. MpowerClassify 는 버전을 올릴 때 그것을 보고 평가셋을 다시 돌릴지 정한다.

  • 한 번만 불러 들고 다닌다 — src/docparse.rs 가 처음 쓸 때 불러 전역(OnceLock)에 둔다. 문서를 읽지 않는 명령(--set-grade·--propagate 등)은 라이브러리 없이도 돈다. 이 모듈이 예전 docparse 크레이트와 같은 이름의 함수·타입(detect::detect_format·extract_as·archive::expand_paths …)을 내주므로 main.rs 의 호출부는 거의 그대로다.
  • 실행 중에는 내리지 않는다 — 프로세스가 끝날 때까지 Library 를 쥐고 있는다(로그 콜백이 아무 때나 오므로).
  • Linux — 실행파일은 이미 RPATH=$ORIGIN 을 쓰지만, libloading 은 절대경로로 연다(exe 옆 경로를 직접 만든다). libdocparse.so 도 $ORIGIN 을 새겨 옆의 libpdfium 을 찾게 한다(§4-2 와 이중 안전).
  • 배포본 — Windows MpowerClassify-rs.exe · docparse.dll · pdfium.dll · …, Linux 도 같은 모양. 실행파일 하나 → 파일 하나가 더 붙는 것이 유일한 변화다.

        finally: self._dll.docparse_free(out)
    def expand(self, paths, tmp_root, **opts) -> dict: …

  • PyO3 를 쓰지 않는 이유 — PyO3 모듈(.pyd)은 별도 빌드물이라 Rust 판과 "같은 바이너리" 가 아니게 되고, maturin·abi3 빌드가 하나 더 생긴다. ctypes 는 표준 라이브러리라 의존이 없고, 이 프로젝트는 이미 V10 개인정보 엔진(mpiisl.dll)을 같은 방식으로 쓴다.
  • GIL — ctypes.CDLL 호출은 GIL 을 놓으므로 추출 중에 다른 파이썬 스레드가 돈다. 로그 콜백이 올 때는 ctypes 가 GIL 을 다시 잡아 준다.
  • Windows 경로 — 인자는 path.encode("utf-8") 로 넘긴다(c_char_p). c_wchar_p 를 쓰지 않는다.
  • 엔진 연결 — 2편 §4 대로 RustEngine(TextExtractor) 이 clean=False 로 원시 텍스트를 받고, 정제·사이냅 폴백·notes 기록은 Python 쪽이 지금처럼 한다. --extractor py 로 옛 파이썬 파서를 고를 수 있게 남긴 채 평가셋으로 판정 차이를 본 뒤 기본값을 바꾼다.
  • PyInstaller 배포 — docparse.dll/libdocparse.so 를 binaries 로 넣어 pdfium 과 같은 폴더에 둔다. 찾는 순서의 "실행파일 옆" 이 이것을 잡는다.

  5. 감싸개 정본 2개 — bindings/rust/docparse_dyn.rs, bindings/python/docparse.py. DocParse-rust 안에서 각각으로 시험 문서를 뽑아 본체 직접 호출 결과와 같은지 본다.

위험대응
