구조 설계 · Python Binding for docparse

Python 판도 Rust 문서파서를 쓰게 하기
— docparse.dll / libdocparse.so 를 ctypes 로

1편에서 별도 프로젝트(D:\Project\DocParse-rust)로 떼어 낸 문서파서 공유 라이브러리를 Python 판이 ctypes 로 불러, Python 판의 형식별 자체 파서 (src/csoclassify/extract/ 의 pdf·hwp·hwpx·doc·xls·ppt·docx·xlsx·pptx·html·텍스트)를 그것으로 바꾼다. 두 판이 같은 파서 하나를 쓰게 된다. 대신 Python 판의 추출 결과가 바뀌므로 평가셋으로 판정 차이를 확인한 뒤 기본값을 바꾼다.

대상 Python 판 선행 1편 (Rust 라이브러리 분리) 완료 연결 ctypes 감싸개 extract/_docparse.py (PyO3 아님) 바뀌는 동작 추출 결과 (평가셋 확인 후 전환) 상태 1단계 구현 · 2단계(평가셋 비교) 남음 (개정 2) 작성일 2026-11-10
한 줄 요약

Rust 판과 같은 파일(docparse.dll / libdocparse.so)을 ctypes 로 불러 쓴다. Python 의 HybridExtractor 는 그대로 두고, 그 안의 형식별 엔진 표와 압축 해제를 Rust 로 바꾼다. 사이냅 폴백, 원시 텍스트 정제, 오류 종류는 Python 쪽이 지금처럼 맡는다. --extractor py 로 예전 파이썬 파서를 고를 수 있게 남긴 채 평가셋 1,000건으로 판정 차이를 확인하고 기본값을 바꾼다. 차이가 정리되면 예전 파서와 olefile·xlrd·pypdfium2 의존을 지운다.

개정 2 · PyO3 → ctypes

처음 판은 PyO3·maturin 으로 파이썬 확장 모듈(Rust/crates/docparse-py)을 만드는 방식이었다. 1편 개정으로 문서파서가 별도 프로젝트의 C 진입점 공유 라이브러리가 되면서, Python 판도 그 파일을 ctypes 로 불러 쓰게 바꿨다. 그러면 Rust 판과 Python 판이 바이트 단위로 같은 바이너리를 쓰고, maturin·abi3 빌드가 따로 생기지 않는다(ctypes 는 표준 라이브러리 — V10 개인정보 엔진 mpiisl.dll 과 같은 방식). 파이썬에 보이는 모양(§4-1)은 PyO3 판과 같게 맞췄으므로 RustEngine·압축 연결·고르는 옵션 설계는 그대로다. 바뀐 곳은 §3·§4-1·§6·§8 이다.

01

왜 하나 — 지금 두 벌을 유지하는 비용

  • 같은 기능 두 벌 — Python extract/ 15개 파일 3,084줄과 Rust 추출 쪽 약 5,900줄이 같은 일을 한다. 고칠 때마다 양쪽을 맞춰야 한다 (예: PDF 표식 U+FFFE 지우기, 엑셀 날짜 서식, hwpx 문단 처리).
  • 맞춤 시험의 짐 — test_html_extract_parity.py 처럼 두 판 결과를 맞추는 시험이 따로 있다. 맞추지 못한 형식은 판정이 조용히 갈린다.
  • 속도 — PDF 는 둘 다 pdfium 이지만, OOXML(zip+XML)·xls·hwp 는 Rust 가 빠르다. 추출하는 동안 GIL 을 놓아 주면 파이썬 쪽 병렬 처리에도 유리하다.
  • 의존 줄이기 — olefile·xlrd·pypdfium2 를 뺄 수 있다(pdfium 라이브러리 파일 자체는 계속 필요, §6).

04

설계

4-1. 파이썬에 보이는 모양

docparse.load(path=None)                  # 처음 한 번. ABI 버전 확인 — 다르면 RuntimeError

r = docparse.extract(

r.text, r.engine, r.fmt

# stats = {"unexpanded": […], "unsupported": […], "partial": […]}
docparse.split_volume_hint(name, path) -> str | None
  • 엔진은 Builtin 만 노출한다. 사이냅은 Python synap_exe.py 가 이미 맡고 있고, 폴백 사슬도 hybrid.py 에 있다. 두 군데서 사이냅을 부르지 않게 한다.
  • GIL 놓기 — ctypes.CDLL 호출은 GIL 을 놓는다. 파이썬 스레드 여러 개가 동시에 추출할 수 있다.
  • 옵션·결과는 JSON — 감싸개가 키워드 인자를 옵션 JSON 으로 바꾸고 결과 JSON 을 위 모양(속성·튜플)으로 바꾼다. 라이브러리가 준 문자열은 감싸개가 docparse_free 로 돌려준다.
  • 예외 문장 — Rust 오류의 사유 문자열을 그대로 메시지로 쓴다. 레코드의 error·error_kind 는 지금 Python 이 만드는 방식(예외 종류로 갈라 보기)을 그대로 쓴다.

4-2. RustEngine — 엔진 표에 끼우기

class RustEngine(TextExtractor):
    def extract(self, input_path, save_dir=None):
        try:
            r = docparse.extract(input_path, fmt=self.fmt, clean=False, **self.limits)
        except docparse.SizeLimitError as e:
            raise SizeLimitError(str(e)) from e
        except docparse.ExtractError as e:
            raise ExtractError(str(e)) from e
        if r.partial: notes.set_partial(*r.partial)      # 지금 파서들이 하던 표식 남기기
        if r.layout:  notes.set_layout(*r.layout)
        if save_dir: save_extracted_text(…)            # 지금과 같은 보존 규칙
        return r.text

# build_extractor — 형식마다 같은 RustEngine 을 꽂는다(형식은 hybrid 가 감지해 넘김)
engines = {f: RustEngine(fmt=f, limits=…) for f in ("pdf","hwp","hwpx","doc","xls","ppt","docx","xlsx","pptx","html","text")}
  • 감지도 Rust 로 — 감지가 다르면 같은 파서를 써도 다른 엔진으로 간다. HybridExtractor(detector=docparse.detect_format) 로 넘긴다. 이미 detector 주입 자리가 있다.
  • 크기 상한 — hybrid 가 이미 check_size_limit 를 부른다. Rust 쪽 검사와 겹치지만 같은 상한값을 넘기므로 결과가 같다. 이중 검사는 무해하니 그대로 둔다.
  • 상주 서버(daemon/server.py)는 build_extractor 를 부르므로 따로 고칠 것이 없다.

4-3. 고르는 옵션 (전환 기간)

옵션뜻기본값
--extractor rust형식별 엔진 = RustEngine3단계에서 기본
--extractor py형식별 엔진 = 지금 파이썬 파서2단계까지 기본
CSOCLASSIFY_EXTRACTOR같은 선택을 환경변수로(상주 서버·배치용)—

같은 옵션이 압축 해제도 고른다(rust = docparse, py = 지금 archive.py). 본문 파서와 압축 해제를 따로 고르게 하면 조합만 늘어나므로 한 스위치로 묶는다. --synap-only·--synap-fallback 와는 독립이다. 그 옵션은 "사이냅을 언제 쓰나"이고, 이 옵션은 "자체 파서가 누구냐"다. docparse 모듈을 못 불러오면(배포 누락) 조용히 py 로 넘어가지 말고 시작할 때 오류로 멈춘다. 조용한 전환은 판정이 몰래 바뀌는 원인이 된다.

4-4. 압축 해제도 Rust 로

지금 cli.py 는 from .extract.archive import expand_paths 로 압축을 펼친다(1244·2707·5634행 부근). archive.py 의 expand_paths 는 이름과 반환 모양을 그대로 두고, 안에서 docparse.expand_paths 를 불러 Job 으로 바꿔 돌려준다. 그러면 cli.py 는 고칠 것이 없다.

  • rar 가 가장 크게 바뀐다 — 지금 Python 은 번들 unrar 실행파일(CentOS 7 에선 libstdc++ 문제까지 따로 챙기는)로 풀고, Rust 는 순수 Rust rars 로 푼다. 시험 문서로 지원 범위(RAR5·암호·하드링크)를 비교해서 차이를 기록한다.
  • 임시 폴더와 정리는 지금처럼 Python 이 만든다. Rust 는 받은 폴더에 풀기만 한다.
  • 압축을 푸는 동안에도 GIL 을 놓는다(ctypes 호출).
05

전환 단계

  1. 연결 — _docparse.py(ctypes)·RustEngine·--extractor 옵션. 개발 PC 는 저장소의 third_party/docparse 를 그대로 불러 쓴다(설치 단계 없음). 기본은 py. — 구현됨
  2. 차이 측정 — 평가셋 두 벌(1,000건)과 sample 을 --extractor py / rust 로 각각 돌린다. 비교는 세 층으로 한다.
    • 본문 — 정제 후 본문 sha256 이 다른 문서 목록, 형식별 개수
    • 판정 — 보안등급·업무분류가 바뀐 문서, 사람 정답지(…사람재검-01.xlsx) 기준 정밀도·재현율 변화
    • 시간 — 문서당 추출 시간 중앙값·최댓값
    차이 나는 문서는 원인을 한 건씩 본다. Rust 쪽이 틀리면 docparse 를 고친다(두 판 모두 좋아진다). Python 쪽이 틀렸던 것이면 그대로 받아들인다.
  3. 기본값 전환 — 판정 지표가 나빠지지 않으면 기본을 rust 로. 배포본·빌드 스크립트 반영(§6). 한 배포 주기 동안 --extractor py 를 남겨 둔다.
  4. 정리 — 문제가 없으면 파이썬 형식별 파서 8개 파일과 archive.py 의 해제 본체, olefile·xlrd·pypdfium2·py7zr·rarfile 의존, 번들 unrar 실행파일을 지운다. 두 판 맞춤 시험(test_html_extract_parity.py 등)은 "같은 모듈을 쓴다"로 바뀌므로 정리한다.

검증 기준

항목통과 기준
같은 모듈 확인--extractor rust 의 Python 판 정제 후 본문 = Rust 판 --text-only 본문 (평가셋·sample 전부 sha256 일치). 이게 이 작업의 목적이다
판정사람 정답지 기준 보안 정밀도·재현율, 업무분류 F1 이 py 대비 나빠지지 않음. 바뀐 문서는 목록으로 남겨 한 건씩 원인 기록
오류 종류크기 상한 문서 → SizeLimitError → 레코드 error_kind 가 지금과 같음. 깨진 파일 → ExtractError
폴백Rust 엔진 실패·빈·짧은 결과 → 사이냅 폴백이 지금처럼 동작 (test_hybrid_extract.py)
압축압축 시험 문서(zip·tar·gz·bz2·xz·7z·rar, 중첩·분할볼륨·상한 초과·손상)에서 펼친 목록·label·origin 과 결과 요약의 "못 펼친 압축" 이 py 와 같음. 다르면 원인 기록(특히 rar — 해제기가 unrar → rars 로 바뀐다)
부분추출 표식대형 PDF 에서 레코드의 부분추출 필드가 py 때와 같은 모양
병렬추출 스레드 4개 동시 실행 시 결과가 단일 스레드와 같음(전역 상태 없음 확인)
배포본Windows·Linux onedir 에서 모듈 불러오기 성공, PDF 추출 성공(pdfium 동봉 확인)
