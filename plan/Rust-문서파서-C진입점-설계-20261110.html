구조 설계 · C ABI for docparse

다른 언어에서 Rust 문서파서 쓰기
— docparse C 진입점(DLL / .so)

1편 개정 2 로 문서파서는 별도 프로젝트 D:\Project\DocParse-rust 가 되었고, C 언어 방식의 함수를 내보내는 공유 라이브러리 (Windows docparse.dll, Linux libdocparse.so)와 헤더(docparse.h)가 유일한 공개 형태가 되었다. MpowerClassify 의 Rust 판·Python 판도 이것을 불러 쓴다. 이 문서는 C·C++·C#·Java·Go 같은 다른 언어 프로젝트가 같은 라이브러리를 쓰는 법과, 그때 남은 일을 적는다.

대상 Rust 판 라이브러리 선행 1편 (라이브러리 분리) 완료 크레이트 DocParse-rust/crates/docparse-ffi 바뀌는 동작 없음 (새 산출물만 생긴다) 상태 C 진입점 구현됨(1편 §5) · 다른 언어 예제만 보류 (개정 2) 작성일 2026-11-10
한 줄 요약

docparse 위에 얇은 C 감싸개 크레이트 docparse-ffi 를 둔다. 함수는 11개다(처음 판 7개 + MpowerClassify 가 쓰는 판단 4개). 옵션과 결과는 UTF-8 JSON 문자열로 주고받아서, 구조체 모양을 언어마다 맞추는 수고와 버전이 오를 때 깨지는 위험을 없앤다. 라이브러리가 만든 문자열은 반드시 docparse_free 로 돌려받는다. Rust 패닉은 경계 밖으로 새지 않게 막아 오류 코드로 바꾼다. MpowerClassify 배포본에도 들어간다(두 판이 불러 쓴다). 남은 일은 C#·Java 등 다른 언어 예제뿐이고, 쓸 프로젝트가 생길 때 한다.

개정 2 · 1편으로 흡수

이 문서의 함수·JSON 모양·안전 규칙은 1편 §5 로 옮겨 구현했다(정본은 DocParse-rust 의 crates/docparse-ffi/include/docparse.h). 처음 판과 달라진 점: ① 위치가 MpowerClassify Rust/crates → DocParse-rust 저장소, ② 함수 7개 → 11개(check_size·split_volume_hint·clean_text·scan_pdf_verdict), ③ 로그 콜백에 site("모듈:줄") 인자 추가, ④ 헤더는 cbindgen 대신 손으로 쓴 것(옵션·결과 JSON 모양을 주석으로 담기 위해), ⑤ 정적 링크용(.lib/.a)은 만들지 않음, ⑥ 배포 묶음 이름은 docparse-<버전>-<플랫폼> 이고 Python·Rust 감싸개 정본을 함께 넣는다. 아래 §2·§3·§7·§10 을 그에 맞게 고쳤다.

01

왜 C 방식인가

언어마다 서로의 함수를 직접 부를 수는 없다. 거의 모든 언어가 공통으로 부를 수 있는 형식이 C 함수 호출 규약(C ABI)이다. Rust 함수를 extern "C" 로 내보내면 각 언어의 표준 연결 수단으로 부를 수 있다.

언어부르는 수단추가 도구
C / C++#include "docparse.h" + 링크없음
C# (.NET)[DllImport("docparse")] (P/Invoke)없음
JavaJNA 또는 Java 22+ FFM(Panama)JNA 라이브러리(선택)
GocgoC 컴파일러
Node.jskoffi · ffi-napinpm 패키지
그 밖C 라이브러리를 부를 수 있는 언어면 모두—

Rust 의 String·Result·Vec 는 C 쪽에서 모양을 모르므로 그대로 넘길 수 없다. 그래서 경계에서는 C 문자열(널 종료 UTF-8)과 정수 코드만 쓴다.

판단

감싸개를 별도 크레이트로 둔다. docparse 본체에 extern "C" 를 섞으면, Rust 사용자도 쓰지 않는 C 함수와 unsafe 코드를 같이 끌고 가야 한다. Python·Rust 감싸개도 이 C 진입점 위에 얹었다 — 모든 언어가 같은 바이너리를 부른다.

03

내보내는 함수

/* docparse.h (요약) — 정본: DocParse-rust/crates/docparse-ffi/include/docparse.h */
#define DOCPARSE_ABI_VERSION 1

typedef enum {
    DP_OK = 0,
    DP_ERR_ARG = 1,          /* 인자 오류: NULL·잘못된 UTF-8·JSON 파싱 실패 */
    DP_ERR_NOT_FOUND = 2,    /* 파일 없음 */
    DP_ERR_SIZE_LIMIT = 3,   /* 크기 상한 초과 — 깨진 파일과 구분 */
    DP_ERR_UNSUPPORTED = 4,  /* 지원하지 않는 형식(이미지 등) */
    DP_ERR_FAILED = 5,       /* 파싱 실패(깨진 파일·암호 등) */
    DP_ERR_PANIC = 99,       /* 라이브러리 내부 오류 — 버그. 메시지 첨부 */
} dp_status;

uint32_t    docparse_abi_version(void);                       /* 1) == DOCPARSE_ABI_VERSION 이어야 함 */
const char* docparse_version(void);                           /* 2) "0.1.0+abc1234" — 해제하지 않음 */
int  docparse_detect(const char* path, const char** out_fmt);    /* 3) "pdf"·…·"unknown" — 해제하지 않음 */
int  docparse_extract(const char* path, const char* opts_json, char** out_json);       /* 4) 본문 추출 */
int  docparse_check_size(const char* path, const char* fmt, const char* opts_json, char** out_json); /* 5) */
int  docparse_expand(const char* paths_json, const char* tmp_root,
                     const char* opts_json, char** out_json);                      /* 6) 압축 펼치기 */
int  docparse_split_volume_hint(const char* name, const char* path, char** out_json);  /* 7) */
int  docparse_clean_text(const char* text, char** out_text);            /* 8) 6단계 정제 */
int  docparse_scan_pdf_verdict(uint64_t pages, uint64_t scan_pages, uint64_t body_chars); /* 9) 1·0 */
void docparse_free(char* p);                                      /* 10) 이 라이브러리가 준 char* 만 */
typedef void (*dp_log_fn)(int level, const char* target, const char* site,
                          const char* msg, void* user);
void docparse_set_logger(dp_log_fn fn, int max_level, void* user);   /* 11) 등록 안 하면 로그를 버린다 */
  • 문자열은 모두 UTF-8이다. 경로도 마찬가지다. Windows 에서 한글 경로를 넘길 때 시스템 코드페이지(CP949)로 바꾸지 말고 UTF-8 로 넘긴다. C# 은 UTF8 마샬링을 지정한다(§6).
  • 반환 코드와 JSON 을 둘 다 준다. 코드만 보고 성공·실패를 가른다. 자세한 사유는 JSON 의 error 에 있다.
  • 해제는 반드시 docparse_free 로 한다. C 의 free() 로 지우면 안 된다. 메모리를 할당한 쪽(Rust)과 지우는 쪽의 할당기가 달라 프로그램이 죽을 수 있다.

4-1. 추출 옵션 (opts_json, NULL 이면 기본값)

{
  "clean": true,                    // 6단계 정제까지(기본 true). false = 원시 텍스트
  "engine": "builtin",              // "builtin" | "synap_fallback" | "synap_only"
  "synap_exe": null,               // engine 이 synap_* 일 때 snf_exe 경로
  "pdfium_lib": null,              // null = DLL 옆 → 시스템 순으로 찾기
  "limits": {
    "parser_timeout_secs": 60, "max_pdf_pages": null,
    "max_file_bytes": null, "max_file_bytes_text": null,

판단 · 왜 JSON

C 구조체로 넘기면 빠르지만, 필드 하나를 더할 때마다 모든 언어의 구조체 선언을 같이 고쳐야 한다. 순서나 크기가 어긋나면 오류 없이 엉뚱한 값을 읽는다. 문서 한 건 파싱에 비하면 JSON 만들고 읽는 비용은 무시할 만하다. 그리고 모든 언어에 JSON 파서가 있다.

08

버전 관리

  • ABI 버전(DOCPARSE_ABI_VERSION)은 함수 모양이 바뀔 때만 올린다. 함수를 지우거나 인자를 바꾸는 경우다. 쓰는 쪽은 시작할 때 docparse_abi_version() 과 헤더 값을 비교해, 다르면 멈춘다.
  • 새 기능은 새 함수나 JSON 키로 더한다. 이렇게 하면 ABI 버전을 올리지 않아도 된다.
  • 라이브러리 버전(docparse_version())은 크레이트 버전에 git 해시를 붙인 것이다. 결과를 저장하는 프로그램은 이 값을 같이 남겨, 어떤 파서로 뽑았는지 추적할 수 있게 한다.
