연동 설계 · Mpower v11 Decrypt Bridge

엠파워 v11 암호화 문서 복호화 연동
— 잠긴 파일을 풀어서 분류하고, 푼 파일은 바로 지운다

엠파워 v11 저장소의 문서는 암호화·압축된 채 디스크에 놓여 있다. 그대로 읽으면 분류기는 깨진 글자만 본다. 분류하기 직전에 엠파워의 removeenc.sh 로 한 건씩 풀고, 분류가 끝나면 푼 파일을 곧바로 지우는 길을 만든다.

대상 Rust 판(MpowerClassify-rs) 먼저 · Python 판 같은 계약 범위 --filelist 칸 추가 · 단일 파일 옵션 · 새 decrypt 모듈 기존 실행 변화 없음(복호화 정보를 안 주면 지금과 같다) 상태 설계 · 구현 완료 2026-10-12 (§14) 작성일 2026-10-12
한 줄 요약

다량 처리는 --filelist 의 각 줄에 mrk · enc_mode · zip_mode 를 적어 주면 그 줄의 파일만 풀어서 분류한다. 단일 처리는 --file 에 --decrypt --mrk … --enc-mode … --zip-mode … 를 붙일 때만 푼다 — 안 붙이면 지금처럼 그대로 읽는다(이미 풀어 둔 파일용). 푼 파일은 임시 폴더에 한 번에 한 건만 존재하고, 분류가 끝나는 즉시 지운다. 복호화가 실패하거나 풀린 결과가 수상하면 분류하지 않고 오류 레코드로 남긴다 — 깨진 내용을 "공개 문서"로 판정하는 것이 가장 나쁜 사고이기 때문이다.

01

왜 필요한가 — 금고 안의 문서

엠파워 v11 은 올라온 문서를 금고에 넣어 보관한다. 디스크에 있는 파일은 원본이 아니라 "암호화(+압축)된 덩어리"이고, 파일마다 다른 열쇠(MRK)로 잠겨 있다. 이름도 급여대장.xlsx 가 아니라 저장용 이름(RFILE_NAME)이다.

지금 MpowerClassify 에 이 파일을 그대로 주면 이렇게 된다.

# 저장소의 파일을 그대로 분류하면
./MpowerClassify-rs --file /MOCOMSYS/storage/vol01/2026/10/SF_4958ef1c --simple
# → 본문을 못 읽는다. 주민번호 3,000건이 든 급여대장인데도 "신호 없음"으로 끝난다

그래서 분류 직전에 금고에서 꺼내는 단계가 필요하다. 꺼내는 도구는 엠파워가 이미 갖고 있다.

/MOCOMSYS/MpowerScript/removeenc/removeenc.sh \
  -s "저장된 파일의 전체 경로" \
  -t "복호화 결과 파일의 전체 경로" \
  -k "평문 MRK 값" \
  -e "ENC_MODE 값" \
  -z "ZIP_MODE 값"

이 설계는 이 명령을 MpowerClassify 가 대신 불러 주는 것이다. 엠파워 쪽은 "파일 풀기 → 분류 → 지우기"를 직접 짜지 않고, 열쇠 정보만 넘기면 된다.

02

복호화 도구를 읽고 알게 된 것

설계의 근거는 C:\svn\Mpower_v11\PHP\Mpower_11.0\MpowerScript\removeenc 의 소스다. 읽어서 확인한 사실만 적는다.

확인한 사실어디서설계에 주는 영향
removeenc.sh 는 /MOCOMSYS/.bash_profile 을 읽고 php removeenc.php -- "$@" 를 실행한다 removeenc.sh 리눅스 전용이다. 파일 한 건마다 bash + php 프로세스가 하나씩 뜬다(§10 성능)
끝날 때 종료코드를 화면(stdout)에도 한 줄 찍는다 (echo $OUT) removeenc.sh 우리 stdout 은 결과 JSON 이 나가는 자리다. 자식의 출력을 그대로 흘리면 JSON 이 깨진다 → 반드시 가로챈다
실제 복호화는 PHP 확장 함수 mpower_decrypt(원본, 대상, encMode, zipMode, mrk) 한 번이다. 복호화와 압축 해제를 한 번에 한다 removeenc.php 압축 해제를 우리가 따로 할 필요가 없다. -z 만 정확히 넘기면 된다
-e · -z 는 0 도 올바른 값이다(빈 값만 오류) removeenc.php "0 이면 없는 것"으로 취급하면 안 된다. 칸이 없는 것과 값이 0 인 것을 구분한다
실패는 종료코드로 알린다 — 254 인자 오류 · 56 PHP 확장 없음 · 14 MRK 문제 · 4 원본 못 엶 · 5 대상 못 엶 · 9 복호화 실패 · 10 압축 해제 실패 등 removeenc.php 코드를 그대로 결과에 싣는다(§7). 엠파워 담당자가 번호만 보고 원인을 안다
KEK 로 감싼 MRK(v2: 로 시작)는 거부한다(코드 14). 감싼 키를 그대로 쓰면 mpower_decrypt 가 성공(0)을 돌려주면서 원본과 같은 크기의 무작위 바이트를 낸다(2026-09-29 실측, 소스 주석) removeenc.php "성공했다"는 말만 믿으면 안 된다. 풀린 결과가 진짜 문서인지 한 번 더 본다(§6)
엠파워 DB 에는 파일마다 SFILE_ID · MRK · ENC_MODE · ZIP_MODE · LFILE_NAME · LFILE_EXT · LFILE_SIZE · RFILE_PATH · RFILE_NAME · VOL_PATH 가 있다 SDR_Indexing_for_node_id.php 목록에 넣을 값이 전부 한 테이블(SHARE_FILE_INFO)에서 나온다. 원래 파일 이름도 함께 받을 수 있다(§3)
핵심

열쇠가 틀려도 도구가 "성공"이라고 답할 수 있다. 그 결과를 분류하면 아무 신호도 없으니 낮은 등급이 나온다 — 기밀 문서가 공개 문서로 기록되는 것이다. 이 설계에서 가장 공들인 부분이 이 한 가지를 막는 것이다.

03

방식 1 — 다량 파일 처리 (--filelist)

지금도 --filelist 는 {path, sfile_id} 를 한 줄씩 적은 목록을 받는다. 여기에 열쇠 칸 세 개와 보조 칸 두 개를 더한다. 옵션은 새로 생기지 않는다 — 목록에 열쇠가 적혀 있으면 풀고, 없으면 지금처럼 그대로 읽는다.

목록 한 줄의 모양

# filelist.jsonl — 한 줄에 문서 하나
{"path":"/MOCOMSYS/storage/vol01/2026/10/SF_4958ef1c","sfile_id":"SF_4958ef1c…","mrk":"9f2c…e1","enc_mode":1,"zip_mode":1,"name":"2026년 10월 급여대장.xlsx","size":48211}
{"path":"/MOCOMSYS/storage/vol01/2026/10/SF_77aa01b2","sfile_id":"SF_77aa01b2…","mrk":"41bd…07","enc_mode":1,"zip_mode":0,"name":"회의록_영업1팀.hwp"}
# 열쇠 칸이 없는 줄 = 이미 평문인 파일. 지금과 똑같이 그대로 읽는다
{"path":"/data/plain/사내규정.pdf","sfile_id":"SF_0c11d9aa…"}
칸필수뜻엠파워 DB 의 어느 값
path필수(기존)디스크에 저장된 파일의 전체 경로 → -sVOL_PATH + RFILE_PATH + RFILE_NAME
sfile_id필수(기존)문서 ID. 결과의 doc_id 로 그대로 나간다SFILE_ID
mrk복호화 시평문 열쇠 → -k. v2: 로 시작하면(감싼 키) 받지 않는다MRK (KEK 를 벗긴 값)
enc_mode복호화 시암호화 방식 → -e. 숫자·문자열 모두 받는다. 0 도 올바른 값ENC_MODE
zip_mode복호화 시저장소 압축 방식 → -z. 위와 같다ZIP_MODE
name권장원래 파일 이름. 저장 이름에는 확장자도 뜻도 없어서, 이것이 있어야 형식 판별과 파일명 신호가 제대로 돈다LFILE_NAME
size권장원래 파일 크기(바이트). 풀린 결과와 견줘 덜 풀린 파일을 잡는다LFILE_SIZE

csv 목록도 같다 — 첫 줄 헤더에 path,sfile_id,mrk,enc_mode,zip_mode,name,size 를 적으면 된다(칸 순서 무관).

왜 name 을 받아야 하나 — 예

저장된 파일 이름은 SF_4958ef1c 같은 값이다. 분류기는 파일 이름에서도 단서를 얻는데(예: 이름에 "급여대장"·"대외비"가 있으면 등급 신호), 저장 이름에는 그런 단서가 하나도 없다. 확장자가 없으니 xlsx 인지 hwp 인지도 이름으로는 알 수 없다.

name 을임시 파일 이름파일명 신호결과
줬다 — 2026년 10월 급여대장.xlsx000001.xlsx"급여대장" 을 본다본문 + 파일명 신호 모두 반영
안 줬다000001 (확장자 없음)볼 것이 없다본문만으로 판정. 형식은 파일 앞머리(시그니처)로 추정

줄마다 일어나는 일

  1. 목록 읽기 — 시작할 때 목록 전체를 읽어 형식을 검사한다(지금과 같다).
  2. 풀기 — 이 줄에 열쇠가 있으면 removeenc.sh 를 불러 임시 폴더에 푼다.
  3. 확인 — 풀린 파일이 진짜 문서인지 본다(§6).
  4. 분류 — 풀린 파일로 추출·규칙·전파를 돈다. 결과의 hash 는 풀린 내용의 지문이다.
  5. 지우기 — 성공이든 실패든 이 줄의 임시 파일을 지우고 다음 줄로 간다.
원칙

"한 번에 한 건만 풀려 있다." 1만 건을 먼저 다 풀어 놓고 분류하면 평문 1만 건이 디스크에 한꺼번에 놓이고(용량·유출 위험), 중간에 죽으면 그대로 남는다. 그래서 풀기–분류–지우기를 한 건 단위로 묶는다.

실행 예

./MpowerClassify-rs --filelist /tmp/job_20261012/filelist.jsonl \
    --simple --format jsonl --out /tmp/job_20261012/result.jsonl --json-errors --progress

# 화면(stderr)

목록 검사에 더해지는 규칙

상황처리왜
열쇠 칸 셋이 모두 있다복호화 후 분류—
열쇠 칸 셋이 모두 없다그대로 분류(지금과 같다)기존 목록이 그대로 돌아야 한다
enc_mode 와 zip_mode 가 둘 다 0removeenc 를 부르지 않고 그대로 분류. mrk 는 없어도 된다 암호화·압축이 안 된 파일이다. 엠파워도 이 경우 복사만 한다(§12 확인 결과 ①)
일부만 있다 (예: mrk 는 있는데 zip_mode 가 없다)그 줄만 오류 레코드(F8) "그대로 읽기"로 넘어가면 암호문을 분류한다. 목록을 만든 쪽이 빠뜨린 것이므로 조용히 넘기지 않는다
mrk 가 v2: 로 시작한다그 줄만 오류 레코드 감싼 키다. removeenc 를 부르기 전에 걸러 헛도는 프로세스를 줄인다
같은 path 에 sfile_id 가 둘(F3, 기존)전체 중단(지금과 같다)—
끄기

목록에 열쇠가 적혀 있어도 --no-decrypt 를 주면 풀지 않는다. 같은 목록으로 "이미 풀어 둔 사본 폴더"를 다시 분류해 볼 때 쓴다.

04

방식 2 — 단일 파일 처리 (--file)

파일 하나를 분류할 때는 풀지 말지를 부르는 쪽이 고른다. 기본은 "풀지 않는다"다 — 그래야 지금 쓰는 명령이 하나도 바뀌지 않는다.

옵션뜻
--decrypt이 파일을 풀어서 분류한다. 아래 셋이 함께 있어야 한다
--mrk <값>평문 MRK. 대신 환경변수 CSOCLASSIFY_MRK 로 줄 수도 있다(명령줄에 열쇠를 남기지 않는 길, §8)
--enc-mode <값>ENC_MODE
--zip-mode <값>ZIP_MODE
--name <이름>(권장) 원래 파일 이름. 목록의 name 칸과 같은 역할

예 ① 저장소의 암호화 파일을 바로 분류

./MpowerClassify-rs --file /MOCOMSYS/storage/vol01/2026/10/SF_4958ef1c \
    --decrypt --mrk "9f2c…e1" --enc-mode 1 --zip-mode 1 \
    --name "2026년 10월 급여대장.xlsx" \
    --simple --json-errors --daemon

안에서 일어나는 일: 임시 폴더에 000001.xlsx 로 풀기 → 확인 → 분류 → 임시 파일 삭제 → 결과 출력.

예 ② 이미 풀어 둔 파일을 분류 (추가 복호화 없음)

# 엠파워가 다른 용도(미리보기·색인)로 이미 풀어 둔 파일이 있다면 그대로 쓴다
./MpowerClassify-rs --file "/MOCOMSYS/tmp/dec/2026년 10월 급여대장.xlsx" --simple --json-errors

--decrypt 가 없으므로 removeenc 를 부르지 않는다. 지금과 완전히 같은 동작이고, 이 파일은 우리가 만든 것이 아니므로 지우지 않는다.

옵션 조합 규칙

준 것결과
--file 만그대로 분류(지금과 같다)
--file --decrypt + 열쇠 셋풀어서 분류
--decrypt 인데 열쇠 셋 중 빠진 것이 있다시작 전에 오류로 종료(코드 3, decrypt_args_invalid)
--mrk 는 줬는데 --decrypt 가 없다같은 오류. "풀릴 줄 알았는데 안 풀린" 상태를 만들지 않는다
--dir --decrypt같은 오류. 폴더에는 파일마다 다른 열쇠를 줄 방법이 없다 → --filelist 를 쓴다
--file X --filelist L (목록에 X 의 열쇠가 있다)목록은 지금처럼 "사전" 역할 — sfile_id 와 함께 열쇠도 목록에서 가져와 푼다. 명령줄에 준 값이 있으면 그것이 우선
05

removeenc.sh 를 부르는 방법

명령 조립 — 셸을 거치지 않는다

문자열을 이어 붙여 sh -c "…" 로 실행하지 않는다. 실행 파일과 인자를 낱개로 넘긴다 (Rust Command::new(cmd).arg("-s").arg(path)… · Python subprocess.run([cmd, "-s", path, …])).

이유는 파일 이름이다. 엠파워에는 보고서 (최종) "수정본".hwp 처럼 공백·따옴표·괄호가 든 이름이 흔하고, $(rm -rf …) 같은 글자가 든 이름도 올릴 수 있다. 낱개로 넘기면 이런 글자가 명령으로 해석될 길이 없다.

도구 위치

우선순위어디서값
1--decrypt-cmd <경로>이번 실행에만
2환경변수 CSOCLASSIFY_DECRYPT_CMD서버에 한 번 설정
3기본값/MOCOMSYS/MpowerScript/removeenc/removeenc.sh

복호화할 문서가 한 건이라도 있으면 시작할 때 이 파일이 있고 실행할 수 있는지 먼저 본다. 없으면 한 건도 읽지 않고 끝낸다 (decrypt_cmd_missing). 1만 건이 전부 같은 이유로 실패한 결과 파일을 만드는 것보다 낫다.

윈도우

removeenc.sh 는 리눅스 서버에만 있다. 윈도우의 MpowerClassify.exe 에서 --decrypt 를 주면 도구를 못 찾아 위 오류로 끝난다. 윈도우에서는 방식 2의 예 ②(이미 풀어 둔 파일)만 쓸 수 있다. --decrypt-cmd 를 둔 덕에 개발 PC 에서는 가짜 도구(파일을 복사만 하는 스크립트)로 흐름을 시험할 수 있다(§11).

출력과 종료코드

  • 자식의 stdout·stderr 는 가로채서 버퍼에 담는다. removeenc.sh 가 찍는 종료코드 숫자 한 줄과 사용법 문구가 우리 결과 JSON 에 섞이지 않게 한다.
  • 성공 여부는 프로세스 종료코드로만 판단한다(0 = 성공). 화면에 찍힌 숫자를 해석하지 않는다.
  • 실패하면 가로챈 문구의 첫 줄을 오류 사유에 붙인다(예: mrk is KEK-wrapped (v2:)…). removeenc 는 열쇠 값을 출력하지 않으므로 그대로 실어도 열쇠가 새지 않는다.
  • 시간 제한 — --decrypt-timeout <초>(기본 60, 기존 --parser-timeout 과 같은 값). 넘으면 자식을 죽이고 그 문서만 실패로 남긴다.
06

"성공"을 한 번 더 확인한다

§2 에서 본 대로, 열쇠가 잘못돼도 도구는 0(성공)을 돌려줄 수 있다. 그래서 풀린 파일을 분류기에 넘기기 전에 세 가지를 본다.

#검사잡아내는 것실패 시
1결과 파일이 있고 0바이트가 아니다도구가 아무것도 쓰지 않은 경우decrypt_failed / empty_output
2목록에 size 가 있으면 크기가 같다쓰다 만 파일 · 압축이 안 풀린 파일decrypt_failed / size_mismatch
3파일 앞머리(시그니처)가 확장자와 맞는다틀린 열쇠로 풀린 무작위 바이트decrypt_failed / signature_mismatch

시그니처 검사 — 예

확장자(name 에서)정상이라면 파일의 첫 바이트
docx · xlsx · pptx · hwpx · zip50 4B ("PK")
pdf25 50 44 46 ("%PDF")
hwp · doc · xls · pptD0 CF 11 E0 (OLE 복합 문서)
txt · csv 등 글자 파일시그니처가 없다 → 검사 3은 건너뛴다(아래 한계)

예: 급여대장.xlsx 를 풀었는데 첫 바이트가 A7 3E 91 0C 였다 → xlsx 는 반드시 "PK" 로 시작하므로 제대로 풀린 것이 아니다 → 분류하지 않고 decrypt_failed(signature_mismatch) 레코드를 낸다. 등급 칸은 비운다(null).

한계

크기 검사(2)는 틀린 열쇠를 못 잡는다 — 무작위 바이트도 원본과 크기가 같기 때문이다. 틀린 열쇠를 잡는 것은 시그니처 검사(3)이고, txt 처럼 시그니처가 없는 형식과 name 을 안 준 경우에는 이 검사가 약해진다. 이때는 추출 단계가 "글자로 읽히지 않는다"고 판단하면 추출 실패로 남는다. 그래서 name 칸을 "권장"으로 둔다.

07

실패했을 때 — 파일 문제와 환경 문제를 나눈다

기준은 하나다. "다음 파일도 똑같이 실패할 것인가?"

갈래예처리
파일 문제 — 이 파일만의 사정열쇠가 틀림(9) · 원본이 없음(4) · 압축 해제 실패(10) · 감싼 키(14) · 시그니처 불일치 · 시간 초과 그 문서만 오류 레코드로 남기고 다음으로 계속. 끝나면 종료코드 1(일부 실패)
환경 문제 — 서버의 사정도구 파일이 없음 · PHP 확장을 못 읽음(56) · 임시 폴더를 못 만듦 즉시 전체 중단. 남은 9,999건도 같은 이유로 실패할 것이므로 계속할 이유가 없다

새 오류 이름·번호 (기존 오류 계약 plan/CLI-오류출력-설계.html 에 추가)

kindcode종료코드언제
decrypt_args_invalid10143--decrypt 조합이 틀렸다(§4 표)
decrypt_cmd_missing10153복호화 도구가 없거나 실행 권한이 없다
decrypt_failed30051이 문서를 풀지 못했다(파일 문제). 레코드 단위

오류 레코드의 모양

{
  "file": "/MOCOMSYS/storage/vol01/2026/10/SF_77aa01b2",
  "name": "회의록_영업1팀.hwp",
  "doc_id": "SF_77aa01b2…", "doc_id_source": "sfile_id",
  "grade": null,
  "error": {
    "stage": "decrypt",
    "kind": "decrypt_failed",
    "detail": "signature_mismatch",          // 또는 removeenc_exit · timeout · empty_output · size_mismatch · key_wrapped · info_incomplete
    "rc": 0,                                  // removeenc 종료코드(부르지 않았으면 null)
    "reason": "hwp 파일인데 앞머리가 OLE 형식이 아닙니다 — 열쇠(mrk)와 모드가 맞는지 확인하세요"
  }
}

[구현 시 조정] 처음 설계는 reason 에 사유 이름을, message 에 문장을 뒀다. 기존 실패 레코드(extract_failed 등)는 reason 이 사람이 읽는 문장이고 --simple 이 그 값을 그대로 싣는다. 같은 틀을 지키려고 문장은 reason, 사유 이름은 detail 로 옮겼다.

기존 "목록에 있으나 파일이 없음"(file_missing) 레코드와 같은 틀이다. 엠파워는 doc_id 로 어느 문서가 실패했는지, rc 로 removeenc 의 어느 오류였는지 바로 안다.

금지

복호화에 실패한 문서를 "그러면 암호문 그대로라도 분류해 보자"로 넘기지 않는다. 등급이 나와 버리면 그것이 정상 결과처럼 DB 에 들어간다. 실패는 언제나 grade: null + error 다.

08

열쇠와 평문을 다루는 규칙

이 기능은 두 가지 민감한 것을 손에 쥔다 — 열쇠(MRK)와 풀린 원문. 둘 다 "쓰는 순간에만 있고, 흔적은 남기지 않는다"가 원칙이다.

풀린 원문 (임시 파일)

항목설계
위치--decrypt-tmp <폴더> → 환경변수 CSOCLASSIFY_DECRYPT_TMP → 시스템 임시 폴더. 그 아래에 cso_dec_<프로세스번호>/ 를 만든다(기존 압축 해제 폴더 cso_zip_<pid> 와 같은 관례)
권한폴더 0700 · 파일 0600. 같은 서버의 다른 계정이 읽지 못하게
파일 이름<일련번호>.<확장자> (예: 000012.hwp). 원래 이름을 쓰지 않는다 — 이름 자체가 민감할 수 있고, 특수문자로 경로가 깨질 수 있다
지우는 때① 문서 한 건이 끝날 때마다(성공·실패 무관) ② 실행이 끝날 때 폴더째 ③ Ctrl+C 를 받았을 때(기존 중단 처리에 cso_dec_ 추가) ④ 내부 오류(패닉)로 죽을 때
강제 종료(kill -9) 뒤지울 기회가 없다. 다음 실행이 시작할 때 주인 프로세스가 죽은 cso_dec_* 폴더를 찾아 지운다
결과·로그임시 경로는 결과 레코드·로그·--textsave 색인 어디에도 쓰지 않는다. 언제나 목록의 path 를 쓴다
운영 팁

임시 폴더를 메모리 디스크로 잡으면(--decrypt-tmp /dev/shm/cso) 풀린 원문이 물리 디스크에 한 번도 닿지 않는다. 한 번에 한 건만 풀려 있으므로 필요한 메모리는 "가장 큰 문서 하나"만큼이다(기본 상한 100MB).

열쇠 (MRK)

  • 로그에 쓰지 않는다. 지금 일반 로그(class_날짜.log)는 실행 명령을 통째로 기록한다 → --mrk 뒤의 값은 **** 로 가려서 기록한다. 오류 문구·디버그 출력도 같다.
  • 결과에 쓰지 않는다. 레코드에는 "복호화했다"는 사실(meta.decrypted: true)만 남긴다.
  • 목록 파일은 부른 쪽의 것이다. 우리는 읽기만 하고 지우지 않는다. 엠파워 쪽에서 권한 600 으로 만들고, 분류가 끝나면 지우는 것을 연동 규칙으로 둔다(§12).
  • 명령줄 노출 — --mrk 와 removeenc 의 -k 는 실행 중에 ps 로 같은 서버의 다른 계정에게 보일 수 있다. 우리 쪽은 CSOCLASSIFY_MRK 환경변수나 목록 방식으로 피할 수 있지만, removeenc.sh 의 -k 는 엠파워 도구의 인터페이스라 이 설계에서 바꿀 수 없다. 분류 서버를 전용 계정으로 운영하는 것으로 대응하고, 도구 개선은 §12 의 논의 항목으로 넘긴다.
09

기존 기능과 만나는 자리

기존 기능복호화와 함께일 때
압축파일 펼치기 (zip·7z·rar…) 순서는 복호화 → 펼치기 → 분류. 헷갈리기 쉬운 점: zip_mode 는 엠파워가 저장할 때 건 압축이라 removeenc 가 푼다. 사용자가 올린 자료.zip 은 그와 별개로, 풀린 뒤 지금처럼 우리가 내부 문서로 펼친다
문서 크기 상한 (--max-file-mb) 두 번 본다. ① 풀기 전 저장 파일 크기 — 터무니없이 크면 풀지도 않는다 ② 풀린 뒤 실제 크기 — 지금과 같은 판정
hash · doc_id hash 는 풀린 내용의 SHA-256 이다(같은 문서는 어디에 저장돼 있든 같은 값). doc_id 는 지금처럼 목록의 sfile_id
목록에만 있고 파일이 없음 (file_missing)지금과 같다. 풀기 전에 원본이 있는지 먼저 본다
임베딩 상주 서버 (--daemon)관계없다. 서버는 텍스트만 받는다 — 열쇠도 파일도 서버로 가지 않는다
본문 저장 (--textsave)그대로 동작한다. 단, 복호화한 문서의 본문이 평문으로 남는다는 점은 기존 경고와 같다
--text-only복호화를 똑같이 지원한다(추출만 확인해 볼 때 쓴다)
--dir · --files-from변화 없다. 목록을 "사전"으로 함께 주면 목록에 열쇠가 있는 파일만 푼다
구조 변경

지금 코드는 "대상 전부 모으기 → 압축 전부 펼치기 → 한 건씩 분류" 순서다(Rust/src/main.rs — collect_files → archive::expand_paths → 루프). 복호화를 "펼치기" 앞에 그대로 끼우면 모든 문서를 먼저 다 풀게 된다 — §3 의 원칙에 어긋난다. 그래서 복호화 대상은 루프 안에서 풀기 → (압축이면) 펼치기 → 분류 → 지우기로 처리하도록 이 부분을 손본다. 구현에서 가장 큰 변경이다.

10

성능 — 아직 재지 않은 것

문서 한 건마다 bash 하나 + php 하나가 새로 뜬다(.bash_profile 읽기, PHP 확장 로딩 포함). 이 비용은 아직 측정하지 않았다 — 구현 뒤 운영 서버에서 건당 시간을 재서 이 절에 채운다.

  • 분류 자체는 --filelist 로 한 프로세스에 몰면 모델을 한 번만 읽으므로 빠르다. 그러면 전체 시간에서 복호화 호출이 차지하는 몫이 커질 수 있다.
  • 건당 비용이 크게 나오면 다음 단계 후보는 "removeenc 를 여러 건 한 번에 받는 모드"다. 엠파워 도구를 고쳐야 하므로 이번 범위가 아니다(§12).
  • 이번 설계는 순차 처리다. 병렬 복호화는 "한 번에 한 건만 풀려 있다"는 원칙과 부딪히므로 측정 결과를 보고 따로 정한다.

시험 — 가짜 도구로 흐름을 먼저 검증한다

개발 PC 에는 removeenc.sh 도, 엠파워 PHP 확장도 없다. --decrypt-cmd 로 같은 인자를 받는 가짜 도구를 끼워 시험한다.

엠파워 v11 쪽과 확인할 것

소스만으로는 알 수 없어서 가정으로 둔 것들이다. 구현 전에 답을 받아야 한다.

#질문지금의 가정답에 따라 바뀌는 것
1ENC_MODE=0 · ZIP_MODE=0 은 "암호화·압축 없음"인가? 확인됨(2026-10-12, 소스) — 맞다. 아래 "확인 결과 ①" 둘 다 0 이면 removeenc 를 부르지 않고 그대로 읽는다(엠파워 자신도 그렇게 한다)
2목록의 path 는 VOL_PATH + RFILE_PATH + RFILE_NAME 이 맞는가? LFILE_NAME · LFILE_SIZE 도 줄 수 있는가? 확인됨(소스) — 맞다. 아래 "확인 결과 ②" size 를 "선택"에서 "권장"으로 올린다(엠파워도 풀린 크기를 LFILE_SIZE 와 견준다)
3DB 의 MRK 가 KEK 로 감싸여 있을 때(v2:), 벗기는 것은 엠파워 쪽이 맞는가? 확인됨(소스) — 맞다. 아래 "확인 결과 ③" 목록을 만드는 엠파워 코드가 decryptMRKWithKEK() 를 거쳐야 한다. 우리 쪽 v2: 거부 규칙은 그대로 둔다
4분류를 돌리는 계정이 저장소 파일을 읽고 removeenc.sh 를 실행할 수 있는가? 가능하다(엠파워 서비스 계정으로 실행) 아니면 권한 설정 절차를 실행가이드에 적어야 한다
5열쇠가 든 목록 파일을 권한 600 으로 만들고 분류 뒤 지우는 것을 엠파워 쪽 규칙으로 둘 수 있는가? 가능하다 —
6(다음 단계) removeenc 가 열쇠를 명령줄 대신 표준입력으로 받거나, 여러 건을 한 번에 받게 고칠 수 있는가? 이번 범위 아님 가능하면 ps 노출(§8)과 건당 비용(§10)이 함께 풀린다

확인 결과 ① — ENC_MODE=0 · ZIP_MODE=0 은 "그냥 복사"다

엠파워의 복호화 공통 함수는 둘 다 0 이면 복호화 함수를 부르지 않고 파일을 복사한다. 0 바이트 파일도 같다.

// www/classes/class.MCrypt.php:1021  (mpowerDecrypt)
if ($srcFileSize == 0 || ($encMode == 0 && $zipMode == 0)) {
    // 복사를 수행한다.
    $this->utilClass->copyFile($srcFilePath, $tgtFilePath);
} else {
    $MRK = $this->decryptMRKWithKEK(trim($MRK));
    $nativeCode = mpower_decrypt($srcFilePath, $tgtFilePath, $encMode, $zipMode, $MRK);
}
  • 암호화할 때도 같은 판정이다(class.MCrypt.php:884). 썸네일·압축 작업 등도 ENC_MODE != 0 || ZIP_MODE != 0 일 때만 복호화한다(class.MImage.php:564 · class.MShaCompressWorker.php:567).
  • 둘은 따로 논다 — ENC_MODE=0, ZIP_MODE≠0(압축만) 이나 ENC_MODE≠0, ZIP_MODE=0(암호화만)이면 removeenc 가 필요하다.
  • 0 이 아닌 ENC_MODE 는 알고리즘 번호다(예: 3 = CTR 계열, 8·9·18·19 = 256비트 키 — class.MCryptStreamReader.php:30-36). 우리는 값을 해석하지 않고 그대로 넘긴다.
  • 개발 DB 실측 기록: (0,0) 5건 · (3,0) 53건, ZIP_MODE≠0 은 없음 — 운영 사이트에는 있을 수 있다(specs/033-file-compress-zip/streaming-archive/handoff.md).
설계 변경

둘 다 0 인 줄은 removeenc 를 부르지 않고 저장 파일을 그대로 읽는다. 시간을 아끼는 것만이 아니다 — removeenc.php 는 -k 가 비어 있으면 인자 오류(254)로 끝나므로, 암호화되지 않은 파일에 MRK 가 없을 때 부르면 멀쩡한 파일이 실패로 기록된다. 따라서 이 경우 mrk 칸은 없어도 되고(F8 예외), 임시 파일도 만들지 않는다. 0 바이트 파일도 같은 길로 간다.

확인 결과 ② — 경로와 이름·크기

  • 저장 파일 경로는 엠파워 전체에서 VOL_PATH . '/' . RFILE_PATH . '/' . RFILE_NAME 로 만든다 (www/updown/reqWebDownloadFileWithParam.php:193 · class.MSDR.php:461 · class.MShaDownload.php:1126 외 다수). VOL_PATH 는 STORAGE_INFO 를 VOL_ID 로 이어서 얻는다.
  • LFILE_NAME · LFILE_EXT · LFILE_SIZE · MRK · ENC_MODE · ZIP_MODE 는 모두 SHARE_FILE_INFO 한 행에 있어 같은 조회로 나온다(removeenc/SDR_Indexing_for_node_id.php 의 SELECT).
  • 엠파워는 풀린 파일 크기가 LFILE_SIZE 와 다르면 실패로 본다(class.MCrypt.php:1089, ERR_UNMATCHED_FILE_SIZE). removeenc.php 에는 이 검사가 없으므로 우리가 size 로 대신 한다.
  • 예외 — 볼륨이 S3 인 경우에는 로컬 경로가 없다(class.MCrypt.php mpowerDecrypt2 설명: "S3 에 파일이 있는 경우 VOL_ID, RFILE_NAME"). removeenc.sh 는 로컬 파일만 받으므로 S3 볼륨 문서는 이 방식의 대상이 아니다. 대상 사이트가 S3 를 쓰면 따로 정해야 한다.

확인 결과 ③ — KEK 는 엠파워 쪽에서 벗긴다

  • MCrypt::decryptMRKWithKEK() 는 v2: 로 시작하면 KEK(AES-256-GCM)로 풀고, 아니면 그대로 돌려준다(옛 평문 MRK). 모든 MRK 에 무조건 불러도 안전하다(class.MCrypt.php:328).
  • KEK 는 서버의 키 파일(__MRK_KEK_FILE, 권한 0600, 웹 루트 밖)에서 읽는다. MpowerClassify 는 이 키에 접근할 수 없고, 접근해서도 안 된다.
  • removeenc.php 스스로 "감싼 키는 호출자가 벗겨서 넘겨야 한다"고 적고 거부한다(코드 14).
  • 같은 일을 하는 기존 코드가 본보기다 — 검색 색인(class.MSDR.php:478 sfileRemoveEnc)이 decryptMRKWithKEK 로 벗긴 뒤 removeenc.sh 를 부른다. 엠파워가 목록을 만들 때 이 순서를 그대로 따르면 된다.
  • v11 은 MRK KEK 가 필수 적용이다(www/admin/batch/gen_mrk_kek.php). 즉 새로 올라온 파일의 DB 값은 거의 다 v2: 이므로, DB 값을 그대로 목록에 넣으면 전부 실패한다.
범위

위 세 가지는 소스로 확인한 것이다. 접속 서버(MPOWER-SVR)의 실제 DB 에 어떤 ENC_MODE·ZIP_MODE 조합이 있는지, 볼륨이 로컬인지 S3 인지는 웹 화면으로는 볼 수 없어 확인하지 못했다(DB 조회가 필요하다).
