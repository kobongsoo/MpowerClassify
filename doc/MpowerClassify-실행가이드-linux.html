★ 먼저 해 보기 — 서버를 띄워 두고 파일을 하나씩 분류하기 2026-10-12 신규

다른 프로그램이 파일 하나마다 MpowerClassify-rs 를 한 번씩 부르는 연동이라면 이 방법으로 실행하세요. 이 프로그램은 부를 때마다 임베딩 모델(약 135MB)을 새로 읽는데, 모델을 물고 있는 서버를 한 번 띄워 두면 그 시간이 사라집니다. 분류 결과는 서버를 쓰든 안 쓰든 같습니다.

부르는 방법한 건에 걸리는 시간언제
그냥 부르기1초 안팎 (대부분이 모델 읽는 시간)가끔 한두 건
서버를 띄우고 --daemon0.2초 안팎파일마다 실행파일을 부르는 연동

빌드서버(CentOS 7) 실측: txt 2건을 한 번에 — 직접 읽기 1,554ms, 서버 사용 178ms. 문서가 크거나 PDF 처럼 추출이 무거우면 두 쪽 모두 그만큼 늘어납니다. 폴더째 한 번에 돌리는 배치(--dir·--files-from)는 서버가 필요 없습니다 — 한 프로세스가 모델을 한 번만 읽습니다(3장).

준비 — 터미널을 두 개 엽니다

두 터미널 모두 같은 계정으로 접속해 배포 폴더로 들어갑니다. 아래 예시는 /opt/MpowerClassify-rs-linux 에 풀었다고 가정합니다 (설치는 1장).

cd /opt/MpowerClassify-rs-linux
터미널하는 일
터미널 1서버를 띄워 둡니다. 서버가 도는 동안 이 터미널은 멈춰 있습니다(정상)
터미널 2상태를 보고, 문서를 분류하고, 서버를 내립니다

1단계 — 서버 띄우기 (터미널 1)

./MpowerClassify-rs --serve

1~2초 뒤 아래 한 줄이 나오면 준비가 끝난 것입니다. 이 터미널을 닫으면 서버도 같이 꺼집니다.

model=e5-small-ko pid=199150 port=35703 준비 완료

터미널을 닫아도 계속 떠 있게 하려면(실제 운용) 백그라운드로 띄웁니다.

nohup ./MpowerClassify-rs --serve > /dev/null 2>&1 &

같은 서버가 이미 떠 있으면 이미 실행 중인 데몬이 있습니다 라고 알리고 바로 끝납니다(둘이 뜨지 않습니다). --serve 는 평범한 포그라운드 프로세스라, 서버 재부팅 뒤 자동으로 띄우려면 systemd 유닛이나 cron 의 @reboot 에 이 명령을 그대로 등록하면 됩니다.

2단계 — 서버가 떴는지 확인 (터미널 2)

./MpowerClassify-rs --status
# 떠 있을 때
model=e5-small-ko pid=199150 port=35703 version=0.1.0 idle_timeout=무한(자동종료 없음) ready=true

# 없을 때
model=e5-small-ko: 실행 중인 데몬 없음
칸뜻
model서버가 물고 있는 임베딩 모델. 서버는 모델마다 하나씩입니다
pid · port서버 프로세스 번호와 포트. 포트는 뜰 때마다 빈 번호를 자동으로 잡고, 이 서버 안에서만 접속됩니다(127.0.0.1 — 방화벽을 열 필요가 없습니다)
idle_timeout이만큼 요청이 없으면 스스로 꺼집니다. 기본은 무한(꺼지지 않음)
readytrue 면 모델을 다 올려 바로 답할 수 있는 상태. 띄운 직후 잠깐 false 일 수 있습니다

3단계 — 문서 하나 분류하기 (터미널 2)

평소 쓰던 명령 끝에 --daemon 한 단어만 붙입니다.

./MpowerClassify-rs --file "/data/docs/의료비 지원 규정.docx" --with-vector --daemon --out /tmp/d.json
# 화면(stderr) 끝줄 — 총시간을 보세요
[summary] 총 1개 / 검출 0, C=0 S=0 O=0 미분류=1 추출실패=0, 총시간=178.0ms
시험할 때는 --with-vector 를 같이 주세요. 이 프로그램은 규칙만으로 등급이 정해진 문서는 임베딩을 하지 않습니다 — 그런 문서는 --daemon 을 줘도 서버에 묻지 않으니 "서버를 쓰는지" 확인이 안 됩니다. --with-vector 는 모든 문서를 임베딩하게 하므로 반드시 서버를 거칩니다. 실제 연동에서는 뺍니다 — 필요한 문서만 서버에 묻는 것이 더 빠릅니다.

4단계 — 얼마나 빨라졌는지 비교 (터미널 2)

같은 문서를 서버 없이(--no-daemon) 한 번, 서버로(--daemon) 한 번 돌려 끝줄의 총시간 을 견줍니다.

./MpowerClassify-rs --file "/data/docs/의료비 지원 규정.docx" --with-vector --no-daemon --out /tmp/n.json
./MpowerClassify-rs --file "/data/docs/의료비 지원 규정.docx" --with-vector --daemon    --out /tmp/d.json
[summary] 총 1개 / … 총시간=1310.4ms     # --no-daemon — 모델을 직접 읽음 (숫자는 예시)
[summary] 총 1개 / … 총시간=178.0ms      # --daemon    — 서버에서 벡터를 받음

5단계 — 정말 서버를 썼는지 확인

어디를 보나서버를 썼다못 썼다(직접 읽음)
분류 명령의 화면아무 말 없음상주 서버를 쓸 수 없어 모델을 직접 읽습니다 — (이유)
로그 파일요청마다 embed_text 줄이 하나씩 늘어남줄이 안 늘어남
grep embed_text log/class_$(date +%Y%m%d).log | tail -3
2026-10-12 10:09:04 [PID 199150] INFO … embed_text chars=1938 ms=78 ok=true

chars 는 문서 글자 수, ms 는 임베딩에 걸린 시간입니다. 문서 본문은 로그에 남기지 않습니다. 못 썼더라도 분류는 정상으로 끝납니다 — 그 호출만 예전 속도로 돌 뿐입니다.

6단계 — 결과가 같은지 확인 (선택)

서버를 쓴 결과와 안 쓴 결과를 연동용 간단 형식으로 뽑아 비교합니다.

./MpowerClassify-rs --file "/data/docs/의료비 지원 규정.docx" --no-daemon --simple --format jsonl --nosummary --out /tmp/n.jsonl
./MpowerClassify-rs --file "/data/docs/의료비 지원 규정.docx" --daemon    --simple --format jsonl --nosummary --out /tmp/d.jsonl
diff /tmp/n.jsonl /tmp/d.jsonl && echo "같음"

7단계 — 서버 내리기 (터미널 2)

./MpowerClassify-rs --stop
데몬 정지 요청 전송        # 서버가 없었으면 "정지할 데몬 없음"

터미널 1의 서버가 끝나고 프롬프트가 돌아옵니다. 터미널 1에서 Ctrl+C 를 눌러도 됩니다. kill -9 로 죽여도 됩니다 — 남은 기록 파일은 다음 호출이 "죽은 기록"으로 걸러 냅니다.

실제 연동에서는 이렇게 씁니다

# ① 연동 프로그램(서비스)이 시작할 때 한 번 — 서버를 미리 띄워 둔다
nohup ./MpowerClassify-rs --serve > /dev/null 2>&1 &

# ② 파일마다 — 기존 호출에 --daemon 만 더한다
./MpowerClassify-rs --file "$f" --daemon --json-errors --simple --nosummary --format jsonl --out "$out"

# ③ 연동 프로그램이 끝날 때
./MpowerClassify-rs --stop
⚠ 서버와 호출은 같은 리눅스 계정으로 실행하세요
서버가 "내가 어느 포트에 있다"를 적어 두는 기록 파일이 계정의 홈 폴더(~/.csoclassify/daemon-rs-e5-small-ko.json, 권한 600)에 있습니다. 서버는 root 로 띄우고 호출은 서비스 계정이 하는 식으로 계정이 다르면 서로를 못 찾습니다 (호출하는 계정으로 서버가 하나 더 뜹니다). 계정을 맞출 수 없으면 양쪽 모두에 같은 폴더를 지정하세요 — 그 폴더는 두 계정이 모두 읽고 쓸 수 있어야 합니다. 
export CSOCLASSIFY_STATE_DIR=/var/lib/mpowerclassify

0 이 문서가 다루는 것

인자·결과 형식·오류 코드는 Windows 와 완전히 같습니다. 이 문서는 리눅스에서만 다른 것 — 설치, 실행권한, 셸 문법, 경로, 배치 운용, 문제 해결 — 을 모았습니다. 인자 하나하나의 뜻과 결과 레코드의 모든 칸은 실행 가이드(본편)를 보세요.

예시는 전부 Rust 판(MpowerClassify-rs)입니다. 리눅스 서버에서는 Rust 판을 권합니다 — tgz 하나에 전부 들어 있어 옮기기 쉽고, 파이썬 런타임이 없어 기동이 빠르며, 배치(cron·스케줄러)에서 한 번 부르고 끝나는 쓰임에 맞습니다. Python 판(MpowerClassify)도 리눅스 배포본이 있습니다. 인자가 같아 실행파일 이름만 바꾸면 되고, 설치 차이는 본편 2장과 배포 폴더의 README.txt 에 있습니다.

1 설치 — 3분

# 1) tgz 를 서버로 올린다(Windows 에서 풀지 말고 파일째로)
scp MpowerClassify-rs-linux.tgz user@server:/opt/

# 2) 리눅스에서 푼다 — 실행권한이 보존된다
cd /opt
tar xzf MpowerClassify-rs-linux.tgz        # → MpowerClassify-rs-linux/ 폴더가 생긴다
cd MpowerClassify-rs-linux

# 3) 확인 — 버전이 찍히고, 규칙셋 두 개가 '정상'으로 나오면 끝
./MpowerClassify-rs --version
./MpowerClassify-rs --check-rules
⚠ tgz 는 반드시 리눅스에서 푸세요
Windows 에서 압축을 풀었다가 폴더째 옮기면 실행권한이 사라집니다(Windows 파일시스템은 실행 비트를 보존하지 못합니다). 그렇게 옮겼다면 chmod +x MpowerClassify-rs *.so* 로 되살리세요. tgz 를 리눅스에서 풀었다면 chmod 는 필요 없습니다.

어디에 풀어도 됩니다 — 실행파일이 자기 옆의 파일들을 찾으므로 /opt·홈·NFS 어디든 폴더째 두면 됩니다. PATH 에 넣거나 심볼릭 링크로 불러도 실행파일의 실제 위치 옆을 봅니다. 다만 폴더 안의 파일을 따로 떼어 옮기지 마세요.

2 패키지 구성

MpowerClassify-rs-linux/ ├─ MpowerClassify-rs 실행 파일(8.5MB). RPATH=$ORIGIN 이 박혀 있어 옆의 .so 를 스스로 찾는다 ├─ libonnxruntime.so ONNX Runtime 1.26 (임베딩 추론) ├─ libonnxruntime_providers_shared.so ORT 부속 ├─ libpdfium.so PDF 텍스트 추출 ├─ libstdc++.so.6 · libgcc_s.so.1 신형 C++ 런타임 — CentOS 7 필수(시스템 것이 낡아 함께 둔다) ├─ models/ │ └─ e5-small-ko/ 임베딩 모델(model.onnx · tokenizer.json 등, 129MB) ├─ cso_rule.yaml 보안등급(C/S/O) 규칙셋 — 재빌드 없이 교체 가능 ├─ doc_rule.yaml 업무분류 규칙셋(자동 생성 — 분류체계 내장). 없으면 업무분류 축이 꺼짐 ├─ doc_rule.local.yaml 회사 조정(있을 때만) ├─ doc_classification_export.json 엠파워 분류체계 JSON — 규칙의 재료 ├─ doc_rule_template.yaml 규칙 설정 본보기 — 규칙의 재료 ├─ synonyms/ 유의어 사전 — 규칙의 재료 ├─ class_seed.jsonl 전파 기준 문서(seed) — 있으면 못 정한 문서를 구제 ├─ README.txt └─ log/ 실행하면 생긴다 — class_YYYYMMDD.log · class_err_YYYYMMDD.log

3 빠른 시작

# 문서 1개
./MpowerClassify-rs --file "/data/docs/계약서.hwp"

# 폴더 전체(하위 폴더까지) → 결과를 파일로. 가장 많이 쓰는 형태
./MpowerClassify-rs --dir /data/collected --format jsonl --out /data/out/result.jsonl

# 다른 프로그램·스크립트에서 부를 때 — 이 세 개를 같이 쓴다
./MpowerClassify-rs --dir /data/collected --json-errors --simple --nosummary \
    --format jsonl --out /data/out/result.jsonl
왜 이 셋인가없으면
--json-errors실패를 문장으로 받게 됩니다 — 문구가 한 글자만 바뀌어도 스크립트가 깨집니다
--simple레코드가 수십 칸으로 커집니다. 연동에 필요한 건 file·hash·doc_id·grade·doctype 다섯 칸입니다
--nosummary집계 레코드가 섞입니다 — 건수는 상태 줄의 total 로 옵니다

⚠ 파일마다 프로세스를 띄우지 마세요
Rust 판은 기본으로 부를 때마다 임베딩 모델을 새로 읽습니다. 호출 구조를 바꿀 수 없으면(파일 1건 = 실행 1회) ./MpowerClassify-rs --serve 로 임베딩 상주 서버를 띄워 두고 호출마다 --daemon 을 붙이세요 — 모델을 한 번만 읽습니다(결과는 같습니다). for f in *; do ./MpowerClassify-rs --file "$f"; done 처럼 돌리면 문서 수만큼 그 비용을 뭅니다 (실측 6건: 한 건씩 6.5초 → 한 번에 1.1초). 문서들을 --dir 로 한 번에, 여러 폴더에 흩어져 있으면 --files-from 으로 목록을 넘기세요(6장).

5 배치 스크립트 예시

매일 밤 수집 폴더를 분류해 날짜별 결과를 남기고, 상태 줄의 code 로 갈라 처리하는 스크립트입니다. 그대로 가져다 경로만 고쳐 쓰면 됩니다.

#!/usr/bin/env bash
# classify_nightly.sh — 수집 폴더를 분류하고 결과를 날짜별로 남긴다
set -u

APP=/opt/MpowerClassify-rs-linux/MpowerClassify-rs
SRC=/data/collected
OUTDIR=/data/classify/out
OUT="$OUTDIR/result_$(date +%Y%m%d).jsonl"

export CSOCLASSIFY_LOGDIR=/var/log/mpowerclassify     # 로그를 한곳에(없으면 실행파일 옆 log/)
mkdir -p "$OUTDIR" "$CSOCLASSIFY_LOGDIR"

# 상태 줄은 stdout 의 '마지막 줄' — 성공이든 실패든 언제나 있다
STATUS=$("$APP" --dir "$SRC" --json-errors --simple --nosummary \
               --format jsonl --out "$OUT" | tail -n 1)

# jq 가 있으면 jq 로, 없으면 grep 으로 code 를 꺼낸다
if command -v jq >/dev/null; then
    CODE=$(printf '%s' "$STATUS" | jq -r '.error.code')
    FAILED=$(printf '%s' "$STATUS" | jq -r '.error.failed // 0')
else
    CODE=$(printf '%s' "$STATUS" | grep -o '"code":[0-9]*' | head -n 1 | cut -d: -f2)
    FAILED=$(printf '%s' "$STATUS" | grep -o '"failed":[0-9]*' | cut -d: -f2)
fi

case "${CODE:-}" in
    0)    echo "완료: $OUT" ;;
    3001|3004)
          echo "완료(못 읽은 문서 ${FAILED:-?}건): $OUT"      # 결과는 정상 — 그 문서만 사람·OCR 로
          grep '"error"' "$OUT" | grep -v '^{"error"' > "$OUTDIR/failed_$(date +%Y%m%d).jsonl" ;;
    3002|3003)
          echo "경고: 임베딩 모델을 못 올렸습니다 — 규칙 등급만 나갔습니다: $OUT" >&2 ;;
    1???) echo "명령이 틀렸습니다: $STATUS" >&2; exit 3 ;;
    2???) echo "정책 파일을 확인하세요: $STATUS" >&2; exit 4 ;;
    4???) echo "결과를 쓰지 못했습니다: $STATUS" >&2; exit 1 ;;
    "")   echo "상태 줄이 없습니다 — 프로세스가 죽었을 수 있습니다(로그 확인)" >&2; exit 1 ;;
    *)    echo "실패: $STATUS" >&2; exit 1 ;;
esac
읽는 법
· 종료코드를 직접 보려면 파이프를 쓰지 말고 "$APP" … > status.txt; RC=$? 로 받거나, bash 라면 ${PIPESTATUS[0]} 를 쓰세요. code 와 종료코드는 늘 짝이 맞으므로 둘 중 하나로만 갈라도 됩니다.
· 모르는 code 는 천의 자리로 뭉뚱그리면 됩니다 — 1000번대 부른 쪽 잘못 · 2000번대 정책 파일 · 3000번대 처리 · 4000번대 출력. 나중에 새 오류가 늘어도 옳은 갈래에 들어갑니다.
· 상태 줄이 아예 없으면 프로세스가 비정상 종료한 것입니다 — "줄이 없음"을 성공으로 읽지 마세요.

cron 에 걸기

# crontab -e — 매일 02:30
30 2 * * * /opt/scripts/classify_nightly.sh >> /var/log/mpowerclassify/cron.log 2>&1

--json-errors 를 주면 오류 문장이 stderr 로 나가지 않아 2>&1 로 합쳐 받아도 깔끔합니다. 진행률이 필요하면 --progress 를 더하세요 — [progress] 처리수/총수 경로 가 stderr 로 나갑니다(전파 단계는 [progress][전파·보안등급]).

6 자주 쓰는 명령

# 1) 규칙만으로 가장 빠르게 — 임베딩 모델을 읽지 않는다
./MpowerClassify-rs --dir /data/collected --rule-only --format jsonl --out result.jsonl

# 2) 여러 폴더에 흩어진 파일을 한 번에 — 목록을 표준입력으로 넘긴다
find /data/인사 /data/계약 -type f \( -name '*.hwp' -o -name '*.pdf' -o -name '*.docx' \) \
  | ./MpowerClassify-rs --files-from - --json-errors --simple --nosummary \
      --format jsonl --out result.jsonl

# 3) 최근 하루 사이 바뀐 문서만
find /data/collected -type f -mtime -1 > /tmp/changed.txt
./MpowerClassify-rs --files-from /tmp/changed.txt --format jsonl --out today.jsonl

# 4) 보안 서버처럼 "여기 있는 것은 기본이 기밀"인 곳 — 신호가 없는 문서에 C 를 준다
./MpowerClassify-rs --dir /secure/share --failsafe C --format jsonl --out result.jsonl

# 5) 보안등급만 / 업무분류만
./MpowerClassify-rs --dir /data/collected --axis security --out sec.jsonl
./MpowerClassify-rs --dir /data/collected --axis doctype --rule-only --out doctype.jsonl

# 6) MpowerV11 문서 번호(sfile_id)를 결과의 doc_id 에 싣는다 — 목록이 대상도 정한다
./MpowerClassify-rs --filelist filelist.jsonl --json-errors --simple --nosummary \
    --format jsonl --out result.jsonl --report-missing-id missing.jsonl

# 7) 기준 문서(seed) 등록 — 화면 없이. 검토자 이름은 필수
./MpowerClassify-rs --seed-add "/data/확정/표준계약서.docx" \
    --seed-grade C --seed-doctype DC_006_001 \
    --seed-reviewer "고봉수" --seeds ./class_seed.jsonl

# 8) 1차 결과에 전파만 다시 — 모델도 원본 문서도 필요 없다(벡터가 든 결과여야 한다)
./MpowerClassify-rs --dir /data/collected --embed-needed --out r1.jsonl
./MpowerClassify-rs --propagate r1.jsonl --seeds ./class_seed.jsonl --out r2.jsonl

# 9) 규칙을 고친 뒤 — 문서를 읽기 전에 검사한다(정상 0 · 틀리면 4)
./MpowerClassify-rs --check-rules; echo "exit=$?"

# 10) 업무분류 규칙을 다시 만든다(분류체계 JSON·사전·회사 조정이 바뀌었을 때)
./MpowerClassify-rs --build-doc-rule \
    --export-input doc_classification_export.json --doc-rules doc_rule.yaml

# 11) 초대형 문서가 섞인 폴더 — 상한을 낮춰 빨리 훑는다
./MpowerClassify-rs --dir /data/collected --max-file-mb 30 --max-pdf-pages 500 \
    --parser-timeout 20 --format jsonl --out result.jsonl

# 12) 추출 본문만 뽑아 보기(파서 확인용) — 규칙·개인정보 검사를 하지 않는다
./MpowerClassify-rs --text-only --file "/data/docs/계약서.hwp" | head -n 20
압축파일도 그대로 넣으면 됩니다 — zip · tar(+gz/bz2/xz) · gz · bz2 · xz · 7z · rar 을 내부 문서로 펼쳐 각각 분류하고, 압축 자체에는 내부 최고 위험등급을 매긴 집계 레코드("archive":true)를 덧붙입니다. 외부 프로그램(unzip·7z 등)은 필요 없습니다. 풀어 둔 임시폴더는 끝나면 지웁니다.

10 주의사항

  • Windows 에서 만든 결과와 섞어 쓸 때 — 같은 모델 파일이라도 ONNX Runtime 이 OS·CPU 마다 미세하게 다른 수를 냅니다 (실측: 같은 OS 안에서는 두 판이 코사인 1.000000, Linux↔Windows 는 최저 0.996). 임계값 바로 옆의 문서는 OS 에 따라 전파 판정이 갈릴 수 있으니, 1차 분류와 전파, seed 등록은 같은 OS 에서 하세요.
  • 임베딩 모델을 바꾸면 seed 도 다시 만드세요. --model 은 e5-small-ko(기본)·e5-small·ko-sroberta 를 받고, 배포본에는 e5-small-ko 만 들어 있습니다. 다른 모델은 models/<별칭>/ 에 model.onnx·tokenizer.json 을 넣습니다. 차원이 다르면 1013 으로 멈추지만, 차원이 같은 두 모델을 섞으면 오류 없이 유사도만 틀어집니다.
  • 같은 seed 파일을 여러 프로세스가 동시에 고치지 마세요. --seed-add --seeds 는 파일을 잠그고 통째로 다시 씁니다. 웹·여러 작업자가 부른다면 --seeds 없이 불러 등록될 줄만 stdout 으로 받고, 한 곳에서 모아 쓰는 편이 안전합니다.
  • --textsave · --with-pii 는 개인정보를 평문으로 남깁니다. 남길 폴더의 권한(chmod 700)과 보관 기간을 먼저 정하세요. 기본 실행은 검출된 원문 값을 결과에도 로그에도 남기지 않습니다.
  • 스캔 PDF(그림만 든 PDF)는 처리제외입니다 — OCR 을 하지 않습니다. 레코드에 "excluded":"scan_pdf" 가 붙고 실패로 세지 않습니다.
  • NFS·CIFS 위의 문서도 그대로 읽습니다. 다만 마운트가 끊긴 폴더는 "대상 없음"(1001)으로 보이니, 배치 앞에서 마운트를 확인하세요.
  • 도움말은 ./MpowerClassify-rs --help — ①~⑪ 로 나뉘어 있고, 이 판에서 되는 것과 안 되는 것이 ⑩·⑪ 에 적혀 있습니다.
