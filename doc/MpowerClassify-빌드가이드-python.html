1 무엇을 만드는가

파이썬으로 짠 MpowerClassify 를 파이썬이 설치돼 있지 않은 PC/서버에서도 돌아가는 폴더로 만듭니다. PyInstaller 가 파이썬 인터프리터와 필요한 라이브러리를 전부 _internal\ 폴더에 담아줍니다.

onedir 방식을 쓰는 이유
PyInstaller 에는 파일 하나로 만드는 onefile 과 폴더로 만드는 onedir 이 있습니다. 이 프로젝트는 onedir 만 씁니다 — onefile 은 실행할 때마다 임시폴더에 압축을 풀어 매번 느리고, 상주 데몬이 임시 snf_exe 경로를 잃어버리는 문제가 있었습니다. (build/csoclassify-onefile.spec 은 참고용으로만 남아 있습니다.)

완성된 배포본 구조

리눅스는 왜 폴더가 아니라 .tgz 인가?
_internal/ 안의 .so 파일들은 심볼릭 링크(예: libstdc++.so.6 → libstdc++.so.6.0.34) 로 얽혀 있습니다. Windows 파일시스템은 심볼릭 링크를 보존하지 못해, Windows 를 거쳐 폴더째 복사하면 링크가 깨집니다. 그래서 리눅스에서 tar 로 묶은 상태로 옮기고 리눅스에서 풉니다. (Rust 판은 심볼릭 링크가 없어 폴더 그대로 배포합니다.)

“외장 리소스” 개념

규칙셋·모델·사이냅 추출기는 exe 안에 넣지 않고 실행파일 옆에 둡니다. 이유는 세 가지입니다.

  • 규칙 교체가 자유롭다 — cso_rule.yaml 만 바꾸면 재빌드 없이 정책 변경
  • 기동이 빠르다 — 모델(129MB)을 매번 압축 해제하지 않음
  • 라이선스 분리 — 사이냅 문서필터는 상용 컴포넌트라 별도 배포

1-1. 문서파서 라이브러리(docparse)는 어떻게 붙나 2026-11-11

문서 → 본문 추출을 하는 파서가 두 벌 있습니다. 실행할 때 --extractor 로 고릅니다.

값파서비고
rust (기본, 2026-11-18~)Rust 판과 같은 문서파서 라이브러리 docparse.dll / libdocparse.so별도 프로젝트 D:\Project\DocParse-rust 산출물. 형식 감지와 압축 펼치기도 같은 라이브러리가 한다. 0.2.0 부터 본문 밖 글(PDF 글상자·서식 칸, docx 메모, SmartArt)도 읽는다
py지금까지의 파이썬 파서(pypdfium2·olefile·xlrd·자체 HWP5/OOXML 파서 …)비교·되돌리기용. 본문 밖 글을 못 읽어 Rust 판과 결과가 갈릴 수 있다
MpowerClassify.exe --dir 폴더 --extractor py            :: 이번 실행만 파이썬 파서로
set CSOCLASSIFY_EXTRACTOR=py                             :: 배치·스크립트 — 환경변수로 (인자가 환경변수보다 앞선다)

상주 데몬(--embed --daemon)도 같은 설정을 따릅니다 2026-11-11 — 클라이언트가 고른 --hybridparse·--extractor 를 요청에 실어 보내고, 데몬이 그 조합의 추출기로 읽습니다. 예전에는 데몬이 사이냅 단독으로 고정돼 두 옵션이 무시됐고, 사이냅이 없는 PC 에서는 데몬이 뜨지 못해 매번 in-process 로 폴백했습니다. 배포본을 바꾼 뒤에는 떠 있던 데몬을 MpowerClassify --stop 으로 한 번 내리세요 — 버전 번호가 같으면 클라이언트가 옛 데몬을 그대로 쓰기 때문입니다.

--synap-only 로 돌리면 모든 문서를 사이냅이 읽으므로 이 스위치와 상관없이 docparse 를 쓰지 않습니다. 자체 파서가 못 읽은 문서를 사이냅으로 넘기는 폴백 사슬과 본문 정제(clean_text)는 rust 일 때도 지금처럼 파이썬이 맡습니다.

    py 면 실행 자체파서=py 만 남습니다.
  • pdfium 은 docparse 가 대신 엽니다. 파이썬 쪽이 CSO_PDFIUM → 실행파일 옆·_internal → pypdfium2_raw 패키지 폴더 순으로 찾아 위치를 넘겨 주므로, 따로 넣을 것은 없습니다.
문서파서를 새 판으로 바꾸려면
DocParse-rust 쪽에서 만든 묶음을 이 저장소에서 아래 한 줄로 받아 넣습니다. third_party/docparse/ 를 갈아 끼우고, 감싸개 두 개(src/csoclassify/extract/_docparse.py·Rust/src/docparse_dyn.rs)도 함께 바꿉니다.

bash scripts/build/update-docparse.sh <묶음.zip> <묶음.tgz>   # 직접 지정

python -m venv .venv
.venv\Scripts\activate

python -m pip install --upgrade pip
pip install -r requirements.txt
프롬프트 앞에 (.venv) 가 붙으면 가상환경 안에 들어온 것입니다. 터미널을 새로 열 때마다 .venv\Scripts\activate 를 다시 실행해야 합니다.

회사 PC 에 이미 필요한 패키지가 다 깔려 있다면 venv 없이 그대로 진행해도 됩니다.

해결됨 2026-09-28 — 예전에는 정본이 갈려 있었습니다. UI 화면(ui\app.py::default_paths())이 ui\doc_rule.yaml (=ui 바로 아래)을 먼저 찾고 없으면 resources\policy 를 봤는데, 실제 파일은 ui\policy\ 에 있어 화면이 보는 파일과 배포에 싣는 파일이 달랐습니다. 지금은 고객 파일의 정본이 ui\policy\ 하나입니다 — 화면 기본 경로가 그곳을 가리키고, scripts/sync_policy.py 도 같은 곳을 원본으로 봅니다. 보안등급 규칙(cso_rule.yaml)도 같은 날 고객 파일로 옮겨, 화면에서 고친 것이 동기화에 되돌아가지 않습니다. 저장소의 resources\policy\cso_rule.yaml 은 새 고객이 복사해 가는 기본값이고 동기화 대상이 아닙니다. 위 확인 절차는 그대로 해 두면 좋습니다.
seed 를 빠뜨리면 조용히 정확도가 깎입니다 — class_seed.jsonl 이 없으면 오류가 나지 않고 전파(Signal B)만 통째로 꺼집니다. 규칙이 못 정한 문서가 구제받지 못하고 등급 없이(null) 나가는데, 화면에는 그냥 "미분류"로 보여 원인을 찾기 어렵습니다. 실제로 2026-08 배포본에서 이 파일이 빠져 보류 21건이 미분류로 나갔고, Rust 판의 seed 를 --seeds 로 지정해 다시 돌리자 두 판의 등급 일치율이 99.5% 로 회복됐습니다(부록 C-5). 원인은 엔진이 아니라 배포 폴더에 파일이 빠진 것이었습니다.

지금은 seed 가 없으면 실행 시 경고를 냅니다 ("전파용 seed 파일이 없어 자동 전파를 건너뜁니다"). 규칙만 쓰는 배포라면 --rule-only 로 의도를 명시하면 그 경고가 사라집니다. 아래 7장의 확인 절차에 외부 seed N건 로드 줄이 실제로 뜨는지 꼭 보세요.
