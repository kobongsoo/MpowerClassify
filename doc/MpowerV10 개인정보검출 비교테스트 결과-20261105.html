Rust 판에는 같은 날 IP 판번호 문맥 누락(아래)을 고친 것도 들어 있다.
  • 공통 11종 전체 — 재현율 V10 54.7% · MC 95.0%, 정밀도 74.1% · 91.3%, F1 62.9% · 93.1%. 11종 모두 MC 의 재현율·F1 이 V10 이상이다. MC 는 Rust 판과 파이썬 판의 정확도가 완전히 같아(아래 항목) 보고서의 정확도 표를 한 열로 합쳤다 — 시간은 두 판이 달라 따로 적는다.
  • MC Rust 판 vs 파이썬 판 — 검출이 한 건도 다르지 않다 (51개 파일, 차이 0건). Rust 판이 프로그램 v9.4.5.85 같은 판번호를 IP 로 잡던 8건은 Rust 쪽 누락이었다 — ko-pii 원본 IP 검출기는 앞에 영문 줄임(v·ver·Sec·Ch·Fig·App)이 오면 IP 로 보지 않는데, Rust 판은 판번호 문맥 정규식을 합쳐 옮기면서 이 갈래를 빠뜨렸다. 원본과 같게 고치고 회귀 사례 7건을 골든 코퍼스에 넣었다 (doc/ko-pii 차이점.html J 절).
  • V10 만 잡은 값 12건 — "계좌"·은행명 없이 문장 속에 쓴 계좌번호 7건(입금처 110-123-456789), 지역명으로 쓴 운전면허 5건(서울 12-345678-90). 둘 다 놓친 값 21건 — 소문자 여권 5, 공백 구분 운전면허 5, 공백·점 구분 사업자번호 8, 문맥 없는 계좌 3.
  • V10 은 "표준 모양"만 잡는다. L1 평문 79.1%, L2 표 58.2%, L3 변형 26.8%(MC 는 100% · 100% · 85.0%). 하이픈 없음·공백/점 구분·전각 숫자로 쓴 주민·외국인번호는 0/20.
  • V10 은 탭(TAB)으로 나뉜 표를 못 읽는다. 같은 표를 쉼표로 쓰면 잡고, 탭으로 쓰면 주민번호를 놓치고 전화번호를 계좌로 잡는다 → L2(표) 재현율이 주민·법인·카드·전화·IP 모두 정확히 50%(쉼표 절반만). 엑셀·DB 에서 내보낸 TXT 가 대개 탭 구분이라 영향이 크다.
  • V10 사업자번호 → 계좌번호 오분류. 사업자번호 60개 중 엄격 13.3%, 유형 무관으로 보면 73%. 계좌 오검출 89건 중 45건이 이 혼동이고, 나머지 44건은 계좌 모양 문서번호·사업자 모양 관리번호 같은 함정이다 → V10 계좌 정밀도 33.6%.

    • 놓친 10건은 모두 "계좌"·은행명 없이 문장 속에 쓴 계좌(입금처 110-123-456789 등)다. ko-pii 는 숫자 모양만으로는 계좌로 보지 않는다 — 계좌는 검증식이 없어 오검출을 막으려는 설계다. 같은 값을 V10 은 7/10 잡지만, 그 대가로 V10 계좌 정밀도가 33.6% 다.
    • 주의 — 표 머리줄 규칙은 이 합성 코퍼스(머리줄에 "계좌번호"가 있는 TSV·CSV)로만 쟀다. 실문서에서 "계좌 개설일" 같은 다른 칸의 숫자를 계좌로 잘못 잡는지는 아직 재지 않았다.
  • MC 여권번호 91.7% (55/60)
    • S·O·G 접두 21/21, M·D·R 접두 24/24, 2021년~ 신형 여권 10/10, 문장 속 여권 5/5. 오검출 0건. 숫자 닮은꼴 되돌리기(O→0 · S→5 · G→6)가 접두를 지우던 문제는 여권만 원문으로 한 번 더 보는 방식으로, 신형 형식은 ko-pii 1.22 와 같은 규칙 [MSROD][0-9]{3}[A-Z][0-9]{4} 로 넣었다(차이 G).
    • 놓친 5건은 모두 소문자 여권(m12345678). ko-pii·V10 모두 대문자 접두만 받는다(V10 도 0/5).
  • MC 의 그 밖의 구멍 — 운전면허 지역명 표기(서울 12-…)·공백 구분(11 23 456789 01) 미지원, 공백·점으로 나눈 사업자번호(123 45 67890, 123.45.67890) 미지원.
  • 체크섬 정책 차이 (특수 묶음) — 체크섬이 틀린 주민번호 V10 0/20 · MC 20/20. 표준식 외국인번호 V10 0/20 · MC 20/20. V10 예외값(회사 대표번호 3개) V10 0/6 · MC 6/6. 사업자 체크섬 불일치 값은 V10 이 계좌로 5/5 잡았다.
  • MC 오검출의 대부분은 함정 값 — 1588·1577 같은 전국 대표번호를 전화로(22건), logo@2x.png 같은 파일명을 이메일로(14건), 버전번호를 IP 로(11건). 19자리 PNU 를 카드번호로 잡은 것도 5건(Luhn 우연 통과).
  • MC 단독 9종 — 주소·건강보험·처방전·EDI·URL 100%, 차량번호 96.7%, 사건번호 90%(가사 드 부호 미지원), PNU 63%(놓친 11건 중 6건은 ko-pii 시도코드 목록에 실제 PNU 코드인 대구 27·인천 28 이 빠져서, 5건은 같은 19자리를 카드번호로 먼저 잡아서), 국적 50%("국적은 베트남이며" 같은 문장형 0/15).
  • 속도 — 작은 파일은 MC Rust 판이 가장 빠르고, 큰 파일은 V10 이 가장 빠르다. 코퍼스 파일(평균 약 0.8천 자)당 중앙값 V10 1.30 ms · MC-Rust 0.47 ms · MC-Py 1.89 ms. 준비 시간 V10 62 ms · MC-Rust 24 ms · MC-Py 473 ms. V10 검출 시간의 약 53% 는 엔진 안 TXT 읽기다.
    크기별(V10 / MC-Rust / MC-Py): 100KB 7.9 ms / 78 ms / 351 ms · 1MB(개인정보 약 1만 5천 건 빽빽) 63 ms / 5.2 s / 20.9 s · 1MB 중 개인정보가 드문 파일 14 ms / 122 ms / 1.7 s. MC 는 두 판 모두 크기·검출 수가 늘면 시간이 크기보다 빠르게 는다(Rust 판도 100KB→1MB 66배) — 검출 로직 자체의 구조 문제로 보인다. 같은 PC 에서도 측정할 때마다 수십 % 씩 흔들리므로, 작은 파일에서의 2배 안쪽 차이는 비슷한 수준으로 읽는 것이 맞다.
  • V10 검출 수 상한 주의 — 기본 MAX_FIND_LIMIT 1000 은 패턴별이 아니라 파일 전체 상한이고, 넘으면 오류 없이(ret=0) 조용히 멈춘다 (1MB 시험 파일에서 1,005건에서 멈춤, 상한을 끄면 7,501건). 크기별 시간은 상한을 끄고 쟀다.
  • 잣대 점검 — 코퍼스를 처음 만들 때 운전면허 지역코드를 11~28 로 만들어 "V10 이 27 을 못 잡음"을 V10 결함으로 셀 뻔했다. 27 은 배정되지 않은 코드라 생성기에서 뺐다. 나머지 극단값(탭 표·PNU·여권 접두)은 한 줄짜리 시험으로 각 엔진의 실제 동작임을 확인했다.
