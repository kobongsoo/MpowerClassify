ko-pii 와 우리 판의 차이

Rust 검출기는 ko-pii 를 옮겨 적은 것입니다. 원칙은 “똑같이 답한다” — 그래서 답이 갈리는 자리는 전부 여기에 적습니다. 최종 갱신 2026-09-04 · 대상 ko-pii 1.15.2

2026-09-03 — 의도적 차이 A·B 를 Python 판에도 이식했습니다. 그전까지 이 문서는 “Rust 만 다르게 판정한다”는 뜻이었고, 그래서 같은 문서에 두 판이 다른 등급을 냈습니다. 이제 A·B 는 두 판 공통이며, 아래 표의 “Rust” 열은 Rust·Python 양쪽으로 읽으십시오. Python 쪽 구현은 classify/rules.py 의 _jibun_admin_ok() · _guarded_ip_detect() 이고, ko-pii 원본 사전(is_district · is_legal_dong)을 그대로 빌려 써 두 판이 같은 명단을 봅니다. C·D·E 는 Rust 판에만 해당하는 이야기로 그대로입니다.

Rust 가 ko-pii 와 같은 답을 내는지는 골든 픽스처로 지킵니다.

Rust/tests/pii_corpus.yaml ← 사람이 고른 '검사 문장' 목록 ↓ python scripts/gen_pii_golden.py (진짜 ko-pii 를 돌려 정답을 받아 적는다) Rust/tests/pii_golden.json ← 정답표 ↓ cargo test pii::golden::정답표와_라벨별_건수가_같다 pii::golden::정답표와_검출값이_같다
규칙 — 일부러 만든 차이는 코퍼스에 넣지 마십시오

pii_corpus.yaml 은 “ko-pii 가 정답” 인 대조표입니다. 일부러 다르게 만든 사례를 여기 넣으면 골든 테스트가 영원히 빨간불이 됩니다. 의도적 차이는 src/pii.rs 의 mod tests 에 손으로 쓴 단위테스트로 두고, 그 근거를 소스 주석([중요] 표시)과 이 문서에 남깁니다.

A·B 는 Python 판에도 같은 판정으로 들어가 있으므로, 양쪽에 같은 시험 벡터를 둡니다. 한쪽만 바뀌면 다른 쪽 시험이 빨간불이 되어 두 판이 갈린 것을 곧바로 알 수 있습니다.

Rust : cargo test → pii::tests::주소_가짜시군구는_거른다 Python : pytest → tests/test_rules.py::test_address_fake_district_rejected → tests/test_rules.py::test_ip_version_context_rejected

A 지번 주소 — 가짜 시군구 거부 일부러 다르게

ko-pii 는 이렇게 동작합니다

지번 주소 정규식은 “시군구로 끝나는 낱말 + 동/읍/면/리로 끝나는 낱말 + 숫자” 를 찾습니다. 그 뒤 문지기가 통과를 정하는데, ko_pii/patterns/address.py 의 이 함수입니다.

def _has_anchor(text, start, city, district):
    if city or district:
        return "prefix"        # ← 검증 없이 통과
    window_start = max(0, start - 20)
    if "주소" in text[window_start:start]:
        return "keyword"
    return None

시·도(광역)가 있을 때만 실제 행정구역인지 확인합니다. 광역이 없으면 “시군구 자리가 비어 있지 않다”는 이유만으로 통과시킵니다. 그래서 이런 일이 생깁니다.

>>> detect_all("연구 정보관리 1", include=["ADDRESS"])
ADDRESS  '연구 정보관리 1'  conf=0.75
  evidence = ['pattern:address_jibun', 'anchor:prefix']
  extra    = {'city': None, 'districts': '연구', 'dong': '정보관리', 'lot_number': '1'}

‘연구’를 區, ‘정보관리’를 里 로 읽은 것입니다. ko-pii 가 스스로 내놓은 출력이라 해석의 여지가 없습니다.

실제로 무엇이 잘못됐나

2026-09-02 D:\분류함 실측에서 인사평가 엑셀 5개에 이 모양이 10건 있었습니다. 주소가 하나도 없는 문서인데 ADDRESS 가 잡혀 등급이 S 로 올라갑니다.

버전을 올려도 해결되지 않습니다. PyPI 최신은 1.15.2(2026-06-18)이고 설치본과 같습니다. GitHub CHANGELOG.md 에는 1.15.3·1.15.4·1.16.0 이 있지만 PyPI 에 배포되지 않았고, 업스트림 main 의 address.py 를 받아 대조해 보니 설치본과 347줄이 한 줄도 다르지 않았습니다(2026-09-02 확인). 그래서 우리 쪽에서 막기로 했습니다.

Rust 는 이렇게 합니다

광역이 없을 때, 시군구 토큰과 동/읍/면/리 토큰 중 최소 하나는 진짜 행정구역 이름이어야 한다고 요구합니다. 둘 다 사전에 없으면 주소로 보지 않습니다. 구현은 src/pii.rs 의 jibun_admin_ok() 입니다.

왜 ‘둘 다’가 아니라 ‘둘 중 하나’인가. “시군구가 사전에 있어야 한다”로 못박으면, 사전에 빠진 기초자치단체에서 진짜 주소를 놓칩니다 (ALL_DISTRICTS 는 206개로, 실제 기초자치단체 226개를 전부 담고 있지 않습니다). 법정동 가제티어는 10,368개로 훨씬 촘촘하니, 둘 중 하나만 맞아도 통과시키면 오탐을 걷어내면서 미탐을 최소화할 수 있습니다.
그래도 미탐은 0 이 아니었습니다 — 보충 사전을 덧댄 이유
전수 스윕(1,780건, 2026-09-03)에서 두 조건이 함께 실패한 실주소가 나왔습니다. 원미구 중동 1153(부천시) 2건입니다.
  • is_district("원미구") = false — ALL_DISTRICTS 에는 광역시의 자치구만 있고, 광역시가 아닌 시(市) 아래의 일반구(행정구)가 빠져 있습니다. 일반구 33개를 표본으로 확인하니 31개가 없었습니다(분당·팔달·덕양·수지·상당 …).
  • is_legal_dong("중동") = false — 법정동 가제티어에도 없어 구멍을 메우지 못했습니다.
그래서 일반구 33개를 보충 사전(_EXTRA_DISTRICTS · EXTRA_DISTRICTS)으로 덧대, 시군구 판정을 ko-pii 사전 ∪ 보충 사전으로 넓혔습니다. 전부 고유한 지명이라 연구 같은 평범한 낱말을 되살리지 않습니다(회귀 시험이 그것도 함께 지킵니다).

영향은 없었습니다 — 미탐이 난 두 문서(공개 데이터셋 klue-mrc)는 다른 주소 20건이 남아 등급이 C → C 로 그대로였고, 전수 등급 변화는 여전히 1건(올바른 정정)이었습니다. 그래도 미탐은 미탐이라 고쳤습니다.

적용 범위는 지번 브랜치뿐입니다. 도로명(…로/길 + 번호)은 신호가 훨씬 강해 이 판정을 그대로 걸면 미탐 위험만 커집니다. 도로명에서 나온 오탐은 아래 A-2 가 더 좁게 막습니다.

A-2 도로명 주소 — 낱말 속 가짜 시군구 거부 일부러 다르게

ko-pii 도로명 갈래는 시군구와 도로명 사이에 띄어쓰기를 요구하지 않습니다. 그래서 낱말 하나가 쪼개져 주소가 됩니다.

detect_all("표정 변화가 실시간으로 3D 인물", include=["ADDRESS"])
  → ADDRESS '실시간으로 3'  extra={'city': None, 'districts': '실시', 'road': '간으로', 'building_number': '3'}

'실시간으로'를 실시(市) + 간으로(路) + 3 으로 읽은 것입니다. 2026-10-26 배포 교차 검증에서 4_디지털콘텐츠_통합보고서_업로드용.pdf 로 처음 관측했습니다.

세 조건이 모두 맞을 때만 버립니다 — 진짜 주소를 놓치지 않게 좁게 막습니다.

조건예결과
① 광역(시·도)이 없다서울특별시 강남구 테헤란로 152광역이 있어 통과
② 마지막 시군구와 도로명이 붙어 있다강남구 테헤란로 152띄어 써서 통과
③ 그 시군구가 진짜 행정구역이 아니다(ko-pii 사전 ∪ 보충 사전)강남구테헤란로 152강남구가 실제라 통과
셋 다 맞음실시간으로 3거부

버린 자리는 그대로 '이미 본 자리'로 남깁니다. 파이썬 판은 ko-pii 가 낸 결과를 뒤에서 거르므로 ko-pii 안에서 지번 갈래가 그 자리를 다시 잡지 않습니다 — Rust 도 같게 했습니다.

B IP — 판번호 문맥 배제 일부러 다르게

ko-pii 는 한글 문맥(버전 1.2.3.4)만 걸러냅니다. 영문 문서에서는 판번호를 IP 로 잡습니다.

입력ko-piiRust
버전 1.2.3.4 로 배포함없음없음
Release 1.2 / 1.2.3.4 Build 7IP 검출없음

Rust 는 RE_IP_CTX_LEFT/RE_IP_CTX_RIGHT 로 영문 낱말(version·release·build· patch·section·figure·table…)과 오른쪽 문맥까지 봅니다. 실측 986개 문서에서 이 차이가 19건이었고, 전부 판번호였습니다. 맞추면 오히려 나빠지므로 그대로 둡니다.

C IPv6 사상 주소 — 범위가 다름 아직 못 맞춤

등급에는 영향이 없습니다. 검출 건수는 같고 잡은 범위(span)만 다릅니다. 등급은 “IP 가 몇 건인가”로 정해지므로 결과가 갈리지 않습니다. 값을 그대로 보여 주는 --with-pii 출력에서만 차이가 보입니다.

D EMAIL·IP 겹침 해소 아직 못 맞춤

표를 텍스트로 뽑아 칸 사이 구분자가 사라진 줄에서, 이메일이 IP 를 삼키느냐가 미세하게 갈립니다.

01kim001@testmail.net192.168.10.25hong002@example.co.kr

ko-pii 는 IP 를 따로 잡고, Rust 는 EMAIL 이 그 구간을 가져갑니다(반대인 경우도 있습니다). 구분자를 잃은 텍스트에서만 생기는 일이라 추출 품질 문제에 가깝고, 우선순위를 낮춰 두었습니다.

E 이어붙은 주민번호 고침

표에서 주민번호 칸 두 개가 구분자 없이 이어 붙으면 Rust 가 하나도 못 잡았습니다.

951026-1411232821016-2760084
  ├ 앞 번호: 뒤에 숫자가 이어져 탈락
  ├ 뒤 번호: 앞에 숫자가 있어 탈락
  └ 겹친 자리 13자리(앞7+뒤6) 가 '구분자 없는 주민번호'로 성립 ← ko-pii 는 이것을 잡는다

원인은 det_rrn·det_frn 만 captures_iter 를 쓰고 있었던 것입니다. 매치를 만든 뒤 경계 검사로 버리는 사이 반복자가 그 매치 끝까지 지나가, 안쪽에서 시작하는 매치를 잃습니다 (부록 E-① 과 같은 갈래). captures_at 기반 captures_bounded() 를 만들어 붙여 parity 를 되찾았습니다.

회귀 사례 4건을 pii_corpus.yaml 에 넣었습니다(값은 체크섬만 맞춘 가짜 — 실문서 값은 개인정보라 넣을 수 없습니다). 이건 맞추는 게 목적이라 코퍼스에 넣는 것이 맞습니다.

F 새 차이를 만들 때

  1. 정말 우리가 맞나 확인합니다 — ko-pii 를 직접 돌려 evidence·extra 까지 봅니다.
  2. 업스트림에서 고쳐졌는지 봅니다 — PyPI 최신 버전과, GitHub main 의 해당 파일을 받아 대조합니다. (배포되지 않은 버전이 CHANGELOG 에만 있는 경우가 실제로 있었습니다.)
  3. 영향 범위를 잽니다 — 실문서로 몇 건이 바뀌는지, 미탐이 생기지 않는지.
  4. 소스에 [중요] 주석으로 ko-pii 원문 인용 + 우리 규칙 + 왜 를 적습니다.
  5. mod tests 에 손으로 쓴 단위테스트를 둡니다. 코퍼스에는 넣지 않습니다.
  6. 두 판에 함께 넣습니다 — 한쪽에만 넣으면 같은 문서에 다른 등급이 나옵니다 (A·B 가 2026-09-03 까지 실제로 그런 상태였습니다).
  7. 이 문서의 30초 요약 표에 한 줄 추가합니다.
