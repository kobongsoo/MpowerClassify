doc_rule.yaml — 업무분류 1차 분류 가이드

문서가 어느 업무분류(분류체계 노드)로 가는지 정하는 규칙 파일입니다. 무엇을 보고, 어떻게 점수를 매기고, 언제 붙이는지를 예시와 함께 설명합니다. 보안등급(C/S/O)은 cso_rule.yaml 이 따로 정합니다(CSO_Rule.html).

0 개요 · 파일 위치

업무분류는 파일 몇 개가 함께 움직입니다. 역할이 다르고, 고치는 사람도 다릅니다. 2026-09-22 변경 규칙 파일은 이제 사람이 고치지 않고 매번 새로 만듭니다. 사람이 고치는 것은 회사 조정 파일과 회사 유의어 사전뿐입니다.

파일누가 쓰나무엇
doc_classification_export.json엠파워(내보내기, 읽기만)회사 분류 체계. 기술/개발 > 매뉴얼 같은 나무와 각 노드의 id(dc_id). 규칙을 만드는 재료
doc_rule.yaml자동 생성(--build-doc-rule)판단 기준 — 이 문서의 주인공. 분류마다 “어떤 말이 어디에 나오면 이 분류인가”. 분류 체계(제목·경로)와 핵어까지 이 안에 들어 있어, 판정 때는 이 파일 하나만 읽습니다. 손으로 고치지 않습니다
doc_rule.local.yaml관리자(화면)회사 조정 — 자동값 위에 덧씌우는 결정(칸 비우기·말 빼기/더하기·분류 끄기·설정). 조정마다 이유(why)를 적습니다(13장)
synonyms/doc_synonyms.*.yaml제품(core·업종) · 관리자(local)같은 뜻 다른 말 사전. 매뉴얼 ↔ 사용설명서·메뉴얼·manual …
doc_rule_template.yaml제품규칙 파일의 설정(문턱·신호 점수·2차 분류) 기본값과 그 값을 고른 이유
doc_rule.yaml 을 찾는 순서위치
① 인자--doc-rules <파일경로> 로 직접 지정하면 그것
② 환경변수CSOCLASSIFY_POLICY_DIR 폴더의 doc_rule.yaml
③ 기본(배포)실행파일과 같은 폴더의 doc_rule.yaml
파일이 없거나 옛 모양일 때 2026-09-22 변경
· 분류 체계는 자동 생성된 doc_rule.yaml 안에 있습니다. 따로 떨어진 분류 체계 파일(옛 doc_taxonomy.yaml)은 읽지 않습니다.
· doc_rule.yaml 이 없으면 업무분류 축을 건너뜁니다(보안등급만 돕니다). --axis doctype 으로 업무분류를 요구했으면 종료코드 3으로 멈춥니다. 예전의 ‘규칙 없이 기준 문서로만 분류’는 규칙 파일이 없으면 할 수 없습니다 — 분류 체계가 규칙 안에 있기 때문입니다. 규칙은 두고 기준 문서로만 분류하려면 --doctype-vector-only 를 씁니다.
· 손으로 고쳐 온 옛 모양 doc_rule.yaml 은 읽지 않고 종료코드 4로 멈춥니다([G0]). 화면의 [새 방식으로 바꾸기](13장)나 --build-doc-rule 로 다시 만드세요.

1 한눈에 — 문서 하나가 분류되는 흐름

위에서부터 차례로 묻고, 답이 나오면 거기서 멈춥니다.

문서 하나 (본문 + 파일 경로) │ ├─ ① 규칙 스캔 ─── 규칙마다 네 곳을 본다 │ 제목(첫 줄) 0.65 · 앞부분 400자 0.55 · 파일 이름 0.30 · 본문 전체 0.15 │ └ 걸린 근거를 합친 점수가 0.35(t_low) 이상이면 → 라벨 │ ├─ ② 후보가 하나도 없으면 │ └ 파일 이름 끝자리가 분류 제목이면 → 라벨 0.35 ⚠ 확인 필요(확정 아님) │ ├─ ③ 2차 분류 (기준 문서와 내용 비교) │ └ 아주 비슷한 기준 문서가 있으면 → 라벨을 더한다(규칙 라벨을 빼앗지 않음) │ 기본 실행에서는 주로 ①·②에서 못 붙인 문서가 대상이다 │ └─ ④ 다 아니면 미분류 → 검토함에서 사람이 정한다

①이 대부분을 맡습니다. ②는 ①이 놓친 “이름만 있는 문서”, ③은 “이름도 표지도 없지만 비슷한 문서가 이미 분류된 경우”를 잡습니다. ①②는 doc_rule.yaml 이, ③은 기준 문서 파일(class_seed.jsonl)과 embed: 블록이 정합니다.

2 doc_rule.yaml 만들기 — 자동 생성

손으로 쓰지 않습니다. 명령 하나가 체계 JSON · 유의어 사전 · 본보기 · 회사 조정을 합쳐 규칙 파일을 통째로 새로 만듭니다. 분류마다 규칙 한 줄을 만들고, 분류 이름에서 말을 뽑아 채웁니다.

MpowerClassify-rs.exe --build-doc-rule --export-input doc_classification_export.json --doc-rules doc_rule.yaml
  • --export-input 을 빼면 규칙 파일 옆의 doc_classification_export.json 을 씁니다. 사전·본보기·doc_rule.local.yaml 도 규칙 파일과 같은 폴더에서 찾습니다.
  • 화면에서는 설정 › ① 회사 분류 체계 [다시 가져오기], 또는 ② 판단 기준 › 업무분류 [규칙 다시 만들기]가 같은 일을 합니다.
  • 같은 입력이면 Python·Rust 두 판이 만든 파일이 글자까지 같습니다. 판 이름(version: doctype-gen-…)은 내용에서 나오므로, 입력이 같으면 판도 같습니다.
  • 엠파워에서 분류 체계가 바뀌면 JSON 만 다시 받아 이 명령을 다시 돌립니다. 회사 조정은 doc_rule.local.yaml 에 남아 있어 그대로 다시 얹힙니다.

예 — 분류 체계에 기술/개발 > 매뉴얼 이 있으면

- id: dt_dc_002_002
  node: DC_002_002                # 어느 분류인지(이름이 아니라 id 로 잇는다)
  title: 매뉴얼                    # 지금 분류 제목 — 이 말들을 만든 제목
  path: 기술/개발 > 매뉴얼          # 결과의 path 로 그대로 나간다
  path_ids: [DC_002, DC_002_002]   # 조상 관계 — 대분류 묶기에 쓴다
  weight: medium                  # 이 규칙을 얼마나 믿나(high/medium/low)
  title_terms: [매뉴얼, 사용설명서, 사용자매뉴얼, 운영매뉴얼, 안내서, 사용법, manual, guide, …]
  head_terms:  [매뉴얼, 사용설명서, 사용자매뉴얼, 운영매뉴얼, 안내서, 사용법, …]
  terms:       [매뉴얼, 사용설명서, 사용자매뉴얼, 운영매뉴얼, 안내서, 사용법, …]
  filename:    [매뉴얼, 메뉴얼, 사용설명서, user_guide, user-manual, 설치_가이드, …]
  exclude:     [가이드라인, 매뉴얼 참조, 매뉴얼을 참고]
  heads:       [매뉴얼, 사용설명서, …]   # 핵어(파일 이름 끝자리, 7장) — 비면 이 분류는 핵어를 안 쓴다
  local: [add:title_terms]         # 회사 조정이 들어간 칸(판정에는 안 씀 — 찾아가는 표지)
  • 사용설명서·안내서·manual 은 아무도 치지 않았습니다. 유의어 사전이 “매뉴얼과 같은 뜻”으로 알고 있어서 들어간 것입니다.
  • user_guide·user-manual 처럼 파일 이름에서 쓰는 구분자 표기도 만들어 줍니다.
  • exclude 도 자동입니다 — “가이드라인”이 “가이드”로 걸리는 사고를 막습니다.
관리자가 할 일은 화면 표에서 이상한 말을 지우고, 회사에서 쓰는 말을 더하는 것뿐입니다. 화면은 그 차이를 doc_rule.local.yaml 에 조정으로 적고 규칙을 다시 만듭니다(13장). 규칙 파일을 손으로 고치면 다음에 다시 만들 때 사라지고, 엔진이 “만들어진 뒤 손으로 고쳐졌습니다” 경고를 냅니다.
만든 뒤 입력이 바뀌면 알려 줍니다. 규칙 파일 머리의 generated.inputs 에 재료 파일마다 지문(sha256)이 적혀 있어, 체계 JSON·사전·본보기·조정 파일 중 하나라도 바뀌거나 없어지면 분류할 때마다 “규칙을 만든 뒤 입력이 바뀌었습니다: … — --build-doc-rule 로 다시 만드세요”가 뜹니다. 배포할 때는 이 재료 파일들을 규칙 파일 곁에 함께 둡니다.
대분류(서랍)에는 규칙을 만들지 않습니다. 기술/개발 처럼 자식이 있는 최상위 노드는 문서에 그대로 적히는 말이 아니라 서랍 이름이라, 규칙을 걸면 아무 문서나 걸립니다. 꺼 둔 분류(status: 0)도 뺍니다.

3 규칙 한 줄 — 필드

필드필수뜻기본
id필수규칙 이름. 파일 안에서 겹치면 안 됩니다—
node필수분류체계의 dc_id. 분류체계에 없으면 로드가 막힙니다(T5), 꺼 둔 노드면 이 규칙은 쉽니다(T6)—
weight선택이 규칙을 얼마나 믿나 — high·medium·low. 네 신호의 점수 줄을 고릅니다(4장)medium
title_terms선택제목(첫 줄)에 이 말이 있으면—
head_terms선택앞부분(기본 400자)에 이 말이 있으면—
terms선택본문 어디든 이 말이 나오면(보조 — 혼자서는 라벨을 못 만듭니다)—
filename선택파일 이름(폴더 제외)에 이 말이 있으면—
exclude선택이 말 안에 든 매치는 세지 않습니다. 네 칸 모두에 적용—
head_chars선택이 규칙만 앞부분 길이를 바꿀 때. 공백 묶음은 한 칸으로 센다(2026-10-19)defaults 값(400)
min_distinct선택본문 신호: 서로 다른 말이 몇 종 이상 나와야 하나defaults 값(1)
min_count선택본문 신호: 합쳐서 몇 번 이상 나와야 하나defaults 값(1)
title · path · path_ids자동분류 제목·경로·조상 id. 판정할 때 분류 체계를 이 칸들에서 다시 짓습니다—
heads자동이 분류의 핵어 목록(7장). 비어 있으면 핵어 층에서 이 분류를 쓰지 않습니다
filename 과 말이 겹쳐 보여도 일이 다릅니다 — filename 은 파일 이름 어디에든 있으면 다른 신호와 합쳐지는 보조 증거(0.30)이고, heads 는 후보가 하나도 없을 때 파일 이름 끝자리만 보고 ‘확인 필요’ 라벨(0.35)을 붙이므로 더 좁게(넓은 말·주제 이름 분류는 빼고) 만듭니다.		—
local자동회사 조정이 들어간 칸(예 clear:terms). 판정은 이 칸을 읽지 않습니다—

화면의 규칙 표에서는 칸 이름이 이렇게 보입니다 — 제목(첫 줄)에 · 앞부분(400자)에 · 본문 어디든(보조) · 파일 이름에 · 단, 이 말이 있으면 제외.

4 네 신호 — 어디를 보나

같은 말이라도 문서의 어디에 있느냐로 믿을 만함이 다릅니다. 그래서 칸이 넷입니다.

신호보는 곳highmediumlow왜 그 점수인가
title첫 비어있지 않은 줄0.800.650.50사람이 문서 맨 위에 일부러 적은 이름 — 가장 셉니다
head앞 400자0.700.550.40표지 다음으로 성격이 잘 드러나는 구간
name파일 이름0.300.300.30짧고 의도적이지만 바뀔 수 있습니다. 그래서 혼자서는 문턱(0.35)을 못 넘게 해 뒀습니다
body본문 전체0.250.150.10어느 문서에나 나올 수 있어 가장 약합니다. 혼자서는 라벨을 못 만듭니다

가로줄(high/medium/low)은 규칙의 weight 가 고릅니다. 파일 이름만 세 칸이 같은 것은 일부러입니다 — “이름에 그 말이 있다”는 사실 하나뿐이라 규칙의 자신감으로 등급을 나눌 근거가 없습니다. 이 표는 signals: 블록으로 바꿀 수 있습니다.

찾는 방식의 세부

규칙예
부분 일치 — 한국어는 띄어쓰기가 없어 말 안에서도 찾습니다계약서 → “용역계약서” 걸림
자간 벌리기도 잡습니다(제목·앞부분·파일 이름)“출 장 여 비 규 정” → 규정 걸림
영문은 단어 경계로만 찾습니다erd 가 “GERD”·“ordered” 안에서는 안 걸림
제외어 안의 매치는 세지 않습니다exclude: [가이드라인] → “보안 가이드라인”의 가이드는 안 셈
ppt·xls·xlsx 는 제목 신호를 건너뜁니다첫 줄이 제목인 비율이 ppt 16.7%, xls 50%라 믿을 수 없어서

5 점수를 합치는 법

걸린 신호의 점수를 더하지 않고 이렇게 합칩니다(noisy-OR).

최종 점수 = 1 − (1 − 신호1) × (1 − 신호2) × …

예) 제목 0.65 + 파일 이름 0.30
    = 1 − 0.35 × 0.70 = 0.755
  • 근거가 쌓일수록 오르지만 1 을 넘지 않습니다.
  • 약한 근거를 아무리 모아도 강한 근거 하나를 쉽게 못 넘습니다.

붙일지 말지 — 규칙 셋

규칙뜻
① 0.35(t_low) 미만이면 버린다지금 실제로 후보를 가르는 유일한 문턱입니다
② 본문 신호만으로는 안 붙인다“매뉴얼을 참고하세요”라고 쓴 문서가 매뉴얼은 아니니까요
③ 같은 분류를 두 규칙이 맞히면 점수가 높은 쪽을 남긴다근거도 그 규칙 것을 남깁니다(감사할 때 설명이 맞아야 하므로)

예 ② — 본문에서만 언급됨

파일:        2026년_3분기_업무보고.hwp
본문 어딘가: "… 자세한 절차는 사용설명서를 참고하십시오 …"

본문 신호 0.15 하나뿐입니다. 본문 신호는 혼자서 라벨을 못 만듭니다 — 이 문서는 매뉴얼을 언급했을 뿐 매뉴얼이 아닙니다.

→ 안 붙음

예 ③ — 제외어가 막음

파일:        정보보호_가이드라인_2026.pdf
본문 첫 줄:  정보보호 가이드라인

가이드 가 제목에 있지만 exclude: [가이드라인] 안에 든 매치라 세지 않습니다.

→ 매뉴얼로 안 붙음

예 ④ — 파일 이름에만 있음

파일:  매뉴얼_초안_정리중.docx
본문:  (표지 없음 · 목차만)

파일 이름 신호 0.30 — 문턱(0.35)에 못 미칩니다. 파일 이름만 보고 붙인 라벨은 오탐이 잦아 일부러 못 넘게 해 뒀습니다.

→ 규칙으로는 안 붙음 — 이런 문서는 7장의 핵어 층이 다시 봅니다(끝자리를 보므로, 이 예는 끝자리가 “정리중”이라 거기서도 안 붙습니다)

예 ⑤ — ppt 는 첫 줄을 제목으로 안 봄

파일:        제품소개.pptx
본문 첫 줄:  사용자 매뉴얼 목차        ← 슬라이드 도형 순서상 우연히 첫 줄

ppt 는 첫 줄이 제목이 아닌 경우가 많아 제목 신호를 건너뜁니다. 대신 앞부분(0.55) 칸이 이 말을 봅니다.

→ 앞부분 신호로 매뉴얼 55% (제목으로 셌다면 65%)

7 1층 핵어 — 파일 이름 끝자리

한국어 복합명사는 마지막 명사가 그 말의 정체입니다. 보안전송관리시스템_작업계획서 는 시스템이 아니라 계획서입니다. 그래서 규칙 스캔이 후보를 하나도 못 만든 문서에 한해, 파일 이름의 끝자리를 한 번 더 봅니다.

보안전송관리시스템_작업계획서_최종_v2(수정본).hwp └───────────────────── 잡음 꼬리 걷기 (최종·v2·(수정본)·날짜·복사본 …) 보안전송관리시스템_작업계획서 └──── 끝자리 = 계획서 → 분류 제목이 '계획서' 인 노드
파일 이름끝자리결과
제안서_검토_회의록.hwp회의록회의록 분류로
회의록_양식_제안서.hwp제안서제안서 분류로
보고서_양식.hwp양식안 붙음 (끝자리가 분류 제목이 아님)

위 두 줄은 단어 구성이 같은데 자리가 다릅니다. 가방처럼 “어딘가에 있나”만 보는 규칙 스캔으로는 둘을 못 가릅니다.

핵어는 어디서 오나 — 새로 적지 않습니다

분류 체계의 잎 제목이 곧 핵어이고, 여기에 유의어 사전의 말을 얹습니다. 규칙을 만들 때 분류마다 heads 칸에 적고, 잡음 꼬리 목록도 최상위 noise_tails 에 함께 적습니다. 고객이 분류 이름을 바꾸면 규칙을 다시 만들 때 저절로 따라갑니다.

제목이 다 핵어는 아닙니다 — 세 겹으로 거릅니다

겹무엇예
ⓐ 자동너무 넓은 말 · 묶음 제목(○○자료) · 문서종류가 아닌 제목(주제·고유명) · 흔한 끝말(규정·지침) · 다른 분류와 겹치는 제목은 안 씁니다행사자료 ⛔ 묶음 · 복리후생 ⛔ 주제 · 회의록 ✅
ⓑ 말 단위 끄기ⓐ가 놓친 예외. 말로 적으므로 제목이 바뀌면 저절로 다시 쓰입니다doc_rule.local.yaml 의
head: {title_exclude: [연수교재]}
ⓒ 노드 단위 끄기드묾. 끌 당시 제목을 함께 적어, 제목이 바뀌면 무효 + 재검토 안내head: {node_off: [{node: DC_X, title_at_decision: 연수교재}]}

화면 설정 › ② 판단 기준 › 업무분류 › “파일 이름 끝자리로 찾기” 표에서 분류마다 쓰는지·왜 안 쓰는지를 보고, 체크 한 번으로 끌 수 있습니다(ⓑ). ⓒ는 그 아래 접힘에 있습니다.

안전장치 셋 — 파일 이름은 바뀔 수 있으니 확정하지 않습니다
  • ① 다른 후보가 없을 때만 — 규칙 스캔이 하나라도 붙였으면 이 층은 돌지 않습니다. 점수는 문턱과 같은 0.35 하나뿐입니다
  • ② 검토 대상 표시 — 결과에 review: true · basis: "name_head" 가 실리고, 화면은 이 라벨을 자동 확정으로 보여 주지 않습니다(문서 상세에 “확인 필요 — 파일 이름만 보고 제안”). 2026-09-22 부터 다만 검토함에는 올리지 않습니다 — 1차 규칙이 아무것도 못 붙인 문서에만 붙고 평가셋에서 7건 모두 맞아, 분류된 문서로 셉니다
  • ③ 기준 문서가 되지 않음 — 이 라벨로는 2차 분류의 잣대(씨앗)를 만들지 않습니다

8 여러 분류가 걸리면

업무분류는 문서 하나에 여러 개가 붙을 수 있습니다(보안등급은 하나). 세 가지가 정리합니다.

상황처리
조상과 자손이 함께 걸림
예) 설계문서 + 그 아래 요구사항정의서		조상은 버리고 자손만 남깁니다 — 자손의 경로에 조상이 이미 들어 있습니다
서로 다른 가지가 걸림
예) 계약서 + 제안서		둘 다 남깁니다. 1계층이 다르면 cross_branch 경고를 붙여 검토 우선순위를 올립니다(자동으로 버리지 않음)
몇 개까지 남기나conflict 가 정합니다 — 아래
conflict:                      # 본보기 기본값(2026-09-28~) — 점수 높은 두 개만
  strategy: top_n
  n: 2

conflict: all                  # 걸린 것을 전부 남긴다(점수 높은 순)

conflict:                      # 상위 N 개만
  strategy: top_n
  n: 3
  min_confidence: 0.5          # (선택) 이 점수 미만은 버린다

top_n 으로 잘린 후보가 있으면 결과에 truncated: 잘린 수 가 남습니다 — 무엇이 빠졌는지 숨기지 않습니다. 실행할 때 --conflict doctype=top_n:3 으로 덮어쓸 수도 있습니다.

9 2차 분류 — 비슷한 문서 (embed)

문서의 내용을 이미 분류가 확정된 기준 문서(class_seed.jsonl)와 견줍니다. 같은 문서의 다른 판·같은 시리즈를 잘 잡습니다.

  • 후보를 더하기만 합니다. 규칙이 붙인 라벨을 빼앗거나 바꾸지 않습니다. 같은 분류면 근거에 embed 가 덧붙고, 새 분류면 후보가 하나 늘어납니다
  • 누가 대상인가 — 비교하려면 문서의 벡터가 있어야 합니다. 기본 실행(--embed-needed)은 ‘업무분류 후보가 없는 문서 · 보안등급을 판단 못 한 문서 · 기준 문서 후보’만 벡터를 만들므로, 사실상 1차에서 못 붙인 문서가 대상입니다. --with-vector 로 전부 만들면 모든 문서가 대상이 됩니다
embed:
  enabled: true
  k: 5                  # 가장 비슷한 기준 문서 몇 개를 이웃으로 보나
  min_sim: 0.70         # 가장 닮은 이웃(1등)조차 이보다 덜 닮았으면 아무것도 안 붙인다
  min_share: 0.40       # 한 분류의 몫(유사도 가중)이 이 비율 이상이면 그 분류로
  dup_threshold: 0.95   # 1등이 이만큼 닮으면 사본으로 보고 그 분류를 그대로 물려받는다

defaults:
  embed_cap: 0.65       # 비슷한 문서만 보고 붙은 라벨의 점수 상한

순서대로 묻습니다.

단계조건결과
①가장 닮은 기준 문서(1등)의 유사도 ≥ 0.95사본으로 보고 그 문서의 분류를 그대로 물려받음
②1등의 유사도 < 0.70믿을 이웃이 없음 → 안 붙임
③그 밖이웃 5개의 유사도를 분류별로 더해 몫을 계산 → 몫이 40% 이상인 분류를 모두 붙임(여러 개 가능)
예 — 가장 닮은 이웃 5개가 매뉴얼 0.86 · 매뉴얼 0.82 · 회의록 0.80 · 매뉴얼 0.76 · 제안서 0.72 이면
1등이 0.86(0.95 미만 · 0.70 이상)이라 ③으로 갑니다. 유사도 합은 3.96, 매뉴얼 몫 = (0.86+0.82+0.76) / 3.96 = 62% · 회의록 20% · 제안서 18% → 매뉴얼만 붙습니다.
점수는 몫(0.62)이지만 비슷한 문서만 보고 붙은 라벨이라 embed_cap(0.65)을 넘지 못합니다 — 무엇이 닮았는지 사람에게 설명할 수 없는 근거가, 규칙 근거가 있는 라벨보다 세지면 안 되기 때문입니다.

기준 문서는 화면 기준문서 메뉴나 CLI --seed-add 로 등록합니다. 실행할 때 --rule-only 를 주면 이 단계를 끕니다.

12 자주 헷갈리는 것

“규정” 을 본문 칸에 넣으면 왜 안 되나

규정·지침 같은 말은 본문·앞부분에 너무 흔합니다(“관련 규정에 따라…”). 그래서 유의어 사전이 이런 말을 제목·파일 이름 칸에만 넣습니다. 어느 칸에 넣느냐로 결과가 갈립니다 — 제목 칸이면 정확하고 앞부분 칸이면 오탐입니다.

파일 이름에 분류 이름이 있는데 왜 안 붙나

파일 이름 신호(0.30)는 혼자서 문턱(0.35)을 못 넘습니다. 제목·앞부분·본문 중 하나라도 함께 걸려야 합니다. 다른 단서가 전혀 없으면 핵어 층이 끝자리를 한 번 더 보지만, 그때도 확인 필요로만 붙습니다.

분류 이름을 바꾸면 규칙도 고쳐야 하나

아니요 — 규칙을 다시 만들면 됩니다. 결과는 dc_id 로 잇기 때문에 옛 문서도 새 이름으로 나옵니다. 규칙의 자동 말과 핵어는 새 제목에서 다시 뽑힙니다(옛 이름 계열 말은 빠집니다). 회사 조정은 dc_id 로 적혀 있어 그대로 얹히고, 조정을 적을 때의 이름(title_at_decision)과 지금 이름이 다르면 “규칙을 만들 때 알린 것”에 안내가 뜹니다 — 그 조정이 새 이름에도 맞는지 확인하세요. 옛 이름으로 불리는 문서가 많으면 그 말을 조정의 add 로 더해 둡니다.

“빠진 유의어만 더하기”는 어디 갔나

자동 생성에서는 필요 없습니다. 규칙을 만들 때마다 사전의 말이 전부 들어가고, 사람이 비운 칸은 조정 파일의 clear 가 다시 비웁니다. 예전 방식(사람이 규칙 파일을 직접 고침)에서는 이 기능이 사람이 일부러 비운 칸을 ‘빠진 말’로 알고 다시 채우는 일이 있었습니다(2026-09-22 발견) — 자동 생성으로 바꾼 이유 중 하나입니다.

점수가 높으면 확정인가

아닙니다. 자동 판정은 언제나 제안입니다. 화면은 사람이 손대기 전까지 제안을 “자동 확정”으로 보여 주고, 관리자가 [이대로 확정]하거나 체크를 풀어 “아니라고 표시함”으로 남깁니다. 그 결정은 cso_override.jsonl 에 따로 쌓이고, 원본 결과는 고치지 않습니다. 파일 이름 끝자리로만 붙은 라벨은 “자동 확정”이 아니라 “확인 필요”로 보입니다(검토함에는 올리지 않음).

보안등급의 “확신 60% 미만”과 관계있나

없습니다. 그 값은 보안등급 검토함 편입선이고 cso_rule.yaml 의 defaults.review_threshold 에 있습니다. 업무분류는 “라벨이 하나도 없음”일 때 검토함에 들어갑니다(파일 이름만 보고 붙은 문서는 2026-09-22 부터 올리지 않음).

잘못 적으면 어떻게 되나

로드할 때 막고 무엇이 틀렸는지 알려 줍니다 — 분류체계에 없는 node(T5), 겹치는 id(T0), 범위를 벗어난 문턱(T20), 더 이상 쓰지 않는 form·structure·paths 필드(T21) 등. 조용히 무시하면 “고쳤는데 왜 안 바뀌지”가 되기 때문입니다. --check-rules 로 분류를 돌리지 않고 검사만 할 수 있습니다. 회사 조정 파일을 잘못 적어도 규칙을 만들 때 막습니다(L0~L6, 13장).

13 회사 조정 — doc_rule.local.yaml

규칙 파일은 매번 새로 만들어지므로, 사람의 결정은 이 파일에만 둡니다. 열쇠는 분류 이름이 아니라 dc_id 라서 분류 이름이 바뀌어도 조정이 살아 있습니다. 보통은 화면(설정 › ② 판단 기준 › 업무분류)이 표에서 고친 것을 이 파일로 적어 주므로 직접 열 일은 드뭅니다.

version: 2026.09.22
industry: [finance]                # 얹을 업종 사전(없으면 core 만)

settings:                          # 적은 것만 본보기 기본값을 덮는다
  defaults: {t_low: 0.35}

rules:
  DC_007:                          # 자사 제품
    title_at_decision: 엠파워제품      # 적을 당시 이름 — 바뀌면 만들 때 안내
    clear: [head_terms, terms]         # 이 칸의 자동 말을 비운다
    why: "제품명 언급만으로 붙지 않게 — 평가셋 정밀도 65.1→71.8%"
  DC_002_002:                      # 매뉴얼
    add:    {title_terms: [도움말]}
    remove: {filename: [가이드]}
    why: "제품 도움말 html — 사람 판정 매뉴얼"
  DC_004_009:
    enabled: false                 # 이 회사는 쓰지 않는 분류
    weight: low

head:                              # 핵어(7장) 조정
  title_exclude: [결과서]
  node_off: []
칸뜻
clear칸 이름 목록 — 그 칸의 자동 말을 모두 비웁니다
remove칸 → 말 목록 — 자동 말에서 뺍니다
add칸 → 말 목록 — 더합니다. clear 한 칸에도 들어갑니다(비운 뒤 고른 말만 두기)
weight · head_chars · min_count · min_distinct이 규칙만 값을 바꿉니다
enabledfalse 면 이 분류의 규칙을 만들지 않습니다
why · title_at_decision이유와 적을 당시 이름. 화면에서 이유를 비워 두면 “화면에서 고침 날짜”가 들어갑니다

칸 이름은 title_terms·head_terms·terms·filename·exclude 다섯입니다. 적용 순서는 clear → remove → add → weight → 숫자 칸입니다. settings 에는 conflict·defaults·signals·embed 만 적을 수 있습니다.

이렇게 나눕니다
· 회사에서 쓰는 말(모든 분류에 두루 통하는 같은 뜻 다른 말) → synonyms/doc_synonyms.local.yaml
· 이 분류에서만 칸을 비우거나 말을 빼고 더하는 결정 → doc_rule.local.yaml
· 규칙을 만들 때 “조정이 가리키는 분류가 없다”, “빼려는 말이 애초에 없다(사전이 바뀌어 이미 빠짐)”, “이름이 바뀌었다”를 알려 줍니다 — 그대로 두어도 되지만 정리하면 파일이 깔끔해집니다.

옛 모양 규칙에서 옮겨 오기

엔진은 옛 모양(손으로 고쳐 온) doc_rule.yaml 을 읽지 않습니다. 그런 파일이 있으면 화면의 업무분류 편집에 [🆕 새 방식으로 바꾸기]만 보이고, 이것이 같은 입력으로 새로 만든 규칙과 견줘 다른 부분만 조정으로 뽑습니다. 그 조정으로 옛 규칙이 재현될 때만 바꾸고, 옛 파일은 .bak 으로 남깁니다. 명령으로는 python scripts/migrate_doc_rule_local.py --old <옛 doc_rule.yaml> --policy <정책 폴더> 가 초안(doc_rule.local.yaml.draft)을 만듭니다.
