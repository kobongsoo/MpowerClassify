★ 엠파워 v11 암호화 문서 분류 2026-10-12 신규

엠파워 v11 저장소의 문서는 잠긴 채(암호화된 채) 디스크에 놓여 있습니다. 잠긴 파일을 그대로 읽으면 뜻 없는 글자뿐이라 분류할 수 없습니다. 그래서 열쇠를 함께 주면 분류 직전에 엠파워의 복호화 도구(removeenc.sh)로 한 건씩 풀어서 분류하고, 끝나면 풀린 파일을 바로 지웁니다.

금고에 비유하면 — 문서는 금고 안에 있고, mrk 가 그 금고의 열쇠입니다. 이 프로그램은 금고를 직접 열지 못합니다. 열쇠를 받아 엠파워의 도구에게 "이걸 열어 달라"고 부탁하고, 꺼낸 문서를 읽고 등급을 매긴 뒤 꺼낸 사본을 없앱니다. 금고 안의 원본은 건드리지 않습니다.
윈도우에서는 복호화 도구 위치를 꼭 알려 줘야 합니다. 실제로 문서를 푸는 것은 엠파워의 removeenc.sh 이고, 이 도구는 엠파워 서버(리눅스)에만 있습니다. 그래서 운영에서는 리눅스 서버에서 돌립니다(리눅스 가이드 ★ 엠파워 장). 윈도우에서는 --decrypt-cmd 로 "대신 풀어 주는 도구"를 지정해야 하며, 이 장의 예제에는 테스트용 중계 스크립트를 넣었습니다(아래 윈도우에서 시험하기).
두 판 모두 됩니다 — MpowerClassify-rs.exe(2026-10-12 판)와 MpowerClassify.exe(Python 판, 2026-10-13 판). 아래 예제의 실행 파일 이름만 바꾸면 같은 인자로 돕니다.

먼저 — 세 가지 경우만 기억하면 됩니다

경우무엇을 주나동작
① 여러 건 (권장)--filelist 목록의 각 줄에 mrk · enc_mode · zip_mode 를 적는다 열쇠가 적힌 줄만 풀어서 분류. 새 옵션이 필요 없습니다
② 한 건--file 에 --decrypt --mrk --enc-mode --zip-mode 를 붙인다그 파일을 풀어서 분류
③ 이미 풀린 파일아무것도 붙이지 않는다지금까지처럼 그대로 읽어 분류(복호화 없음)

한 건이 처리되는 순서 — 여러 건이어도 한 번에 한 건만 풀려 있습니다.

  1. 푼다 — 임시 폴더에 풀린 사본을 만든다(복호화 도구 호출)
  2. 확인한다 — 제대로 풀렸는지 본다(크기 · 파일 앞머리가 그 형식이 맞는지)
  3. 분류한다 — 본문을 읽고 등급·업무분류를 매긴다
  4. 지운다 — 풀린 사본을 지우고 다음 문서로 간다(실패해도, 중간에 멈춰도 지웁니다)

① 여러 건 — 목록(--filelist)에 열쇠를 적는다

목록은 한 줄에 문서 하나입니다. 아래 예는 세 가지 줄이 섞여 있습니다.

:: ① 잠긴 문서 — 열쇠 세 칸이 있으므로 풀어서 분류한다
{"path":"D:/저장소/F_f095df74.SMF","sfile_id":"SF_aaa","mrk":"(평문 MRK)","enc_mode":3,"zip_mode":0,"name":"워드문서.docx","size":28367}
:: ② 잠기지 않은 문서(둘 다 0) — 도구를 부르지 않고 그대로 읽는다
{"path":"D:/저장소/F_cb3fd2de.SMF","sfile_id":"SF_bbb","mrk":"(평문 MRK)","enc_mode":0,"zip_mode":0,"name":"압축묶음.zip","size":780690}
:: ③ 열쇠 칸이 없는 줄 — 풀지 않고 그대로 읽는다

줄의 모양에 따라 이렇게 움직입니다. 줄마다 따로 판단하므로 한 목록에 섞여 있어도 됩니다.

줄에 있는 칸동작
path · sfile_id 만풀지 않고 그대로 읽어 분류
+ mrk · enc_mode · zip_mode (둘 중 하나라도 0 이 아님)풀어서 분류

셋 중 일부만 있음 (예: mrk 만)그 문서만 실패로 남김 — info_incomplete

칸의 뜻

칸뜻엠파워 DB 의 어느 값인가
path이 프로그램이 도는 컴퓨터에서 본 잠긴 파일의 전체 경로VOL_PATH/RFILE_PATH/RFILE_NAME
sfile_id문서 번호. 결과의 doc_id 로 나옵니다SFILE_ID

size (선택)원래 파일 크기(바이트). 풀린 결과의 크기와 견줍니다LFILE_SIZE

이 밖의 칸(예: server_path)은 읽지 않고 무시합니다.

:: 나) 열쇠를 명령줄에 남기고 싶지 않을 때 — 환경변수로 준다
set CSOCLASSIFY_MRK=(평문 MRK)
MpowerClassify-rs.exe --file "D:\저장소\F_f095df74.SMF" --decrypt --enc-mode 3 --zip-mode 0 ^

:: 다) 풀어서 본문만 뽑아 보기(제대로 풀리는지 눈으로 확인)
MpowerClassify-rs.exe --text-only --file "D:\저장소\F_f095df74.SMF" --decrypt ^

--decrypt 는 --file 한 건에만 씁니다. 폴더(--dir)나 목록 실행에는 붙이지 않습니다 — 파일마다 열쇠가 다르기 때문에, 여러 건은 목록의 각 줄에 적는 것이 맞습니다.

③ 풀지 않는 경우

MpowerClassify-rs.exe --filelist filelist.jsonl --no-decrypt --simple --format jsonl --out result.jsonl

풀린 파일은 어디에 생기고, 언제 지워지나

풀린 파일의 경로를 부르는 쪽이 알 필요는 없습니다. 어디에 풀지는 이 프로그램이 스스로 정해서 복호화 도구에 알려 주고(removeenc.sh 의 -t 인자), 같은 자리에서 읽어 분류합니다. 그래서 목록이나 --file 에는 잠긴 파일의 경로만 주면 됩니다.

단계경로설명
바탕 폴더--decrypt-tmp → 환경변수 CSOCLASSIFY_DECRYPT_TMP → 시스템 임시 폴더 (윈도우는 %TEMP%)앞의 것이 있으면 그것을 씁니다
실행마다 한 폴더<바탕>\cso_dec_<프로세스번호>\이번 실행만의 작업장. 리눅스에서는 권한 700(다른 계정이 못 봄)
문서마다 한 폴더·한 파일…\000001\000001.docx이름은 순번, 확장자만 name 에서 가져옵니다

아래는 2026-10-13 에 이 배포 폴더에서 암호화 문서 9건을 돌리며 임시 폴더를 지켜본 실제 결과입니다. 한 번에 한 건만 있다가 사라집니다.

C:\Users\(계정)\AppData\Local\Temp\cso_dec_17908\
   000001\000001.pdf     1,226,050 B   ← 1번째 문서를 분류하는 동안만 있다
   000002\000002.hwpx       54,987 B   ← 2번째 문서. 이때 000001 폴더는 이미 지워졌다
   000003\000003.doc       146,944 B
   …
   000008\000008.txt           215 B
   000010\000010.docx       28,367 B   ← 9번이 없는 것은 그 문서가 잠기지 않은(0,0) zip 이라 도구를 부르지 않아서
(실행이 끝나면 cso_dec_… 폴더 자체가 없어진다)

--file 한 건을 --decrypt 로 돌려도 같습니다 — cso_dec_<번호>\000001\000001.docx 가 생겼다가, 분류가 끝나면 폴더째 사라집니다(지켜본 실행에서는 생성부터 삭제까지 약 1초).

언제무엇을 지우나
문서 한 건의 분류가 끝나면그 문서의 폴더(000001)를 바로 지웁니다 — 실패한 문서도 지웁니다
실행이 끝나면cso_dec_<번호> 폴더를 통째로 지웁니다. 오류로 멈추거나 Ctrl+C 로 끊어도 지웁니다
강제 종료돼 지울 기회가 없었으면다음 실행이 시작할 때 주인 없는 cso_dec_* 폴더를 치웁니다
왜 문서마다 폴더(000001 · 000002 …)를 두나 — 문서 하나에서 나온 것을 한 번에, 빠짐없이 지우기 위해서입니다. 풀린 문서가 압축 파일이면 그 안의 문서들을 다시 펼치므로 한 문서에서 파일이 여러 개 나옵니다. 복호화 도구가 대상 경로 옆에 중간 파일을 남길 수도 있습니다. 폴더로 묶어 두면 "그 폴더를 지운다" 한 번으로 끝나고, 하나라도 빠뜨려 풀린 원문이 남는 일이 없습니다.
왜 이름이 순번인가 — 문서 이름 자체가 민감할 수 있고(예: 구조조정_대상자.xlsx), 공백·괄호·특수문자가 든 이름은 도구에 넘기는 경로를 깨뜨릴 수 있어서입니다. 이 임시 경로는 결과에도 로그에도 나오지 않습니다 — 결과의 file 은 준 경로 그대로입니다.

--decrypt-cmd · --decrypt-tmp — 언제 주나

① --decrypt-cmd (복호화 도구 위치) — 도구는 인자 → 환경변수 CSOCLASSIFY_DECRYPT_CMD → 기본 위치 순으로 찾습니다.

실행하는 곳--decrypt-cmd이유
윈도우 PC (시험)꼭 준다 기본 위치도, 엠파워 복호화 도구도 윈도우에는 없습니다. 중계 스크립트를 줍니다(아래 윈도우에서 시험하기)
엠파워 서버 (운영)필요 없다 기본 위치 /MOCOMSYS/MpowerScript/removeenc/removeenc.sh 에 도구가 있습니다

도구가 없거나 실행 권한이 없으면 문서를 한 건도 읽지 않고 1015 decrypt_cmd_missing(종료코드 3)으로 멈추므로, 경로가 틀렸는지는 바로 알 수 있습니다.

② --decrypt-tmp (풀린 사본을 둘 곳) — 주지 않아도 됩니다(시스템 임시 폴더를 씁니다). 다만 운영에서는 주기를 권합니다.

:: 풀린 사본을 둘 폴더를 따로 정한다(없으면 만들어 줍니다)
MpowerClassify-rs.exe --filelist filelist.jsonl --decrypt-tmp D:\temp\cso ^
    --simple --format jsonl --out result.jsonl --json-errors ^
    --decrypt-cmd sample\enc_test\relay_removeenc.cmd

:: 매번 주기 번거로우면 환경변수로 한 번 정해 둔다
set CSOCLASSIFY_DECRYPT_TMP=D:\temp\cso

운영(리눅스 서버)에서는 메모리 디스크 /dev/shm 을 주기를 권합니다 — 풀린 원문이 디스크에 닿지 않습니다 (리눅스 가이드 ★ 엠파워 장).

결과 읽기 — 잘 풀렸을 때

{"file":"D:/저장소/F_872c8944.SMF","hash":"b7918ff0…","doc_id":"SF_aaa","doc_id_source":"sfile_id",
 "name":"한글문서.hwp","grade":"S","doctype":[], … ,"meta":{"ts":"2026-10-12 17:12:11","decrypted":true}}
칸뜻
file준 경로 그대로(잠긴 파일의 경로). 임시 폴더 경로는 결과에 나오지 않습니다
hash풀린 내용의 지문(SHA-256). 원본 문서의 지문과 같으면 제대로 풀린 것입니다
name준 원래 이름(줬을 때만 나옵니다)
meta.decryptedtrue = 도구로 풀어서 읽었다. 그대로 읽은 문서에는 이 칸이 없습니다

결과 읽기 — 풀지 못했을 때

풀지 못했거나 풀린 결과가 수상하면 분류하지 않습니다. 등급 없이("grade":null) 이유만 남기고 다음 문서로 넘어갑니다. 아래는 열쇠를 한 글자 틀리게 줬을 때 실제로 나온 모양입니다.

{"file":"…/F_872c8944.SMF","doc_id":"SF_…","name":"한글문서.hwp","grade":null,
 "error":{"stage":"decrypt","kind":"decrypt_failed","detail":"signature_mismatch","rc":0,
          "reason":"hwp 파일인데 앞머리가 OLE 형식이 아닙니다 — 열쇠(mrk)와 모드가 맞는지 확인하세요"}}

왜 실패했는지는 error.detail 로 가립니다.

★ 먼저 해 보기 — 서버를 띄워 두고 파일을 하나씩 분류하기 2026-10-12 신규

주의 — 네 배포본 공통
· 규칙셋 cso_rule.yaml 과 모델은 실행파일과 같은 폴더 기준으로 찾습니다. 규칙셋이 없으면 "어디에 두라"는 안내를 내고 종료(코드 3 · 2001)합니다.
· 업무분류 축은 자동 생성된 doc_rule.yaml 이 있으면 켜집니다(분류체계가 그 안에 있음) 따로 떨어진 분류체계 파일(옛 doc_taxonomy.yaml)은 읽지 않음. 재료 파일(체계 JSON·본보기·사전·조정 파일)은 판정에 쓰지 않지만, 곁에 없으면 돌 때마다 “입력이 없어짐” 경고가 나고 현장에서 규칙을 다시 만들 수 없으니 함께 둡니다.
· 모델이 없으면 전파만 빠지고 규칙 등급은 그대로 나갑니다(종료코드 2 · 3002). 배포본에는 e5-small-ko 만 들어 있습니다 — 다른 모델은 models\<별칭>\ 에 넣습니다(5장).
· Python 판의 _internal\ 은 exe 와 한 세트라 지우거나 따로 옮기면 실행이 안 됩니다.
· 사이냅(synap\)은 선택입니다 — 자체 파서가 1차이고 사이냅은 폴백 전용이라 폴더째 없어도 동작합니다. 두려면 synap\windows\snf_exe.exe 자리에 둡니다(synap\ 바로 아래가 아님).

file글자분류한 문서의 경로 — 준 경로 그대로. 압축 안의 문서는 압축경로/안쪽경로

doc_id글자 · null엠파워 문서 번호(sfile_id). --filelist 로 넘겼을 때만 채워집니다. null 이면 매핑 테이블에 넣지 말고 hash 로 가리세요(프로그램이 번호를 지어내지 않습니다)

doctype글자 배열업무분류 ID 들. 못 정했으면 []. 이 칸이 아예 없으면 업무분류 축이 꺼진 실행입니다(doc_rule.yaml 이 없거나 --axis security)
error글자 또는 묶음그 문서를 못 읽었을 때만 붙습니다. 추출 실패는 이유 문장, 복호화 실패 · 파일 없음 등은 {"stage","kind","detail","reason"} 묶음

grade 가 null 인 것과 error 가 붙은 것은 다릅니다. null 만 있으면 "읽었지만 등급을 못 정했다"(→ 검토), error 가 있으면 "아예 못 읽었다"(→ 원본 확인 · OCR), excluded 면 "범위 밖"(→ OCR 대상으로 따로 모음)입니다.

--emb-test Rust 판만—Rust 판 도움말(⑪)에 '받기만 하고 아무 일도 하지 않는 인자'로 올라 있습니다. 평소에는 쓸 일이 없습니다
청킹(chunking)이란? 긴 문서를 임베딩 모델이 한 번에 처리할 수 있는 크기로 잘라, 각 조각(청크)을 임베딩한 뒤 평균내어 문서 1개의 벡터를 만듭니다. 두 값으로 조절합니다:
  • --max-tokens — 청크 1개의 최대 토큰 수(기본 512, e5 모델의 최대 시퀀스 길이). 크게 하면 청크 수↓·문맥↑, 작게 하면 더 잘게 나뉨.
  • --overlap — 인접 청크가 겹치는 토큰 수(기본 32). 청크 경계에서 문맥이 끊기지 않도록 조금 겹칩니다.
:: 청크 크기·겹침을 직접 지정(생략하면 512 / 32)
MpowerClassify.exe --file "문서.hwp" --max-tokens 256 --overlap 32

추출 본문을 파일로 남기기 — --textsave

분류하면서 문서에서 뽑아낸 본문을 폴더에 남깁니다. "왜 이 문서가 C 인가"를 사람이 직접 읽어 확인하거나, 규칙을 고칠 때 문서를 다시 파싱하지 않고 같은 본문으로 실험할 때 씁니다.

MpowerClassify.exe --dir "D:\분류함" --textsave "D:\파싱"
D:\파싱\
  ├ 567b4e6e3af751a1…c6769e08.txt   ← 파일명 = 원본의 SHA-256 (레코드의 hash 와 같은 값)
  ├ _index.jsonl                     ← 어느 원본인지는 여기서 본다
  └ _README.md                       ← 취급 주의 안내
이 옵션은 개인정보를 평문으로 디스크에 복제합니다. 분류는 원래 본문을 디스크에 남기지 않습니다 — 이 옵션은 그 방어를 여는 문입니다.
보안등급 C(기밀) 문서의 본문도 걸러내지 않고 그대로 남습니다. 등급으로 거르면 "왜 C 인가"를 확인한다는 목적 자체가 깨지기 때문입니다.
그래서 기본은 꺼짐이고, 폴더를 반드시 지정해야 하며(생략 시 기본 폴더 같은 것은 없습니다), 실행할 때 화면에 경고 한 줄이 나갑니다.
무엇어떻게
파일 이름 원본 파일의 SHA-256. 결과 레코드의 hash 칸과 같은 값이라 결과 한 줄에서 그 문서의 본문으로 바로 갈 수 있습니다. 길이가 64자로 고정이라 긴 경로·한글 파일명 문제도 없습니다
같은 문서가 여러 개면 .txt 는 한 개만 생깁니다(내용이 같으므로). 요약이 내용이 같은 N건은 한 파일로 합쳐졌습니다 로 알려 주니, 파일 수가 문서 수보다 적어도 빠진 것이 아닙니다
어느 시점의 본문 정제·절단까지 끝난 것 — 도구가 실제로 보고 판정한 그 텍스트입니다. 그래서 --max-text-chars 로 잘린 문서는 뒤가 없습니다(색인의 truncated 가 true)
본문이 없으면 파일을 만들지 않습니다. 0바이트 파일을 남기면 "저장됐다"로 오해되기 때문입니다. 레코드에 text_saved 키가 없는 것으로 구분합니다
저장이 실패하면 분류는 그대로 끝까지 갑니다 — 등급도 종료코드도 바뀌지 않습니다. 대신 레코드에 text_save_error, 요약에 저장실패=N 이 남습니다

색인 _index.jsonl — 한 줄에 한 문서입니다. hash 이름만으로는 사람이 못 알아보므로 이것이 원본과 잇는 유일한 다리입니다.

{"hash":"567b4e6e…","txt":"567b4e6e….txt","file":"D:/분류함/01_제품매뉴얼/MCCS 이중화 테스트 시나리오.xlsx",
 "doc_id":null,"chars":18452,"truncated":false,"ts":"2026-09-07 15:02:11"}

같은 문서가 여러 경로에 있으면 .txt 는 하나지만 색인 줄은 경로마다 쌓입니다 — 중복 제거의 이득은 챙기면서 "어느 경로들에서 나왔는지"는 잃지 않습니다. 같은 폴더에 다시 돌리면 줄이 이어붙습니다(어제 색인을 오늘 실행이 말없이 지우는 것이 더 위험하므로). 새로 시작하려면 폴더를 비우세요. doc_id 는 --filelist 로 sfile_id 를 얻은 문서에만 값이 있습니다.

두 판이 같은 폴더를 쓰면 안 됩니다. 저장하는 것은 원본이 아니라 추출한 본문이고, 파이썬 판(사이냅·하이브리드)과 Rust 판(순수 Rust 파서)은 같은 문서에서도 본문이 다르게 나옵니다(실측: 같은 PPTX 가 9,312 / 9,330 바이트). 섞이면 남의 본문을 자기 것인 양 가리키게 되므로, 같은 이름인데 내용이 다르면 덮지 않고 오류로 알립니다 — 저장실패=N 이 뜨면 폴더를 나누세요.

규칙셋 미리 검사 — --check-rules

규칙셋을 고친 뒤 실제 스캔을 돌리기 전에 안전한지 확인합니다. 문서는 한 건도 읽지 않습니다. 두 축을 모두 검사합니다(업무분류 파일이 옆에 있으면 그것도 함께).

MpowerClassify.exe --check-rules --cso-rules cso_rule.yaml

이상이 없으면 축별로 건수를 요약하고 0 으로 끝납니다:

[MpowerClassify] 규칙셋 정상: ...\cso_rule.yaml
  version=cso-2026.08.3  등급=O/S/C
  regex_pii=20 · pii_combos=5 · keywords=9 · sensitive=7 · stamps=3
[MpowerClassify] 업무분류 규칙셋 정상(자동 생성 — 분류체계 내장): ...\doc_rule.yaml
  version=doctype-gen-b29e4fa53046  conflict=all  규칙=22건(활성 22건)  노드=28개  최상위=7개

Rust 판은 같은 내용을 “업무분류(doctype) 축 정상” 한 덩어리로 보여 줍니다(줄 모양만 다르고 종료코드는 같음).

규칙 파일이 없으면 업무분류 축을 쓰지 않는다고 알리고 0 으로 끝납니다. 옛 모양 규칙 파일이면 실제 분류와 똑같이 [G0] 로 4 를 냅니다:

[MpowerClassify] 업무분류 규칙셋 없음 → 업무분류(doctype) 축 미사용: ...\doc_rule.yaml
  규칙은 --build-doc-rule 로 만듭니다.

문제가 있으면 위반을 전부 모아 보여 주고 4 로 끝납니다.

7 업무분류(doctype) 축

보안등급 축(C/S/O)에 더해, 문서가 무슨 업무 문서인지(계약서·회의록·요구사항정의서 …)를 같이 판정하는 두 번째 축입니다. 분류 기준은 MpowerV11 의 문서분류체계(DOC_CLASSIFICATION)를 그대로 내려받은 스냅샷이라, DB 의 분류 트리와 같은 이름·같은 ID로 결과가 나옵니다.

두 축의 차이 — 왜 따로 다루나

보안등급 축 security업무분류 축 doctype
값의 성격서열이 있음 (O < S < C)서열 없는 분류 트리(형제끼리 우열 없음)
결과 개수항상 1개(단일 등급)여러 개 가능(한 문서가 계약서이면서 법무 문서)
충돌 처리max 고정 — 가장 민감한 쪽 채택(안전측)all(전부) 또는 top_n:N(상위 N개) — 선택 가능
실행 시 변경불가 — --conflict security=… 는 오류(코드 4)가능 — --conflict doctype=top_n:3
못 정했을 때grade: null(보류) → 검토 대상values: [](빈 목록) — 정상

보안등급은 낮게 나오는 실패가 사고라서 안전측 고정이 유일하게 정당합니다. 반면 업무분류는 "계약서이면서 동시에 법무 문서"가 둘 다 맞는 상황이라 하나로 줄일 이유가 없어, 전략을 고를 수 있게 열어 뒀습니다.

  • 규칙 파일을 손으로 고치면 “만들어진 뒤 손으로 고쳐졌습니다 — 다음에 다시 만들면 사라집니다” 경고가 납니다.
  • 만든 뒤 재료(체계 JSON·사전·본보기·조정 파일)가 바뀌거나 없어지면 분류할 때마다 “규칙을 만든 뒤 입력이 바뀌었습니다: … — --build-doc-rule 로 다시 만드세요” 가 납니다.
  • 회사마다 다른 결정은 doc_rule.local.yaml(분류별 조정)과 synonyms/doc_synonyms.local.yaml(회사 말)에 둡니다. 다시 만들어도 사라지지 않습니다.
  • 같은 입력이면 두 판이 만든 파일이 글자까지 같습니다.
자세한 모양은 doc/DOC_Rule.html 2장·13장. 손으로 고쳐 온 옛 모양 규칙에서 옮기려면 화면의 [새 방식으로 바꾸기]를 씁니다.

규칙 한 건의 모양 — doc_rule.yaml

conflict: all                  # 축 전체의 충돌 전략: all | top_n(+ n)

doctype_rules:
- id: dt_dc_006_001            # 규칙 식별자(중복 불가)

  title: 계약서                 # 분류 제목·경로·조상 — 분류체계 역할
  path: 법무/규정 > 계약서
  path_ids: [DC_006, DC_006_001]
  weight: medium               # high | medium | low — 신뢰도로 환산
  title_terms: ["계약서"]          # 첫 줄(제목)에 있으면 매칭 — 가장 강한 증거
  head_terms: ["계약기간"]         # 앞 head_chars 자(표제부)에 있으면 매칭
  terms: ["용역계약", "계약조건"]   # 본문 어디든 있으면 매칭 — 가장 약한 증거
  exclude: ["계약해지 안내"]        # 이 말이 있으면 매칭 취소(오탐 방지)
  filename: ["계약서"]             # 파일 이름에 있으면 매칭

신호 4가지와 그 신뢰도

규칙이 문서의 어디에서 맞혔느냐에 따라 확신이 다릅니다. 그 값을 곱해 쌓는 방식이라 (noisy-OR: 1 - Π(1-c)) 근거가 늘수록 점수가 오르되 1을 넘지 않습니다.

신호규칙 필드어디를 보나highmediumlow
titletitle_terms첫 비어있지 않은 줄 사람이 일부러 적은 이름이라 가장 셈0.800.650.50
headhead_terms앞 head_chars(기본 400)자0.700.550.40
namefilename폴더를 뺀 파일 이름 weight 를 보지 않아 세 칸이 같음0.300.300.30
bodyterms문서 전체 단독으로는 후보가 못 됨0.250.150.10

예) title(0.65) + name(0.30) → 1 - 0.35×0.70 = 0.755. t_low(기본 0.35) 이상이면 그 분류가 붙습니다.

form:·paths:·structure: 필드는 쓰지 않습니다 — 규칙에 남아 있으면 조용히 무시하지 않고 검증이 "더 이상 쓰지 않는 필드입니다"로 알려 줍니다 — 지우세요.

신뢰도를 직접 조정하기 — signals:

위 표의 숫자는 실측 전 잠정치라 현장에서 다시 맞출 값입니다. 재빌드 없이 바꿀 수 있습니다 — 규칙 파일이 자동 생성이므로, 값은 doc_rule.local.yaml 의 settings.signals 에 적고 규칙을 다시 만듭니다.

signals:
  title: {high: 0.80, medium: 0.65, low: 0.50}
  head:  {high: 0.70, medium: 0.55, low: 0.40}
  body:  {high: 0.25, medium: 0.15, low: 0.10}
  name:  {high: 0.30, medium: 0.30, low: 0.30}
규칙내용
일부만 적어도 된다 title: {high: 0.90} 한 줄이면 그 칸만 덮어쓰고 나머지는 기본값입니다. "title 만 올려 보자"가 두 줄로 끝나야 실제로 시도됩니다
블록이 없으면 그대로 이 블록을 적지 않으면 위 표의 기본값으로 돕니다
잘못 적으면 막힌다 0.0~1.0 밖, 숫자가 아닌 값, 모르는 신호 이름(titel 같은 오타), 모르는 등급 키는 로드 시점에 거절됩니다(--check-rules · 화면 저장, 종료코드 4). 조용히 무시하면 "고쳤는데 왜 안 바뀌지"를 혼자 헤매게 됩니다
name 은 세 값이 같아야 이 신호만 규칙의 weight 를 보지 않고 medium 값만 씁니다 — high 를 다르게 적어도 효과가 없어서, 아예 막고 그 사유를 알려 줍니다
버전은 저절로 바뀝니다 값을 바꾸면 판정이 바뀝니다. 자동 생성 규칙의 version 은 내용 지문이라 값이 바뀌면 판도 바뀌어, 결과만 보고도 "어느 기준으로 매긴 값인지" 되짚을 수 있습니다

두 판이 같은 표를 읽어 같은 점수를 냅니다. 값과 설명은 doc_rule_template.yaml 주석에도 함께 있습니다.

결과 — doctype 축

// 등급 축(security)과 나란한 최상위 칸입니다 — 한쪽이 다른 쪽 안에 있지 않습니다.
"doctype": {
  "values": [
    { "dc_id": "DC_006_001",
      "path": "법무/규정 > 계약서",            // 사람이 읽는 전체 경로
      "path_ids": [ "DC_006", "DC_006_001" ],  // 뿌리→말단 노드 ID
      "confidence": 0.6,
      "from": [ "name" ],                      // 무엇이 이 라벨을 냈나(title/head/body/name/embed)
      "stage": "rule",                         // rule | embed | both
      "signals": { "name": { "c": 0.3, "terms": [ "계약서" ] } } }   // 신호별 기여도 + 근거
  ],
  // 아래 세 칸은 '값이 있을 때만' 붙습니다 — 없으면 기본이라는 뜻입니다.
  "truncated": 2,           // top_n 으로 잘려나간 후보 수. 0이면 칸 자체가 없음
  "conflicts": [ … ],       // 서로 다른 큰 갈래가 동시에 제안된 경우의 경고. 없으면 칸 없음
  "strategy": "top_n:3",    // --conflict 로 덮어썼을 때만. 없으면 규칙 파일이 정한 대로
  "embed": { … }            // 전파가 돌았을 때만(기준 문서 비교 근거)
}
값이 있을 때만 붙는 칸
· truncated — 0이면 생략. 없으면 "아무것도 안 잘림"입니다. 잘렸을 때는 반드시 보입니다.
· conflicts — 비었으면 생략(같은 이유).
· strategy — --conflict 로 덮어썼을 때만. 안 덮어썼으면 규칙 파일에 적힌 값 그대로입니다. 어느 규칙 파일이었는지는 meta.doctype_rule_version 이 가리킵니다.
축이 꺼지면 doctype 키 자체가 없습니다(빈 값이 아니라 키 부재). "values": [] 는 "축은 돌았는데 아무것도 못 찾음", 키가 아예 없으면 "이번 실행은 축을 쓰지 않음"입니다. 두 상황은 대응이 다르므로(규칙 보강 vs 파일 배치) 구분해 두었습니다. 소비 측 코드는 if "doctype" in rec 로 먼저 확인하세요.

조상 흡수 — 왜 상위 분류가 사라지나

한 문서가 "법무/규정"(상위) 과 "법무/규정 > 계약서"(하위) 에 동시에 걸리면, 더 구체적인 하위 노드만 남기고 조상은 지웁니다. "계약서"라고 이미 말한 마당에 "법무 문서"를 덧붙이는 건 정보가 없고, 집계할 때 같은 문서를 두 번 세게 만들기 때문입니다. 형제 관계(다른 가지)는 서로 상관없으므로 둘 다 남습니다.

충돌 전략 — 후보가 여럿일 때

전략동작지정

--conflict 값은 규칙파일에 적었을 때와 완전히 같은 검사를 통과해야 합니다 — doctype=max(없는 전략), doctype=top_n(n 누락), doctype=top_n:0 은 모두 종료코드 4 입니다.

--axis doctype 은 자동 생성 doc_rule.yaml(분류체계 내장)이 반드시 있어야 합니다. 없으면 "축을 건너뜀"이 아니라 종료코드 3으로 멈춥니다 — 사용자가 그 축을 명시적으로 요구했는데 조용히 빈 결과를 내면 "분류할 게 없었다"로 오해되기 때문입니다.

규칙 없이 기준 문서로만 — --doctype-vector-only

업무분류의 규칙만 끄고, 기준 문서(class_seed.jsonl)와의 유사도로만 분류합니다. 규칙을 아직 못 만든 조직이나, 규칙 없이 얼마나 잡히는지 재 보고 싶을 때 씁니다.

옵션끄는 것남는 것
--doctype-vector-only 업무분류 규칙만(doc_rule.yaml 의 규칙 목록) 보안등급 축은 그대로 돕니다. 규칙 파일의 embed 임계값 · conflict 전략 · defaults 는 그대로 씁니다
--axis doctype 보안등급 축 전체(PII 검출까지) 업무분류만

둘은 끄는 대상이 다릅니다. "업무분류를 벡터로만 하고 보안등급은 아예 안 함" 이라면 둘을 같이 줍니다.

:: 업무분류를 기준 문서 비교로만 · 보안등급은 계산 안 함
MpowerClassify.exe --dir "D:/문서" --doctype-vector-only --axis doctype --seeds class_seed.jsonl
--seeds 를 빠뜨리면 결과가 통째로 0건입니다. 비교할 기준이 없으면 붙을 수가 없고, 기준이 없으면 임베딩 자체를 건너뜁니다. exe 옆에 class_seed.jsonl 이 있으면 --seeds 없이도 자동으로 찾습니다 — 파일 이름이 정확히 그것이어야 합니다.

규칙을 끄면 1차 스캔이 빈손이 되므로, 화면에 [T12] DC_00x 를 참조하는 규칙이 없습니다 경고가 분류마다 한 줄씩 나옵니다 — 이 모드에서는 정상입니다. 붙은 라벨은 stage:"embed" 이고 신뢰도는 defaults.embed_cap(기본 0.65)에서 막힙니다 — 근거를 댈 수 있는 규칙 후보보다 세면 안 되기 때문입니다.

임베딩 전파(embed) — 규칙이 못 잡은 문서 분류

보안등급 축과 마찬가지로, seed 저장소가 있으면 업무분류도 임베딩 유사도로 전파합니다. 두 축의 전파 방식은 다릅니다:

보안등급업무분류
대상보류(grade=null) 문서만 구제모든 문서 — 이미 라벨이 있어도 후보를 더한다
득표 임계0.70 (이웃의 70% 이상이 같은 등급)0.25 (라벨마다 따로 계산)
이유등급은 하나뿐이라 다수결이 성립표가 동시에 맞는 여러 라벨로 갈리므로 같은 잣대를 쓰면 아무것도 못 넘김

전파로 붙은 라벨은 from 에 "embed" 가 들어갑니다. 이웃 문서와 거의 같은 문서(near-dup)면 그 문서의 라벨 집합 전체를 그대로 물려받고, 그렇지 않으면 라벨별로 따로 신뢰도를 계산합니다. 전파 후에도 조상 흡수와 충돌 전략은 다시 적용되므로, 규칙과 임베딩이 섞여도 결과 형태는 같습니다. 실행하면 화면에 [전파][업무분류] seed=… embed기여=… 벡터없음=… 한 줄이 나옵니다.

전파하려면 그 문서의 벡터가 있어야 합니다 — 임베딩은 느린 단계라 필요한 문서에만 겁니다. 기본(--embed-needed 포함)에서 벡터를 만드는 대상은 아직 못 정한 축이 하나라도 있는 문서입니다:
· 보안등급이 보류이거나 seed_eligible 이거나,
· 업무분류 라벨이 하나도 안 붙은 문서
--rule-only 는 임베딩을 아예 안 하므로 전파도 하지 않습니다.

seed 만들기 — 확정된 문서를 기준 문서로 등록

기준 문서(seed)는 "이 문서는 이 등급·이 분류가 맞다"고 사람이 확정한 문서의 벡터와 라벨입니다. 저장소(class_seed.jsonl)는 문서 한 건이 한 줄인 JSONL 이고, 엔진이 읽는 칸은 셋입니다.

칸필요한 축값
vector둘 다 필수그 문서의 임베딩 벡터 — 분류에 쓰는 --model 과 같은 모델로 만든 것이어야 합니다(차원이 다르면 1013)
doctype업무분류dc_id 문자열 배열(예: ["DC_002_001_001"]). 여러 개 가능
grade보안등급"C"/"S"/"O"

두 축은 서로 독립적으로 같은 파일을 읽습니다 — 한 줄에 grade 와 doctype 을 둘 다 넣어도 되고 한쪽만 넣어도 됩니다. 한 줄의 전체 모양(스키마 v3)은 11장에 있습니다. 옛 형식(labels.doctype)의 파일도 그대로 읽습니다.

:: 손으로 줄을 만들지 말고 --seed-add 로 등록합니다 — 벡터·지문(hash)·기록을 도구가 채웁니다
MpowerClassify.exe --seed-add "요구사항정의서_확정본.hwp" ^
    --seed-grade S --seed-doctype DC_002_001_001 ^
    --seed-reviewer "홍길동" --seeds "class_seed.jsonl"

:: 다음 실행부터 이 seed 와 닮은 문서가 자동으로 같은 분류를 받는다
MpowerClassify.exe --dir "D:\collected" --seeds "class_seed.jsonl" --format jsonl --out result.jsonl

인자와 목록 형식은 5장 '기준 문서 등록'. 화면(문서자동분류 UI)의 문서함에서 등록해도 같은 파일에 같은 모양으로 쌓입니다. 규칙이 고신뢰로 분류한 문서에서 업무분류 seed 를 한꺼번에 뽑으려면 --make-doctype-seeds(Python 판).

dc_id 는 규칙 파일의 node·path 에서 확인합니다. 스냅샷에 없는 dc_id 를 적으면 그 후보는 조용히 무시됩니다(삭제된 노드를 가리키는 낡은 seed 가 결과를 오염시키지 않도록). --check-rules 로 노드 목록과 seed 건수를 함께 확인할 수 있습니다.

9 실행 예시 — 하려는 일별

줄 끝의 ^ 는 줄 잇기입니다(한 줄로 써도 됩니다). 경로에 공백 · 한글 · 괄호가 있으면 큰따옴표로 감쌉니다.

분류하기

:: 1) 연동 표준형 — 다른 프로그램에서 부를 때

11 중요: Seed 관리와 Drift 방지

[중요] 이 섹션은 seed 파일 관리 시 절대 규칙입니다. 지키지 않으면 자동 분류 결과가 시간이 지나며 오염될 수 있습니다.

핵심 원칙: Drift 방지

임베딩 기반 전파는 "후보"를 만들 뿐 최종 기준이 아닙니다. 전파로 붙은 등급을 다시 seed로 사용하면 초기 오분류가 스스로를 강화하며 코퍼스 전체로 번진다는 원칙이 있습니다. 이를 Drift라 합니다:

[원칙] 전파로 붙은 라벨은 절대 seed 가 되지 않는다.
seed 자격은 다음 두 경로뿐이다:
(a) 1단계 규칙 고신뢰만 (rule-based confidence ≥ threshold)
(b) 사람이 수동으로 확정한 것

이 규칙이 깨지면 초기 오분류가 스스로를 강화하며 코퍼스 전체로 번진다.
