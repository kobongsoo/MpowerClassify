① 표 안의 개인정보를 놓치던 것 — Rust 판

HTML 표에서 같은 행의 셀 값이 구분자 없이 이어붙고 있었습니다.

<td>900101-1234568</td><td>010-1234-5678</td>
   →  900101-1234568010-1234-5678        // 이어붙음

이러면 검출기의 경계 검사(앞뒤가 숫자면 거부)에 걸려 두 값이 함께 사라집니다. 파이썬 판은 2026-09-04 에 고쳤는데 Rust 판이 그 수정을 못 받은 채였습니다. 실측: ip_address 7↔5 · biz_reg_no 8↔6 · phone_mobile 7↔8 로 두 판이 갈려 있었고, 지금은 전 건 일치합니다.

② 머리말·꼬리말을 안 읽던 것 — 파이썬 판, docx

'대외비' 스탬프와 회사명은 본문이 아니라 머리말·꼬리말에 찍히는 일이 훨씬 흔합니다. 파이썬 판이 그 자리를 안 읽어, 그런 문서는 스탬프가 없는 것처럼 보였습니다(Rust 판은 읽고 있었습니다). 본문 뒤에 잇습니다 — 앞에 붙이면 '앞 400자(표제부)'를 보는 규칙이 가리키는 범위가 통째로 밀려, 이 변경과 상관없는 문서의 판정까지 흔들립니다.

③ 업무분류 2단계가 꺼져 있던 것 — Rust 판

어떤 문서에 벡터를 만들지 고르는 조건 중 하나(seed_eligible)를 레코드의 옛 자리에서 읽고 있어 언제나 거짓이었습니다. 그래서 규칙이 고신뢰로 찍어 준 문서가 임베딩에서 통째로 빠지고, 업무분류 2단계(기준 문서 비교)가 사라졌습니다. 오류도 경고도 없이 값만 조용히 뒤집히는 종류였습니다. 실측(사내 문서 18건): 세 문서의 업무분류 확신이 파이썬 1.0 대 Rust 0.755·0.906·0.98 로 갈려 있었습니다. 라벨은 우연히 같았고 숫자만 달랐는데, 그 숫자가 seed 승격 임계값(0.85)을 사이에 두고 있어 같은 문서가 판에 따라 기준 문서가 되기도, 안 되기도 했습니다.

④ HTML 에서 두 판이 다른 글자를 읽던 것 — 양쪽

같은 HTML 문서인데 두 판이 뽑아내는 본문이 달랐습니다. 세 군데였습니다.

  • <pre> 를 문단 경계로 잘못 봄(Rust) — 태그 이름 뒤 경계를 안 봐서 <pre> 가 p+re 로 잡혔습니다. pre·param·picture·progress·track·thead·link 가 걸렸습니다.
  • 이름 엔티티를 안 풂(Rust) — &mdash;·&middot; 가 본문에 글자 그대로 남았습니다(doc/ 의 HTML 에만 11곳). 이제 HTML5 이름 엔티티 2,125개를 파이썬과 같은 표로 전부 풉니다. &nbsp; 도 일반 공백이 아니라 파이썬과 같은 U+00A0 이 됐습니다.
  • <br/> 이 줄바꿈 두 개(파이썬) — 같은 뜻인 <br> 은 하나였습니다. 파이썬 판 안에서도 표기에 따라 결과가 달랐던 셈이라 이쪽을 고쳤습니다.

등급이 뒤집힌 문서는 없었지만 PII 좌표가 어긋났고, 규칙 용어가 그 경계에 걸리면 판정까지 갈릴 수 있는 자리였습니다. 실측(doc/ 11건 · 사내 문서 18건): 고친 뒤 두 판의 추출 본문이 글자 하나까지 같습니다. 파이썬 판은 변경 전후로도 등급·신호·PII 가 전 건 그대로였습니다.

두 판이 이제 같은 답을 냅니다 — 사내 문서 18건과 doc/ 11건을 두 판으로 돌려 레코드 전체를 통째로 견줬고, ts(줄마다 찍는 시각)와 윈도우 경로 구분자를 뺀 나머지가 전 건 일치했습니다. 추출 본문도 글자 하나까지 같습니다. 이 비교는 회귀 시험으로 고정해 뒀습니다 — 다시 갈리면 시험이 먼저 실패합니다.

· 업무분류 축은 자동 생성된 doc_rule.yaml 이 있으면 켜집니다(분류체계가 그 안에 있음) 2026-09-22 변경 — 따로 떨어진 분류체계 파일(옛 doc_taxonomy.yaml)은 읽지 않음. 재료 파일(체계 JSON·본보기·사전·조정 파일)은 판정에 쓰지 않지만, 곁에 없으면 돌 때마다 “입력이 없어짐” 경고가 나고 현장에서 규칙을 다시 만들 수 없으니 함께 둡니다.
· 모델이 없으면 전파만 빠지고 규칙 등급은 그대로 나갑니다(종료코드 2 · 3002). 배포본에는 e5-small-ko 만 들어 있습니다 — 다른 모델은 models\<별칭>\ 에 넣습니다(5장).
· Python 판의 _internal\ 은 exe 와 한 세트라 지우거나 따로 옮기면 실행이 안 됩니다.
· 사이냅(synap\)은 선택입니다 2026-08-26 부터 — 자체 파서가 1차이고 사이냅은 폴백 전용이라 폴더째 없어도 동작합니다. 두려면 synap\windows\snf_exe.exe 자리에 둡니다(synap\ 바로 아래가 아님).

3 실행 모드

여러 문서를 처리한다면 먼저 1 빠른 시작의 “한 번에 묶어서 부르세요” 를 읽으세요 — 파일마다 프로세스를 띄우면 5배 넘게 느려집니다.

모드는 플래그로 정해집니다. 아무 모드 플래그가 없으면 C/S/O 분류가 기본입니다. 임베딩 벡터만 필요하면 --embed, 추출 텍스트만 필요하면 --text-only 를 줍니다.

① 분류 (기본) — 모드 플래그 불필요

두 축을 한 번에 분류합니다(2026-08-25). 문서를 한 번 읽어 보안등급 축(security) = C/S/O 와 업무분류 축(doctype) = 문서분류체계 노드를 동시에 판정하고, 결과 레코드에 security·doctype 두 칸으로 나란히 담습니다. 업무분류 축은 자동 생성 doc_rule.yaml(분류체계 내장)이 있으면 켜지고, 없으면 지금까지처럼 C/S/O 만 나옵니다. → 4장

여러 판정 신호(내용·민감정보·보안분류 스탬프·파일명)로 등급을 판정합니다. --file/--dir 만 주면 바로 분류합니다(예전의 --classify 는 이제 붙일 필요가 없습니다). 출력은 기본 json — --file 단건이든 --dir 배치든 JSON 배열 [ … ](그대로 뷰어로 열림)입니다 — 첫 원소가 실행 헤더({"run": …}), 이어서 문서 레코드, 마지막이 요약({"summary": …})입니다 한 건만 넣어도 원소가 셋입니다. --nosummary 면 요약이 빠집니다. 줄단위로 스트리밍/처리하려면 --format jsonl(문서당 1줄).

Python 판과 달리 기본은 꺼짐이라 --daemon 을 줘야 씁니다. --status·--stop·--idle-timeout 의 뜻과 출력은 Python 판과 같습니다. 파일마다 exe 를 한 번씩 부르는 연동(엠파워 v11)을 위한 기능으로, 실측(txt 20건, 한 건씩 호출)은 건당 1.29초 → 0.19초였습니다. 서버와 호출은 같은 계정이어야 서로 찾습니다(접속 기록이 %LOCALAPPDATA%\MpowerClassify 에 있습니다) — 계정이 다르면 양쪽에 환경변수 CSOCLASSIFY_STATE_DIR 로 같은 폴더를 주세요. 두 판의 서버는 서로 별개입니다(Rust 호출은 Rust 서버만 씁니다).
Rust 판도 필요할 때만 모델을 읽습니다(2026-09-02). Rust 판은 상주 서버를 쓰지 않으면 실행할 때마다 모델을 새로 읽는데, 이제 1차 규칙 스캔을 끝낸 뒤 "임베딩할 문서가 하나라도 있는지"를 먼저 보고 없으면 모델을 아예 올리지 않습니다. 전 문서가 규칙으로 확정된 실행에서 [MpowerClassify-rs] 임베딩 불필요(전 문서 규칙 확정) → 모델 로드 생략 이 찍히면 정상입니다. 실측: 규칙으로 확정된 문서 1건을 --file 로 부를 때 1,133ms → 18ms.
※ 같은 날 --embed-needed 가 Rust 판에서도 실제로 동작하게 됐습니다. 예전에는 인자를 받아만 두고 무시해서, seed 파일이 없으면 임베딩이 통째로 생략됐습니다(파이썬 판은 언제나 동작). 이 인자를 주면 못 정한 문서의 vector 가 결과 레코드에 함께 실립니다(파이썬 판과 같은 뜻). 아무 인자도 안 준 기본 실행의 출력은 예전 그대로입니다.
유휴 자동종료 = 무한(2026-08-16 변경). --idle-timeout 을 지정하지 않으면 데몬이 자동 종료되지 않고 계속 상주합니다(반복 실행이 항상 빠름). 유한하게 두려면 --idle-timeout 600(초) 처럼 주세요. 명시적으로 내리려면 --stop.
데몬 프로세스 찾기 — 작업관리자에 왜 안 보이나? 데몬은 콘솔 창 없이(CREATE_NO_WINDOW) 백그라운드로 떠서, 프로세스 이름이 MpowerClassify.exe 입니다(exe 배포 기준. 소스로 python -m csoclassify 실행 시엔 python.exe). 매 호출의 클라이언트도 같은 이름이지만 즉시 종료되고, 계속 남아 있는 MpowerClassify.exe 하나가 데몬입니다. 찾는 방법:

· 종료는 MpowerClassify.exe --stop(권장) 또는 해당 pid 종료.

form · path · structure 세 신호는 없어졌습니다 2026-09-07 — 설계에는 있었지만 어느 규칙도 그 필드를 채우지 않아 한 번도 돌지 않았습니다. 도는 코드와 안 도는 코드가 섞이면 읽는 사람이 매번 "이건 도는 건가"를 되짚어야 해서 두 판에서 함께 걷어냈습니다. 제거 전후로 실제 문서의 판정값은 바뀌지 않았습니다(같은 문서 0.906 → 0.906).

      "signals": { "name": { "c": 0.3, "terms": [ "계약서" ] } } }   // 신호별 기여도 + 근거
  ],
  // 아래 세 칸은 '값이 있을 때만' 붙습니다 — 없으면 기본이라는 뜻입니다.
  "truncated": 2,           // top_n 으로 잘려나간 후보 수. 0이면 칸 자체가 없음
  "conflicts": [ … ],       // 서로 다른 큰 갈래가 동시에 제안된 경우의 경고. 없으면 칸 없음
  "strategy": "top_n:3",    // --conflict 로 덮어썼을 때만. 없으면 규칙 파일이 정한 대로
  "embed": { … }            // 전파가 돌았을 때만(기준 문서 비교 근거)

doctype 축이 간결해졌습니다 2026-09-10 — 판정은 그대로이고, 값이 하나뿐이던 칸을 걷어냈습니다.
· status 제거 — 엔진은 "proposed" 말고 다른 값을 낼 수 없었습니다. 확정은 검토 화면의 몫이고 그 결정은 cso_override.jsonl 에 쌓입니다(원본 레코드는 고치지 않습니다). 문서마다 같은 글자를 적어도 새로 알려 주는 것이 없었습니다.
· truncated — 0이면 생략. 없으면 "아무것도 안 잘림"입니다. 잘렸을 때는 반드시 보입니다 — 무엇이 왜 빠졌는지는 숨기면 안 되니까요.
· conflicts — 비었으면 생략(같은 이유).
· strategy — --conflict 로 덮어썼을 때만. 안 덮어썼으면 규칙 파일에 적힌 값 그대로라 두 번 적는 셈이었습니다. 어느 규칙 파일이었는지는 meta.doctype_rule_version 이 가리킵니다.

임베딩 전파(embed) — 규칙이 못 잡은 문서 분류

보안등급 축과 마찬가지로, seed 저장소가 있으면 업무분류도 임베딩 유사도로 전파합니다. 규칙 파일이 없는 배포에서는 이것이 유일한 분류 수단입니다. 두 축의 전파 방식은 다릅니다:

보안등급업무분류
대상보류(grade=null) 문서만 구제모든 문서 — 이미 라벨이 있어도 후보를 더한다
득표 임계0.70 (이웃의 70% 이상이 같은 등급)0.25 (라벨마다 따로 계산)
이유등급은 하나뿐이라 다수결이 성립표가 동시에 맞는 여러 라벨로 갈리므로 같은 잣대를 쓰면 아무것도 못 넘김

전파로 붙은 라벨은 from 에 "embed" 가 들어갑니다. 이웃 문서와 거의 같은 문서(near-dup)면 그 문서의 라벨 집합 전체를 그대로 물려받고, 그렇지 않으면 라벨별로 따로 신뢰도를 계산합니다. 전파 후에도 조상 흡수와 충돌 전략은 다시 적용되므로, 규칙과 임베딩이 섞여도 결과 형태는 같습니다. 실행하면 화면에 [전파][업무분류] seed=… embed기여=… 벡터없음=… 한 줄이 나옵니다.

전파하려면 그 문서의 벡터가 있어야 합니다 — 임베딩은 느린 단계라 필요한 문서에만 겁니다. 기본(--embed-needed 포함)에서 벡터를 만드는 대상은 아직 못 정한 축이 하나라도 있는 문서입니다:
· 보안등급이 보류이거나 seed_eligible 이거나,
· 업무분류 라벨이 하나도 안 붙은 문서 2026-08-25 추가
두 번째 조건이 없으면, 규칙 없이 도는 배포에서 보안등급만 멀쩡히 나온 문서는 벡터가 안 만들어져 업무분류가 영영 미분류로 남습니다. --rule-only 는 임베딩을 아예 안 하므로 전파도 하지 않습니다(규칙 없이 --rule-only 를 주면 업무분류는 전부 미분류).

추출 본문을 파일로 남기기 — --textsave 2026-09-07 신규

분류하면서 문서에서 뽑아낸 본문을 폴더에 남깁니다. "왜 이 문서가 C 인가"를 사람이 직접 읽어 확인하거나, 규칙을 고칠 때 문서를 다시 파싱하지 않고 같은 본문으로 실험할 때 씁니다.

MpowerClassify.exe --dir "D:\분류함" --textsave "D:\파싱"
D:\파싱\
  ├ 567b4e6e3af751a1…c6769e08.txt   ← 파일명 = 원본의 SHA-256 (레코드의 hash 와 같은 값)
  ├ _index.jsonl                     ← 어느 원본인지는 여기서 본다
  └ _README.md                       ← 취급 주의 안내
이 옵션은 개인정보를 평문으로 디스크에 복제합니다. 분류는 원래 본문을 디스크에 남기지 않습니다 — 이 옵션은 그 방어를 여는 문입니다.
보안등급 C(기밀) 문서의 본문도 걸러내지 않고 그대로 남습니다. 등급으로 거르면 "왜 C 인가"를 확인한다는 목적 자체가 깨지기 때문입니다.
그래서 기본은 꺼짐이고, 폴더를 반드시 지정해야 하며(생략 시 기본 폴더 같은 것은 없습니다), 실행할 때 화면에 경고 한 줄이 나갑니다.
무엇어떻게
파일 이름 원본 파일의 SHA-256. 결과 레코드의 hash 칸과 같은 값이라 결과 한 줄에서 그 문서의 본문으로 바로 갈 수 있습니다. 길이가 64자로 고정이라 긴 경로·한글 파일명 문제도 없습니다
같은 문서가 여러 개면 .txt 는 한 개만 생깁니다(내용이 같으므로). 요약이 내용이 같은 N건은 한 파일로 합쳐졌습니다 로 알려 주니, 파일 수가 문서 수보다 적어도 빠진 것이 아닙니다
어느 시점의 본문 정제·절단까지 끝난 것 — 도구가 실제로 보고 판정한 그 텍스트입니다. 그래서 --max-text-chars 로 잘린 문서는 뒤가 없습니다(색인의 truncated 가 true)
본문이 없으면 파일을 만들지 않습니다. 0바이트 파일을 남기면 "저장됐다"로 오해되기 때문입니다. 레코드에 text_saved 키가 없는 것으로 구분합니다
저장이 실패하면 분류는 그대로 끝까지 갑니다 — 등급도 종료코드도 바뀌지 않습니다. 대신 레코드에 text_save_error, 요약에 저장실패=N 이 남습니다

색인 _index.jsonl — 한 줄에 한 문서입니다. hash 이름만으로는 사람이 못 알아보므로 이것이 원본과 잇는 유일한 다리입니다.

{"hash":"567b4e6e…","txt":"567b4e6e….txt","file":"D:/분류함/01_제품매뉴얼/MCCS 이중화 테스트 시나리오.xlsx",
 "doc_id":null,"chars":18452,"truncated":false,"ts":"2026-09-07 15:02:11"}

같은 문서가 여러 경로에 있으면 .txt 는 하나지만 색인 줄은 경로마다 쌓입니다 — 중복 제거의 이득은 챙기면서 "어느 경로들에서 나왔는지"는 잃지 않습니다. 같은 폴더에 다시 돌리면 줄이 이어붙습니다(어제 색인을 오늘 실행이 말없이 지우는 것이 더 위험하므로). 새로 시작하려면 폴더를 비우세요. doc_id 는 --filelist 로 sfile_id 를 얻은 문서에만 값이 있습니다.

두 판이 같은 폴더를 쓰면 안 됩니다. 저장하는 것은 원본이 아니라 추출한 본문이고, 파이썬 판(사이냅·하이브리드)과 Rust 판(순수 Rust 파서)은 같은 문서에서도 본문이 다르게 나옵니다(실측: 같은 PPTX 가 9,312 / 9,330 바이트). 섞이면 남의 본문을 자기 것인 양 가리키게 되므로, 같은 이름인데 내용이 다르면 덮지 않고 오류로 알립니다 — 저장실패=N 이 뜨면 폴더를 나누세요.

10 중요: Seed 관리와 Drift 방지

[중요] 이 섹션은 seed 파일 관리 시 절대 규칙입니다. 지키지 않으면 자동 분류 결과가 시간이 지나며 오염될 수 있습니다.

핵심 원칙: Drift 방지

임베딩 기반 전파는 "후보"를 만들 뿐 최종 기준이 아닙니다. 전파로 붙은 등급을 다시 seed로 사용하면 초기 오분류가 스스로를 강화하며 코퍼스 전체로 번진다는 원칙이 있습니다. 이를 Drift라 합니다:

[원칙] 전파로 붙은 라벨은 절대 seed 가 되지 않는다.
seed 자격은 다음 두 경로뿐이다:
(a) 1단계 규칙 고신뢰만 (rule-based confidence ≥ threshold)
(b) 사람이 수동으로 확정한 것

이 규칙이 깨지면 초기 오분류가 스스로를 강화하며 코퍼스 전체로 번진다.
